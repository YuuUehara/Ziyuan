# 路线图

各版已完成的变化见 [CHANGELOG.md](../CHANGELOG.md)。

**当前版本为 1.2.0。** 交付小说翻译的后续三阶段（单块翻译闭环、断点续做、Web 审阅）与御笔札记，作品关注并入武英殿并可自动入队；发布流程加入 crates.io 可信发布。1.0.0 以 rc.4 为最终基线。冻结范围以[稳定性约定](stability.md)为准，ChatGPT 订阅与 HTTP MCP 仍为实验性。下列早期路线保留作历史记录，当前的 1.2.0 交付见文末。

## v0.6.0（已发布）

v0.5 让朝廷能常驻、能记事、能接外界，但不少本事只有命令行用得上，几项外部对接也没在真实环境里跑过。v0.6 的重点是**补齐与落实**：各前端用得上，长期跑得动，真实环境验得过。按优先级排列：

1. ~~**奉天门补齐：Web 与 TUI 追上 CLI**~~ 已完成：Web 可开关常朝（`serve` 内常驻执行与自动复核）、下诏表单可授外藩（MCP）、有「礼部修 CHANGELOG」按钮与实录检索框、驿传诏令可一键回报 GitHub；TUI 补上复勘、平反与实录。规则仍只在 governance 一处。
2. ~~**事件簿版本与兼容**~~ 已完成（按实情调整）：已发布的旧版本改不了，兼容只能由新版保证。逐一用 v0.1–v0.5 发布时的解码器试读样本，定下每种事件（含后加的字段与代码）最早能被哪一版读；样本入测试，保证新版读得回各版写下的事件簿。`ziyuan migrate` 检查本版能否读、打开它至少要哪一版，指出最先要求该版的一行；读不了时指出行号与原因。格式仍为 v1，无需迁移；放弃「首行记格式版本」——每行已带 `v1`，另加首行反而会让 v0.4/v0.5 连新建的事件簿都打不开。升级提示带上本版版本号。彩蛋：史官记「祖宗成法不可轻改」。
3. ~~**长期运行：快照与回放提速**~~ 已完成：按每件诏令 16 条事件（6 次工具调用与用量、约 1.6 KB 回奏）造事件簿，release 版冷启动 `ziyuan court`：1 千件 25 毫秒，1 万件（17 万条、46 MB）0.23 秒，5 万件（85 万条、230 MB）1.1 秒。其中八成是读入与解码（大头是回奏全文的 hex），回放只占两成，快照省不下多少，故不做。真正的瓶颈在前端：1 万件时 Web 每次刷新要传 26 MB、渲染 1.7 秒，起居注 0.76 秒。现在页面只列待理会的诏令与最近 50 件（「全部列出」可看全部），起居注 Web 只回最近 500 条、TUI 只列最近 1000 条；事件类型不再靠编码整条事件求得。1 万件时刷新降到 8 毫秒（页面 14 毫秒），起居注 21 毫秒。内存：回奏全文由事件簿与朝廷状态共用一份、事件枚举瘦身、逐行读取事件簿，`serve` 不再多持一份会话；5 万件时 `ziyuan court` 峰值由 500 MB 降到 312 MB，`serve` 常驻由 648 MB 降到 335 MB。实录检索不再为每件实录建词表，5 万件时由 1.4 秒降到 0.01–0.12 秒，结果不变。后来仍加了快照，并让整本事件簿按需读入：每满 5000 条事件（且不少于上部所收的十分之一）修一部《大明会典》（`.ziyuan/huidian`，存朝廷现状），打开时从会典接着回放其后的事件；整本事件簿只在看起居注时才读入，都察院复核只逐条读过、留下该件诏令的指派与工具调用。5 万件（80 万条、210 MB）时 `ziyuan court` 由 0.69 秒降到 0.33 秒，打开后常驻内存由 291 MB 降到 166 MB（读入会典时峰值 274 MB）。事件簿仍只增不改；会典只是缓存，换了版本、损坏或与事件簿对不上（开头与止处之前的内容另有摘要核对）都不沿用，史官记「会典与祖制不符，以实录为准」并重修，也可随时删去；`ziyuan migrate` 显示会典状况。
4. ~~**准奏落盘进版本库**~~ 已完成：`ziyuan apply --commit`（Web「准奏并提交」、TUI `m`）落盘后只把本诏令写入的文件记为一个 jj 或 git 提交，说明含诏令、承办者与 `Ziyuan-Edict` 尾注；草稿 PR 用同一说明，可与本地提交对应。提交不记入事件簿，旧版本照常可读。
5. ~~**ChatGPT 订阅接入**~~ 已完成（只用模拟服务测过）：`ziyuan login` / `logout`，`ZIYUAN_LLM_PROVIDER=chatgpt` 改走 Responses API，计入订阅额度。
6. **真实环境实测**（进行中）：
   - ~~zsh 与 fish 补全~~ 已实测：修正了 zsh 加载报错与含冒号官职代码补不出的问题。
   - ~~CI 在 Windows 上跑全部测试~~ 已改：先交叉编译到 `x86_64-pc-windows-gnu`、在 Wine 中跑通全部测试。修正了两处 Windows 上的真问题：`run_tests` 原先只用 `sh -c`（Windows 改为 `cmd /C`，并保留 `SystemRoot`、`PATHEXT` 等环境变量）；`search_code` 交给模型的路径用了 `\`（现一律为 `/`）。
   - ~~GitHub 驿站~~ 已在私有测试仓库上实测：issue 与成员 `/ziyuan` 评论入队（普通评论与紫垣自己的回帖不入队、重复拉取不重复入队），评定后回报评论，准奏后开草稿 PR（PR 中提交的说明与本地 `apply --commit` 的相同）。实测发现驿传诏令只有只读玉玺、永远开不了 PR，已加 `github pull --tools`；回奏正文改为如实写明改动状态与 PR 链接。
   - OpenAI / ChatGPT 订阅真实账号有条件时补做。
7. ~~**司礼监分权：Web 令牌分级**~~ 已完成（`ziyuan serve --viewer`）：除皇帝令牌外，可发只读令牌（只看朝廷、起居注与实录，不能下诏、批红、准奏），便于给旁人观政；令牌只存于 `.ziyuan`。
8. **外藩扩容**：挪到 v0.7。

发布到 crates.io 须先逐个发布十个 crate，对外不可撤回，待皇帝另行决定。

## 版本号约定

1.0 之前，加功能的版本升次版本号（0.5 → 0.6），只含修复的版本升修订号（0.6.0 → 0.6.1）。1.0 起，兼容新增升次版本号、兼容修复升修订号，破坏冻结接口的变更留到下一主版本。每次改动先记在 CHANGELOG 的「Unreleased」一节，发版时改为版本号。

## 通往 1.0（历史设想，已完成）

1.0 意味着承诺不再破坏兼容，重点是定下哪些东西冻结：

- 事件簿格式 v1：已有逐版兼容的测试样本，1.0 起写明为长期承诺。
- `.ziyuan/` 下的文件：最终仅冻结稳定性约定列出的格式与语义；会典只是缓存，不在冻结范围内。
- CLI 子命令、参数与环境变量：先清理命名，冻结后只增不改。
- 对外的库 API：只承诺 `ziyuan` 命令行，各库 crate 视为内部实现。
- ~~真实环境：Windows CI 稳定通过，至少一家真实模型服务跑通端到端。~~ 已达成（DeepSeek）。
- 是否发布到 crates.io（发布后不可撤回）由皇帝决定。

实际路线：0.6.0 收尾 → 0.7.0（HTTP MCP 与兼容清理）→ 补做真实模型端到端 → 0.8.0（缺位荐举）→ 0.9.0（冻结前收尾）→ 0.10.0（号舍、改动预览与奉天门改版）→ 1.0.0-rc.1 → rc.2 → rc.3 → rc.4 → 1.0.0。

### 发布线：1.0 与 1.1 新功能分开

1. 1.0 以 [RC-01..07](acceptance/1.0.0-rc.1.md)、[稳定性约定](stability.md)和现有验收记录为依据；未经批准写入、重复外部副作用、假隔离与审计失真仍是阻塞。小说工作流新功能不作为已验收能力塞入 1.0。
2. 1.0 的版本登记与发布流程不引入新运行时能力；后续新增按 1.1 计划独立开发与验收。当时暂缓的 crates.io 发布已在 1.2.0 加入流程，见[发布指南](releasing.md)；本规划本身不执行发版、推送或外部写操作。

### 1.1.0 本轮范围：文本工具、作品更新提醒与易读文档

以下功能在 1.1.0 实现；验证结果与未测项目见验收记录：

1. **整理文本**：导入用户提供的日文、英文纯文本，按完整段落分块，检查候选译稿是否漏段、重复或乱序。不改原件，不自动调用模型。
2. **关注作品更新**：通过 syosetu 的官方作品信息接口，在命令行与 Web 中查看新章节或作品信息变化。可手动检查，也可在 Web 服务运行时开启定期检查；不下载正文、不自动翻译、不发邮件或手机推送。本机程序的公开接口实测超时，不能据此声称联网已验收。
3. **让文档更好读**：先说明能做什么和怎么用，再解释限制。保留必要的权限、费用和人工审核说明，把实现细节放到开发章节。

本轮先交付可靠的小工具，不把后面的完整翻译流程都塞进一个版本。

操作入口：[文本整理与检查](text-projects.md)、[作品更新提醒](subscriptions.md)。检查结果见 [1.1.0 验收记录](acceptance/1.1.0.md)。

### 小说翻译：1.2.0 已交付

长期目标是让用户从有权使用的日／英 UTF-8 原文，逐块完成中译、审校、批准写入及中断后续做，而不是一次把整本书交给模型。原先分四阶段安排，现均已实现（第一阶段在 1.1.0，其余在 1.2.0）；操作入口与限制见[小说翻译指南](novel-translation.md)，工程与浏览器验收见 [1.2.0 验收记录](acceptance/1.2.0.md)。

1. **先整理文本（1.1.0 已交付）**：记录来源和使用权限，按章节、自然段分块，给每段固定编号，检查原文有没有变、译稿有没有漏段或重复。只做本地命令行工具，不调用模型。分块在导入时确定，块上限 48 KiB；改原文或改分块须建新项目。
2. **做好一块的翻译与校对（1.2.0 已交付）**：上下文草稿经 `text context approve` 成为不可变快照；`text translate` 出初稿，`text review` 做两路只读审校，`text zhupi` 写逐段朱批，`text revise` 按朱批优先统稿。准奏门控与结构检查同源，写入只准 `zh.json` 与 `proposals/`，不符即整件拒绝。
3. **中断后能继续做（1.2.0 已交付）**：`text status` 按事件回放与磁盘现状列出每块状态、失效原因与对账提示；`text resume` 只为未开始块下诏，重试失败/撤销须 `--yes`，版本失效与不确定不自动覆盖。失败或撤销的修订不阻塞块，最近一件已准奏译文仍为现行稿。
4. **完善 Web 审阅（1.2.0 已交付）**：武英殿「翰林院 · 译书」卡片按项目→章→块导航，原文 / 已准奏译文 / 待准修订三栏对照，附检查问题与失效原因；下诏、审校、修订、朱批、定稿、退回与上下文批准均可在卡片内发起，只读令牌写入回 403。另加御笔札记（`ziyuan note`），记录用户自己的认可译法，不自动交给模型。

**仍未验证**：没有连续多章的真实模型长跑，也没有长篇一致性与出版质量的证据；本轮实际测过什么、未测什么，以验收记录为准。

### 验收与暂缓范围

- 工程验收覆盖日／英对白、空段、CRLF、Unicode、超长自然段、缺失／重复／乱序 ID、过期输入、逐段取舍、中断及并发操作。部分准奏后必须按实际落盘内容重新检查，不以任务完成或文件存在替代合格。
- 文学验收逐步扩到每种源语言连续三章；在同模型、输入、术语和预算规则下，对比单模型直译与协作流程，记录 tokens、费用、耗时、人修分钟数、术语问题及严重错译。双语人工盲评是独立门槛，模型互评不能替代；若收益不足以抵消成本，不扩建。
- 暂不做自动抓书、自动出版、EPUB / DOCX / OCR、向量翻译记忆库、无审批批量写入、运行中改 DAG、并行写安全承诺或 Windows 原生号舍。保留现有 2–8 子任务、无嵌套分办限制，节点键不等于工具去重，scope 不等于路径级只读 ACL。

### 发布：crates.io 已自动化（1.2.0 起）

早期计划里“crates.io 暂不发布、待另行决定”已经落实为流程的一部分：推 `v*` 标签后，四平台下载包全部验收且 GitHub Release 公开，`release.yml` 的 `crates` 作业再用 GitHub OIDC 换取短期令牌，按依赖顺序发布十个 crate，已在 crates.io 的版本跳过。可信发布须逐 crate 在 crates.io 预先配置，且要求 crate 已存在，因此首个版本仍须手工用 API token 发布；该作业只发布当前标签的版本，不回溯旧版本。crates.io 不能删除版本，只能 yank。步骤与注意事项见[发布指南](releasing.md)。
