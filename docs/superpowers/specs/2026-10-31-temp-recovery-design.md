# 1.2.2 原子替换临时文件清理设计

状态：书面设计已于 2026-10-31 获用户批准；活跃保护协议已按第二轮实验写入下文“租约协议”。未实现、未验收，不授权发版。

## 目标与边界

进程被强杀后，下一次写入或显式清理能处理可证明陈旧的临时文件，不再依赖用户逐个找文件。安全优先于清空目录：无法证明陈旧的项必须保留并说明原因。

首版包含两条入口：

- 正常原子替换前，只扫描本次目标所在目录，不递归扫工作目录。
- `ziyuan text recovery temps [--json] [--yes]` 扫描当前工作目录及其子目录。默认只预览；`--yes` 才删除，每项删除前重新核验，不依赖上次预览结果。不交互等待输入。

不恢复临时文件内容、不猜测目标文件、不修改业务恢复记录或世代号，也不代替 `recovery finish` / `abandon`。工作目录处于待恢复状态时仍可诊断；删除不能涉及恢复协议仍引用的材料。工作目录之外不扫描。

## 已核实的现状

`crates/ziyuan-runtime/src/tools/replace.rs` 的命名为 `.ziyuan-tmp-<pid>-<nanos>-<counter>`，通过 `create_new` 在目标父目录创建。`fill` 在改名前关闭文件；失败时 `discard` 只删除本次文件。进程强杀不会运行 `discard`，因此留下孤儿文件。

工作目录写锁与奇偶世代已存在于 `ziyuan-storage`，但不能据此假定每个运行时替换或旧版进程都持有工作目录锁。另有存储层原子写入路径，本补丁不能顺带按宽泛前缀清除它们。

## 方案选择

采用“目录局部自动清理 + 显式全目录清理 + 活跃所有权核验”。只提供手工命令不能解决下次写入的常见场景；按年龄或 PID 清理不能排除长写入、时钟变化或 PID 复用，均不采用。

组件分为严格候选识别、非阻塞所有权核验、扫描与删除、报告四部分。CLI 只负责解析及呈现，不另写一套删除规则；自动入口和手工入口复用同一核验器。

## 删除不变量

1. 名称须完整匹配三段十进制数字格式，不接受额外后缀、空段、符号或溢出值；分别以 `u32`、`u128`、`u64` 校验 PID、纳秒值和计数。合法名称只是候选资格，不是所有权证明。
2. 只处理普通文件。用不跟随链接的元数据检查路径及遍历目录；跳过符号链接、junction 和其他 reparse point，不进入其子树。硬链接数异常或无法判断身份时保留。
3. 从文件可见之前到替换成功或失败清理结束，写入者必须具有连续的活跃保护；包含创建至加锁窗口、`fill` 关闭句柄至改名窗口及 Windows 改名重试窗口。本设计以同目录租约载体实现，见下节“租约协议”。
4. 清理者非阻塞核验所有权；活跃、锁冲突、协议未知、路径身份变化、权限不足及其他核验错误均保留。不能先释放保护再按路径删除；持有租约锁期间完成删除。
5. 同进程还须有活跃集合或等效互斥保护，不能假定 OS 文件锁排斥同进程其他句柄。双清理者也不得重复删除或误报成功。
6. 读取及删除前再次核对身份；静态链接绝不跟随。与现有工作目录 API 一致，不承诺抵御不受信任进程恶意并发替换祖先目录；不能将此限制说成已具备抗路径攻击保证。
7. 业务恢复记录引用的项不得删除。清理器以调用方构造的受保护相对路径集合为输入，集合无法构造时整轮不删；不读取恢复记录本身，以免 runtime 依赖存储层。

## 活跃保护的技术门槛

不能直接在当前 `fill` 内加锁：函数返回会关闭句柄，改名前便失去保护；Windows 持锁句柄也可能妨碍改名或删除。实施计划的首项必须是跨进程、跨平台可行性验证，证明：

- 创建、发布、写入、同步、关句柄、改名与丢弃整个生命周期均受保护；
- 强杀自动释放活跃保护，但陈旧判定仍有可信的协议归属证据；
- Windows 的打开共享模式、锁范围、改名和删除语义与原有原子替换保证兼容；
- 清理不与工作目录锁形成等待环，不因自己已持锁而重入死锁；
- 新增锁／租约控制文件本身不产生无法安全处理的垃圾或被清理后分裂锁身份。

具体使用文件句柄锁还是独立租约载体，须由上述验证结果决定并补充本设计，不能在验证前声称实现方案已闭合。若必须改变文件命名、引入依赖或扩大控制文件范围，先补充设计供用户审阅。

2026-10-31 已按本门槛做跨进程实验（原生 Windows／NTFS，Rust 1.99.1）：结论是协议尚未闭合，现有锁不能作为删除依据；Windows 上持锁能否被外部改名／删除取决于打开时的共享模式，std 默认值允许，去掉 `FILE_SHARE_DELETE` 则被拒（错误码 32）。证据与未测项见[可行性报告](../../acceptance/1.2.2-temp-lease-feasibility.md)。第二轮实验（租约载体）已闭合该空窗，协议见下节；生产实现与发版须另行批准。

## 租约协议（2026-10-31 第二轮实验结论，已写入本文）

状态：协议在原生 Windows／NTFS 上验证通过并写入本设计；生产实现尚未开始，不表示 1.2.2 已可发版。证据与未测项见[可行性报告](../../acceptance/1.2.2-temp-lease-feasibility.md)。

### 载体与版本

- 位置与命名：与临时文件同目录，文件名为 `.ziyuan-lease-<id>`，`<id>` 为 32 位小写十六进制随机值。租约随目标文件所在目录落地，所以一个目录里的租约只描述该目录中的临时文件，扫描可以逐目录进行。
- 创建方式：`create_new`。同名已存在即失败，第二个写入者据此报冲突并退出，绝不截断或复用他人的租约。
- 内容：恰好一行、以 `\n` 结尾：`ziyuan-lease v1 temp=<临时文件名> id=<id>`。`temp=` 必须是单一普通文件名组件。只排除分隔符不够：Windows 上 `join("C:temp")` 或 `join("a:b")` 会替换整个基准路径，因此按路径组件判断。
- 读取上限 4096 字节。超限、非 UTF-8、读取失败、字段重复一律判为不可解析并保留，不让整次清理以 I/O 错误中止。
- 版本语义：`v1` 之外的任何值都视为“本版不认识的协议”，保留并报告，不作兼容猜测。

### 写入者状态机

相位，括号内为该相位可能的盘上残留：

1. `Idle`（无）：`create_new` 建租约。
2. `Leased`（仅租约，未加锁）：一次写入整行内容，`sync_all`。
3. `Held`（仅租约，已加锁）：锁住租约。
4. `Checked`（仅租约，已加锁）：核验租约路径仍指向自己这个文件（`symlink_metadata` 成立且为普通文件）；不成立即关闭句柄、报错退出，不建临时文件。
5. `Filling`（租约 + 临时文件，内容未完成）：建临时文件、写入、`sync_all`、关闭临时文件句柄。
6. `Renaming`（租约 + 临时文件，内容已完整）：改名；Windows 重试窗口内租约仍然持锁。
7. `Renamed`（租约 + 已生效的目标文件）：关闭租约句柄，删除租约。
8. `Done`（无）。

写入者唯一允许等待的地方是第 3 步取锁，而且必须有上限（300 毫秒量级，超时返回 `TimedOut`）。它取的是自己刚 `create_new` 出来的文件，正常路径不会发生等待，上限只是防止路径被外部替换时无休止挂起。

第 4 步不是可选的保险，而是协议的一部分。`Leased` 与 `Held` 之间是唯一还能被清理器回收的窗口：此时租约合法、未加锁，它引用的临时文件也还不存在，孤儿租约路径完全有理由把它当成残留。原生 Windows 实测：名字被删掉之后，写入者手上那个句柄加锁**仍然成功**（`locked=true gone=true`），所以只看加锁结果发现不了这件事。加锁成功后清理器再也拿不到租约锁，路径不会被再次回收，因此“加锁后核验一次”就是充分的判定；缺了它，写入者会带着一个已被删除的租约继续建临时文件，留下一个没有归属证据、任何清理器都不敢删的临时文件（用例 `writer_aborts_when_its_lease_was_reclaimed_before_the_lock` 的 `unchecked` 分支正是这个后果）。

顺序不可交换：先加锁再建临时文件，保证“临时文件存在 ⇒ 租约已被写入者持有过”。反过来（先建临时文件后加锁）会重新打开第一轮识别出的创建到加锁窗口。

### 清理者状态机

临时文件名里没有租约 `id`，所以归属只能反向找：先列出目录里的租约，再看谁的内容指向这个临时文件。写入与清理两侧都不允许从候选名反推 `id`。

按目录执行，每步都可单独失败，失败一律保留：

1. 逐目录列出候选：目录项名称严格匹配 `.ziyuan-tmp-<pid>-<nanos>-<counter>`，三段十进制分别按 `u32`、`u128`、`u64` 校验，不接受额外后缀、空段、符号或溢出。相似名称不是候选，不进入任何后续判断。
2. 逐目录列出租约：名称匹配 `.ziyuan-lease-<id>` 且 `<id>` 为 32 位小写十六进制。`id` 只从文件名读取。
3. 受保护核验（对每个候选）：候选的工作区相对路径（用 `/` 分隔，与恢复记录同一形式）命中调用方给出的集合，即 `Keep { RecoveryReferenced }`，不打开任何句柄。比较必须用相对路径，嵌套目录里的候选是 `sub/<name>`；只比文件名会把该保护的项当成普通候选。
4. 类型核验：用不跟随链接的元数据判断，不是普通文件（目录、符号链接、junction、其他 reparse point、无法读取）即 `Keep { TempNotRegular }`。
5. 逐个租约非阻塞试锁，永不等待：
   - 任何一个租约被占用即 `Keep { LeaseBusy }`。因为读不到被占用租约的内容，无法排除它就是本候选的写入者，所以整个目录本轮不动。
   - 取得锁后核验租约本身：不是普通文件 `Keep { LeaseNotRegular }`；版本未知 `Keep { LeaseUnknownVersion }`；无法解析 `Keep { LeaseUnparsable }`；`id=` 与文件名不符 `Keep { LeaseIdMismatch }`。这几种都说明“目录里有一份我读不懂或不敢信的归属证据”，本轮不删，报告原因。
   - 内容合法的租约若 `temp=` 指向别的候选，只是不认领，不阻止本候选继续判断。
6. 归属判定：
   - 认领本候选的合法租约恰好一个，**且目录里没有第 5 步那几类读不懂或不认信的租约**，才进入删除。多一份读不懂的租约就有一份它可能同样指向本候选的可能，因此不删。
   - 没有认领者且目录里没有上述租约，`Keep { TempWithoutLease }`。
   - 没有认领者但有上述租约，报那类原因（多份时按 `id` 排序取第一个，仅为报告稳定）。
   - 多于一个认领者，`Keep { TempAmbiguous }`，绝不猜哪一个是主人；此时即使同时存在读不懂的租约，也报 `TempAmbiguous`。
7. 删除：**在持有该租约锁期间**先删临时文件（若此时已不存在则 `Keep { TempAlreadyAbsent }`，不视为失败），再删租约，最后关闭句柄。
8. 孤儿租约：只在取得租约锁、内容合法、其 `temp=` 已不存在时删除（`OrphanLease`）；若 `temp=` 仍在则 `Keep { TempStillPresent }`；无法判断 `temp=` 是否存在（元数据读取失败）也按 `TempStillPresent` 保留，另在报告里记一条 I/O 失败，不把它算作"已确认不存在"；租约已不存在则 `Keep { LeaseAlreadyAbsent }`。这条路径不需要受保护集合：`temp=` 还在受保护范围内时它就是 `TempStillPresent`，会被保留。它可能撞上一个尚未加锁的存活写入者，协议允许它动手，代价由写入者一侧的第 4 步核验承担。

同一目录里的候选与租约都可能有多个，因此报告必须逐项列出：一个候选的处置不改变另一个候选的处置，一个读不懂的租约只影响本轮该目录的删除。

实验里另有一个"调用方已知 `id` 的单租约原语"，它把类型判断放在取得租约锁之后。那不是生产契约，只用来单独验证核验规则；生产入口是上面的目录扫描，顺序以本节为准。

### 原因清单

删除原因只有两个：`WriterDeadLeaseVerified`（租约被持有并核验通过）、`OrphanLease`（合法租约，其 `temp=` 已不存在）。

保留原因是逐项枚举的，报告直接使用这些值，不另作映射：

| 原因 | 触发点 |
| --- | --- |
| `RecoveryReferenced` | 受保护集合命中，未打开任何句柄 |
| `TempNotRegular` | 候选不是普通文件 |
| `TempWithoutLease` | 没有任何合法租约认领它 |
| `TempAlreadyAbsent` | 删除前发现候选已不存在 |
| `TempAmbiguous` | 多个合法租约认领同一候选 |
| `LeaseBusy` | 目录里有租约被占用 |
| `LeaseNotRegular` | 租约路径不是普通文件 |
| `LeaseUnknownVersion` | 租约版本不是 `v1` |
| `LeaseUnparsable` | 内容不合格式、超限、非 UTF-8、字段重复、读取失败 |
| `LeaseIdMismatch` | 租约 `id=` 与文件名不符 |
| `LeaseAlreadyAbsent` | 孤儿租约路径发现租约已不存在 |
| `TempStillPresent` | 孤儿租约路径发现其 `temp=` 仍在 |

`LeaseContentMismatch` 只是单租约原语内部“这份租约不认领该候选”的中间判定，目录扫描把它当作继续判断，不写进报告。

每个原因都有对应用例断言具体值，包括看起来“构造上不可达”的分支。

### 锁顺序

会等待的锁只有两种：工作目录锁（`ziyuan-storage` 的 `.ziyuan/write.lock`，可等待、有截止时间）与租约文件锁（本协议；写入者独占自建文件，清理者只非阻塞试探）。另有执行者锁与 `JsonFile` 的短等锁，同样有上限，且都不参与本协议。

- 写入者：工作目录锁 → 自建租约 → 临时文件。受管事务在锁内调用 `apply_changes`，所以这条顺序同样覆盖“写入前的自动清理”。
- 清理者：只做非阻塞租约试探，不取工作目录锁。
- 因此不存在“持有一把锁、等待另一把”的边，构不成等待环。这一点不只是推断：工作目录锁的两处等待（进程内预约与 `try_lock` 重试）共用同一截止时间，最坏结果是 `WorkspaceError::Timeout` 而非无限等待；同进程第二个句柄取锁会超时，不会重入，已有用例 `independent_handles_exclude_and_drop_releases` 断言。
- 自动清理不得取工作目录锁：它由写入事务在已持锁状态下调用，再取只会自锁到超时。手工清理也不取：会把写入者挡到超时，而且没有收益，非阻塞试探已经足够。
- 核验通过后不得先释放租约锁再按路径删除。释放即失去“核验—删除”的原子性，两个清理者会各自核验通过并各删一次；这个缺陷在受控交错下 10/10 复现失败。
- 孤儿租约路径与写入者之间没有额外的锁：它可能在写入者加锁之前回收一个活跃租约。协议允许这件事，代价由写入者第 4 步的路径核验承担，不引入新的等待边。

### 身份复核

- 锁身份按文件对象，不按路径。改名后在新路径试锁仍为 Busy，硬链接是同一对象仍为 Busy，删除后同名重建可立即取锁。所以路径存在、时间戳、PID 都不能作陈旧判据；能作判据的只有“我持有的这把锁”。
- 清理者取得的租约锁句柄就是它核验的那个对象，核验与删除都基于该句柄；路径只用于删除，删除失败按保留处理。
- 临时文件名里的 PID 只作人工诊断，不参与任何判断。

### 强杀残留处置

| 强杀相位 | 残留 | 决策 | 依据 |
| --- | --- | --- | --- |
| `Leased`、内容写到一半 | 仅租约，内容不完整 | `Keep { LeaseUnparsable }` | 不能证明归属，见已知限制 |
| `Leased` 完成、未加锁 | 仅租约 | `Remove { OrphanLease }` | 内容合法，`temp=` 不存在 |
| `Held`、尚未建临时文件 | 仅租约 | `Remove { OrphanLease }` | 同上 |
| `Filling`、`Renaming` | 租约 + 临时文件 | `Remove { WriterDeadLeaseVerified }` | 取得租约锁，版本、`id`、`temp=` 一致，临时文件是普通文件 |
| `Renamed`、未删租约 | 仅租约 | `Remove { OrphanLease }` | 内容合法，`temp=` 已被改名，不存在 |
| `Done` | 无 | 无 | 正常结束 |

强杀后租约锁由操作系统释放，清理者能在截止时间内取得。对应测试：`killed_before_temp_creation_leaves_only_lease`、`killed_writer_lease_is_reclaimable`、`lease_covers_close_before_rename_window`。

### 失败降级

写入侧：任一步失败时目标保持原文或不存在，且只删除本次自己建的控制文件。

| 失败点 | 处置 |
| --- | --- |
| `create_new` 冲突 | 不写，报冲突；目标不变，不截断他人租约 |
| 写内容或 `sync_all` 失败 | 关闭句柄、删除自建租约、报错；无临时文件 |
| 租约加锁超时 | 同上 |
| 租约在加锁前被清理器回收 | 加锁可能仍然成功，但路径核验发现名字已消失：关闭句柄、报错退出，**不建临时文件**；目标不变 |
| 建临时文件失败 | 关闭租约句柄、删除租约、报错 |
| 写入或同步失败 | 删临时文件 → 关闭租约句柄 → 删租约 → 报错，沿用既有 `discard` 语义 |
| 改名失败（含重试预算耗尽） | 删临时文件、删租约、报错；目标保持原文或不存在 |
| 改名成功但删租约失败 | **不回滚、不报替换失败**。目标内容已生效，残留租约交给后续清理按 `OrphanLease` 处理，报告单独列出 |
| 清理本身失败 | 不阻断新写入；替换结果与清理结果分开报告 |

清理侧：核验不足即保留，绝不以“无法判断”为由删除。

| 失败点 | 处置 |
| --- | --- |
| 目录读取失败 | 报告该目录未能扫描，继续其他目录；手工入口退出码 1 |
| 候选或租约元数据读取失败 | 该候选保留，逐项记 I/O 失败，不中断整轮 |
| 租约不是普通文件 | `Keep { LeaseNotRegular }`，本轮不删该目录的候选 |
| 租约打不开（非 `NotFound`） | 该候选保留并记 I/O 失败 |
| 租约内容读取失败 | `Keep { LeaseUnparsable }`，不把整轮清理变成中止 |
| 删除临时文件或租约失败 | 保留，逐项报告；手工入口退出码 1 |
| 受保护集合构造失败（记录不可读等） | 整轮不删；手工入口报错退 1，自动入口跳过并报告 |

### 受保护路径（恢复记录引用核验）

- 恢复记录的 `targets[].path` 是可移植相对路径：`is_portable_relative` 拒绝空、`\`、`:`、NUL、空段、`.`、`..`。临时文件名只在原子替换内部生成，从不登记进记录，所以记录不会引用“临时文件本身”。
- 但项目文件可能恰好与临时名同形（`.ziyuan-tmp-<pid>-<nanos>-<counter>` 是合法相对路径，写入禁区只排除 `.ziyuan`、`.git`、`.jj`、`.env*`），记录就会引用它，而它按严格命名正是清理候选。这一条才是真实的碰撞，必须显式处理。反过来，禁止写入 `.ziyuan/` 也意味着记录目标不可能落在控制目录内，扫描不必为它做例外。
- 因此清理器以“受保护相对路径集合”为输入：候选的工作区相对路径命中集合即 `Keep { RecoveryReferenced }`，并且不打开任何句柄。集合由调用方（`ziyuan-app` / `ziyuan-cli`，两者已同时依赖 runtime 与 storage）从 `pending_record()` 的所有 `targets[].path` 构造，runtime 侧不引入对 storage 的依赖。
- 比较形式必须一致：集合里的路径用 `/` 分隔且相对工作区根，嵌套目录的候选是 `sub/<name>`。若只比较文件名，`sub/` 下的同形候选会被当成普通候选删除；用例 `recovery_referenced_temp_is_retained` 同时断言了正确与错误两种形式的结果。
- 记录不可读或状态无法判定时整轮不删。自动入口在工作目录处于待恢复状态时本就写不进去（`ensure_writable` 拒绝），跳过即可。
- 扫描不进入 `.ziyuan/` 控制目录：存储层自己的原子写入在那里用 `{name}.tmp-<pid>-<nanos>-<n>`，命名虽然不同，但按前缀宽泛清理会误伤。
- 受保护判断必须在打开任何租约之前完成。用例在没有租约的目录里传入受保护集合：若实现先读租约，只会得到 `TempWithoutLease`，而期望值是 `RecoveryReferenced`。

### 未来共享模块位置

- 临时文件名的生成与校验必须在 `ziyuan-runtime` 内一处定义，`replace.rs` 与清理器共用同一组常量与函数，不允许两处字符串各写一遍而漂移。
- 核验器（候选识别、租约核验、受保护判断、决策枚举）与两条入口同处 runtime；签名接受受保护集合，不读取恢复记录。
- 报告结构由 runtime 给出，CLI 只做解析与呈现，避免第二套删除规则。

### 已知限制

- 极窄窗口：`create_new` 之后、整行内容写完整之前被强杀，会留下内容不可解析、未加锁、且不指向任何临时文件的租约残片。清理器无法证明归属，按 `LeaseUnparsable` 永久保留并报告，需手工删除。这里有意选择泄漏而非误删：残片只有几十字节，而误删会让活跃写入失去归属证据。
- 同一目录里只要有一份读不懂或版本未知的租约，本轮的临时文件候选就都不会删除（`LeaseUnknownVersion`／`LeaseUnparsable`／`LeaseIdMismatch`）。这是宁可不动也不误删的代价：一份损坏的租约会让该目录暂不能自动清理，直到手工删掉它。
- 旧版无租约的临时文件一律 `TempWithoutLease`，不会自动清理。
- 临时文件名回收再用：租约只记录文件名，不记录文件对象标识，“删除临时文件后同名重建”的竞争未验证。
- 同进程活跃集合：租约只覆盖跨进程归属判断，同进程还需活跃集合或等效互斥，本协议未包含。
- Windows 上持锁并不阻止他人改名或删除（std 默认共享模式允许），协议是协作式的，不承诺抵御不受信任进程的并发替换。
- 符号链接与 junction 形态的候选／租约只用“不是普通文件”这一条覆盖，原生 Windows 上创建它们需要额外权限，实验主机没有取到这类样本，因此只用目录形态验证了 `TempNotRegular` 与 `LeaseNotRegular`。
- 硬链接数异常：设计上保留，但原因值、检查方式与用例都还没有定，本阶段不声称已覆盖。

“能够取得文件锁”不能证明旧版写入者已停止。无法证明陈旧的旧文件以 `ownership_unknown` 保留；`--yes` 不是绕过核验的强制删除。首版可能不能自动删除所有历史遗留，须如实说明，不承诺“全部清空”。

## 输出及错误

默认预览不创建控制文件、不加写锁、不删除文件；活跃状态仅为当时观察。`--json` 与文本模式具有相同确认语义，不能隐式清理。

报告至少含模式、扫描范围、候选数、可清理数、已删除数、逐项相对路径／处置／原因，以及未能扫描的目录。可区分活跃、未知所有权、非普通文件、链接、恢复引用、身份变化和 I/O 失败。相似但不匹配的文件不作为可清理候选；测试确认其不受影响。报告不包含临时文件正文、凭据或绝对外部路径。

自动清理失败不阻断本次新写入；清理报告独立于替换结果，不能把“替换成功、清理部分失败”写成替换失败。不得把诊断混入已有 JSON 成功载荷；报告接入沿用现有诊断通道，必要的新增字段在实施计划中明确。手工模式全部完成返回 0，扫描／删除 I/O 失败或无法核验所需恢复记录返回 1，用法错误返回 2；仅保留活跃或未知项不算执行失败，但报告必须明显标出未清理数。

## 验收与交付

| 场景 | 必须证明 |
| --- | --- |
| 独立进程强杀后再次写入／手工清理 | 可证明陈旧的文件清除，目标旧内容或完整新内容不受损 |
| 创建、写首字节前、同步后、改名前暂停 | 另一进程及同一进程清理均保留活跃文件 |
| 两个清理者并行、PID 复用、旧版无租约 | 无误删，未知项明确保留，不按年龄猜测 |
| 相似名称、目录、链接、junction、硬链接 | 不删除，不越界遍历 |
| 只读目录、锁冲突、删除失败、遍历失败 | 报告准确，自动入口仍尝试新写入 |
| 业务恢复未完成 | 不删除被引用材料，不推进世代或解锁业务恢复 |
| Windows 原生跨进程替换与共享冲突 | 保留原有原子性、权限、重试与失败清理语义 |

先验证保护协议，再实现共用核验器、两条入口和测试。只有门槛通过后才将 1.2.2 标为已完成；本设计阶段不修改版本、不发布、不声明平台验收通过。
