# 1.2.2 原子替换临时文件清理设计

状态：书面设计已于 2026-10-31 获用户批准；活跃保护协议仍须可行性验证及补充审阅。未实现、未验收，不授权发版。

## 目标与边界

进程被强杀后，下一次写入或显式清理能处理可证明陈旧的临时文件，不再依赖用户逐个找文件。安全优先于清空目录：无法证明陈旧的项必须保留并说明原因。

首版包含两条入口：

- 正常原子替换前，只扫描本次目标所在目录，不递归扫工作目录。
- `ziyuan text recovery temps [--json] [--yes]` 扫描当前工作目录及其子目录。默认只预览；`--yes` 才删除，每项删除前重新核验，不依赖上次预览结果。不交互等待输入。

不恢复临时文件内容、不猜测目标文件、不修改业务恢复记录或世代号，也不代替 `recovery finish` / `abandon`。工作目录处于待恢复状态时仍可诊断；删除不能涉及恢复协议仍引用的材料。工作目录之外不扫描。

## 已核实的现状

`crates/ziyuan-runtime/src/tools/replace.rs` 的命名为 `.ziyuan-tmp-<pid>-<nanos>-<counter>`，通过 `create_new` 在目标父目录创建。`fill` 在改名前关闭文件；失败时 `discard` 只删除本次文件。进程强杀不会运行 `discard`，因此留下孤儿文件。

工作目录写锁与奇偶世代已存在于 `ziyuan-storage`，但不能据此假定每个运行时替换或旧版进程都持有工作目录锁。另有存储层原子写入路径，本补丁不能顺带按宽泛前缀清除它们。

## 方案选择

采用“目录局部自动清理 + 显式全目录清理 + 活跃所有权核验”。只提供手工命令不能解决下次写入的常见场景；按年龄或 PID 清理不能排除长写入、时钟变化或 PID 复用，均不采用。

组件分为严格候选识别、非阻塞所有权核验、扫描与删除、报告四部分。CLI 只负责解析及呈现，不另写一套删除规则；自动入口和手工入口复用同一核验器。

## 删除不变量

1. 名称须完整匹配三段十进制数字格式，不接受额外后缀、空段、符号或溢出值；分别以 `u32`、`u128`、`u64` 校验 PID、纳秒值和计数。合法名称只是候选资格，不是所有权证明。
2. 只处理普通文件。用不跟随链接的元数据检查路径及遍历目录；跳过符号链接、junction 和其他 reparse point，不进入其子树。硬链接数异常或无法判断身份时保留。
3. 从文件可见之前到替换成功或失败清理结束，写入者必须具有连续的活跃保护；包含创建至加锁窗口、`fill` 关闭句柄至改名窗口及 Windows 改名重试窗口。
4. 清理者非阻塞核验所有权；活跃、锁冲突、协议未知、路径身份变化、权限不足及其他核验错误均保留。不能先释放保护再按路径删除。
5. 同进程还须有活跃集合或等效互斥保护，不能假定 OS 文件锁排斥同进程其他句柄。双清理者也不得重复删除或误报成功。
6. 读取及删除前再次核对身份；静态链接绝不跟随。与现有工作目录 API 一致，不承诺抵御不受信任进程恶意并发替换祖先目录；不能将此限制说成已具备抗路径攻击保证。
7. 业务恢复记录引用的项不得删除；恢复状态不可读或不能完成引用核验时，相关项保留。

## 活跃保护的技术门槛

不能直接在当前 `fill` 内加锁：函数返回会关闭句柄，改名前便失去保护；Windows 持锁句柄也可能妨碍改名或删除。实施计划的首项必须是跨进程、跨平台可行性验证，证明：

- 创建、发布、写入、同步、关句柄、改名与丢弃整个生命周期均受保护；
- 强杀自动释放活跃保护，但陈旧判定仍有可信的协议归属证据；
- Windows 的打开共享模式、锁范围、改名和删除语义与原有原子替换保证兼容；
- 清理不与工作目录锁形成等待环，不因自己已持锁而重入死锁；
- 新增锁／租约控制文件本身不产生无法安全处理的垃圾或被清理后分裂锁身份。

具体使用文件句柄锁还是独立租约载体，须由上述验证结果决定并补充本设计，不能在验证前声称实现方案已闭合。若必须改变文件命名、引入依赖或扩大控制文件范围，先补充设计供用户审阅。

2026-10-31 已按本门槛做跨进程实验（原生 Windows／NTFS，Rust 1.99.1）：结论是协议尚未闭合，现有锁不能作为删除依据；Windows 上持锁能否被外部改名／删除取决于打开时的共享模式，std 默认值允许，去掉 `FILE_SHARE_DELETE` 则被拒（错误码 32）。证据与未测项见[可行性报告](../../acceptance/1.2.2-temp-lease-feasibility.md)；补充协议前仍不得实现生产清理。

旧版 `.ziyuan-tmp-*` 没有可信租约记录。“能够取得文件锁”不能证明旧版写入者已停止。无法证明陈旧的旧文件以 `ownership_unknown` 保留；`--yes` 不是绕过核验的强制删除。首版可能不能自动删除所有历史遗留，须如实说明，不承诺“全部清空”。

## 输出及错误

默认预览不创建控制文件、不加写锁、不删除文件；活跃状态仅为当时观察。`--json` 与文本模式具有相同确认语义，不能隐式清理。

报告至少含模式、扫描范围、候选数、可清理数、已删除数、逐项相对路径／处置／原因，以及未能扫描的目录。可区分活跃、未知所有权、非普通文件、链接、恢复引用、身份变化和 I/O 失败。相似但不匹配的文件不作为可清理候选；测试确认其不受影响。报告不包含临时文件正文、凭据或绝对外部路径。

自动清理失败不阻断本次新写入；清理报告独立于替换结果，不能把“替换成功、清理部分失败”写成替换失败。不得把诊断混入已有 JSON 成功载荷；报告接入沿用现有诊断通道，必要的新增字段在实施计划中明确。手工模式全部完成返回 0，扫描／删除 I/O 失败或无法核验所需恢复记录返回 1，用法错误返回 2；仅保留活跃或未知项不算执行失败，但报告必须明显标出未清理数。

## 验收与交付

| 场景 | 必须证明 |
| --- | --- |
| 独立进程强杀后再次写入／手工清理 | 可证明陈旧的文件清除，目标旧内容或完整新内容不受损 |
| 创建、写首字节前、同步后、改名前暂停 | 另一进程及同一进程清理均保留活跃文件 |
| 两个清理者并行、PID 复用、旧版无租约 | 无误删，未知项明确保留，不按年龄猜测 |
| 相似名称、目录、链接、junction、硬链接 | 不删除，不越界遍历 |
| 只读目录、锁冲突、删除失败、遍历失败 | 报告准确，自动入口仍尝试新写入 |
| 业务恢复未完成 | 不删除被引用材料，不推进世代或解锁业务恢复 |
| Windows 原生跨进程替换与共享冲突 | 保留原有原子性、权限、重试与失败清理语义 |

先验证保护协议，再实现共用核验器、两条入口和测试。只有门槛通过后才将 1.2.2 标为已完成；本设计阶段不修改版本、不发布、不声明平台验收通过。
