# 1.1.0 设计：文本工具、作品更新提醒与易读文档

日期：2026-10-30。基于 main `189c25e9`（1.0.0）。用户已确认以下范围；本文描述待开发功能，不代表已经可用。

## 用户希望得到什么

1. 把有权使用的日文、英文纯文本整理为可检查的小块，不丢段、不改原件。
2. 关注 syosetu 上的指定作品，在命令行和 Web 中知道是否有更新。
3. 不熟悉实现细节的人也能看懂安装、操作步骤和限制。

三个部分独立交付。文本工具不依赖作品关注，更新提醒不调用模型，也不自动创建翻译任务。

## 一、文本基础工具

### 操作与结果

- 新建项目，登记名称、源语言、作者、来源、取得日期和使用权限说明。记录是用户声明，不是软件认证授权。
- 导入用户明确排序的 UTF-8 TXT 章节。首次仅接受日文、英文，目标语言为简体中文。
- 预览段落编号、分块结果和大小，检查用户提供的候选译稿。
- 不调用模型；现有翻译、审阅与批准流程保持不变。

### 文件与分段

应用层新增独立 `text_project` 模块。每个项目放在工作区 `.ziyuan/text-projects/<项目ID>/`，清单带格式版本，原件副本、提示用文本与候选译稿分开保存。ID 由程序生成，不直接把用户名称作为目录路径。

保留原文件字节、行尾和 SHA-256 摘要。识别 LF、CRLF 下的空行分隔；空行保留为排版信息，连续相同内容仍是两个不同段落。每段在同一源版本有固定编号，重新分块不改变编号。

单块提示文件最多 48 KiB，且每个完整自然段必须能放入一块；过长时指出章节和位置，要求用户手动分段，不静默截断。大小按最终序列化字节计算，编号等开销也计入。此限制不是模型窗口保证。空输入、非法 UTF-8 和未知语言拒绝。

1.1.0 不支持原地更新已导入原文；原文变化时导入为新项目，不承诺跨版本自动匹配段落。导入前后检查原件未变，失败不留下可见的半成品项目。

### 候选译稿

候选译稿采用带格式版本的 JSON，包含块 ID 及按顺序排列的 `{id, text}` 段落列表，不用模型猜测纯文本中的编号。逐项检查缺失、重复、乱序、陌生编号和空译文，并核对项目原文副本是否仍与摘要一致。

检查只读取候选文件，不写入项目译稿，不批准、不触发任务。段落齐全不等于译文准确。

## 二、syosetu 作品更新提醒

### 首批操作

接受标准作品链接 `https://ncode.syosetu.com/<ncode>/` 或作品编号；关注列表属于当前工作区。支持添加、查看、取消、手动检查，以及将提醒标为已读。重复关注不新建另一份记录。

CLI 与 Web 共用应用层服务。Web 提供关注列表、最近检查时间、未读提醒、错误状态和手动检查按钮。只读令牌只能查看，不得添加、取消、检查、标已读或修改定时设置。

### 公开接口与边界

使用[官方作品信息接口](https://dev.syosetu.com/man/api/)，只访问固定 HTTPS 接口 `https://api.syosetu.com/novelapi/api/`，不抓正文、不登录、不接收 Cookie 或用户凭据。

按编号请求 JSON，仅索取标题、编号、作者、章节数、最末章节发布时间和作品更新时间。每批最多 50 部作品，显式指定接口返回数量，不依赖默认 20 项。必须设超时和响应大小上限。生产地址固定；测试通过内存替身验证请求和响应，不开放任意 URL 配置。关闭重定向，不跟随响应中的链接发起请求。

官方说明：数据反映通常延迟约 5 分钟，最长可能 2 小时；搜索排除作品和 R18 作品不在普通接口范围内。不承诺即时或全覆盖提醒。

### 更新如何判断

- 首次成功检查记录当前状态，不发旧章节提醒。
- 后续章节数增加且末次发布时间不早于已知记录，提示“发现新章节”，显示观察到的章节数变化，不保证实际新增章节的精确数量。
- 其他作品信息变化提示“作品信息有变化”，不宣称已定位正文改写。忽略评分和系统维护时间。
- 相同已保存变化不重复生成提醒；有未读提醒时再次检查不自动标已读。
- 时间倒退或章节数减少作为异常变化保留旧比较基线，显示待核实，不冒充新章节。
- 查不到、超时、响应损坏分别报错，不判为删除、不清空上次成功记录。其余作品可继续检查。

### 保存与定期检查

关注、成功基线、提醒和检查状态统一保存在 `.ziyuan/subscriptions/state.json`，带格式版本。用独立锁协调 CLI、Web 和多个服务进程；采用同目录临时文件与安全替换。读写使用相同大小上限，保存超限时保留旧文件，不写出之后无法打开的状态。成功基线与对应提醒在同一次保存中提交，避免中断后只保存其中一项。损坏或更新版本的文件明确报错，不以空列表覆盖。

网络等待期间不持有文件锁。请求前记录状态修订，返回后重新读取并核对该关注项仍存在、身份与基线未变；冲突时放弃过期结果或重新检查，不恢复已经取消的关注。

定期检查默认关闭，用户开启后间隔默认 30 分钟，最小 15 分钟。仅 Web 服务运行时生效，不依赖浏览器标签页打开；关闭服务后停止。保存每项下次可检查时间，多个服务先抢占带过期时间的检查资格，防止同时轮询；进程中断后资格到期可恢复。手动检查有短冷却时间，失败采用有上限的退避，不忙循环。

提醒只在本地 CLI/Web 显示。不向邮箱、手机、系统通知中心或其他平台发送消息，不自动下载正文、翻译、下诏或出版。

## 三、文档怎样写

优先整理 README、入门指南、小说翻译指南与路线图：

- 先写结果和最短步骤，再写可选配置，最后写限制与开发细节。
- 首次写“任务（诏令）”“批准后写入文件（准奏）”；后续按上下文选择容易理解的说法，不更改现有命令名。
- “确定性校验”改为“按固定规则检查”，“产物对齐”改为“检查是否漏段或重复”；必要字段名如 `base_hash` 放在开发说明中。
- 保留权限、付费、人工审阅和版权边界，但集中解释，避免每段重复长警告。
- 区分“已可用”“已验证”“计划中”；保留原有验收记录，不把规划写成能力。

不将架构文档和历史发行说明强行改成入门教程，不删除有用的技术细节或伪造已有测量结果。

## 代码组织与兼容

- 文本模型、检查和关注规则放 `ziyuan-app` 的两个独立模块；各自存储、请求与规则分文件。
- 新的本地 JSON 保存逻辑集中在 `ziyuan-storage`，不挤入事件编解码器。
- 命令解析、输出放 CLI；Web 接入共用服务，不在页面上另写更新判定。
- 沿用 serde、serde_json、ring、ureq、Tokio，不新增 crate；app 按需声明已有工作区依赖 ureq。
- 现有 CLI、事件簿 v1 与旧项目照常可用，不改现有事件类型。新增 JSON 文件独立带版本，1.0 忽略它们不等于具备读写新功能的能力。
- 版本号在功能和验收完成后再升到 1.1.0；本设计不创建发行标签或 Release。

## 验收

文本：日英样本、重复段落、空行、CRLF、Unicode、非法编码、过长段落、输出大小边界、错误译稿、原文被改、重复导入和失败无半成品。

提醒：首次不提醒、章节增加、仅信息变化、评分变化、重复检查、已读状态、异常倒退、查不到、限流、超时、损坏响应、重启、保存中断、同时检查与取消关注。

Web：鉴权、只读权限、定时开关、进程退出停止、阻塞请求不拖住页面、长标题、空列表、错误状态及窄屏。离线替身用于自动测试；公开 API 小规模实测单列，不作为离线测试前提。

工程门槛：格式、Clippy、全工作区测试及现有兼容测试通过；Windows/macOS/Linux 文件替换和锁行为由各平台 CI 验证。真实网络与跨平台未测时明确注明，不用单机通过代替。
