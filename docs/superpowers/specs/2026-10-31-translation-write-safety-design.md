# 1.2.x 译书并行写安全设计

状态：方案方向已确认；本文待审阅，不代表已实现或已验收。

## 决定与版本边界

- 1.2.x 先交付译书数据的多进程 CLI / Web 写入安全，再独立设计向量翻译记忆库。具体小版本号在实现计划中登记。
- 首版面向本地磁盘、同一工作目录内遵守协议的紫垣进程。所有参与写入的进程必须升级到支持该协议的版本；不能与 1.2.0 或旧进程混用。
- 首次受管写入登记独立的 writer-protocol 版本标记，供本版及未来版本检查；它不能让已经发布的旧程序自动遵守协议。
- 检测到人工或其他工具的外部改动时拒绝覆盖。不承诺阻止不遵守锁协议的编辑器在检查之后继续写入，不支持网络盘、云同步目录、跨机器写入或恶意路径替换。
- 从 1.3.0 开始分阶段规划代码任务的并行写安全、运行中修改 DAG、Windows 原生号舍（即 ADR-0001 预留的 `ziyuan-sandbox-windows` 独立 crate）。底层能力必须可用于代码任务，但本设计不据此声称代码任务已安全。

## 现状与问题

`JsonFile::update` 已有进程间锁、锁内重读和原子替换；朱批、札记等单文件更新不应重新发明存储格式。上下文快照以清单最后发布，草稿写入也有临时文件替换。

但这些不能保证跨步骤一致性：

- `Session::apply_reviewed` 先回放、检查、写目标文件，再提交事件，整个过程没有统一的工作目录写锁。
- 运行时 `apply_changes` 先检查全部目标，随后直接逐文件写入；中断时可能留下部分落盘或半份文件。
- 上下文批准、朱批更新、定稿检查与事件提交之间没有共同的互斥边界。
- 事件簿已有带预期长度的提交与残行处理，但它不能单独构成“文件与事件一同提交”的事务。

## 选择

采用工作目录级短写事务、版本校验与持久化恢复记录。

不采用项目／块级细锁作为首版方案，避免跨项目札记、术语晋升和共享事件簿形成复杂锁顺序。不迁移数据库，保留已有可读文件和事件回放方式。

只串行化修改与一致性检查。模型生成、模型网络请求、用户审阅、构建和测试不持有写事务锁。

## 分层与现有机制的复用

代码任务已有一半事务流程：`write_file` 只在内存暂存，完整的 `FileChange`（路径、原文、改后内容）随呈报写入事件簿；`changes_version` 是准奏的审阅版本；`BaseState` 把目标分为仍是原文、已是改后内容、被别处改过，中断后重试准奏会跳过已写文件。缺口是：`fs::write` 非原子；重试可换一组跳过段落，使已写文件与事件不符；进程之间没有写入互斥（`executor.lock` 只排斥同时执行诏令，不管写入）。

因此设计分三层，首版只新建必要部分：

| 层 | 职责 | 首版做法 | 1.3 代码任务如何复用 |
| --- | --- | --- | --- |
| 一、存储层（`ziyuan-storage`） | 工作目录写锁、提交世代号、恢复记录的读写与版本 | 新建；锁接口带范围参数，首版范围恒为整个工作目录 | 直接复用；细化为路径级范围时调用方接口不变 |
| 二、改动集 | 目标从 `Absent`／`Present(hash)` 到新状态的转换、逐目标核对、原子替换、恢复分类 | 由现有 `BaseState` 推广而来，替换 `apply_changes` 的直接写入 | 直接复用；另加待决改动之间的路径冲突检测 |
| 三、领域接入 | 把具体操作翻译成改动集与事件 | 通用准奏与译书材料两类接入 | 代码任务沿用通用准奏接入，再新增隔离与合并 |

复用原则：不另造版本格式，不复制已在事件簿中的内容，不改事件格式。

## 安全不变量

1. 参与协议的程序不能同时执行同一工作目录内的受管写事务。
2. 依赖状态在锁内重新读取；不能用 Web 缓存或旧 Session 的状态批准写入。
3. 基于先前预览的操作须验证该预览版本；版本不符即冲突，不静默改为批准最新内容。无预览的 CLI 直接操作明确表示作用于锁内最新状态，区别见下文。
4. 所有目标先校验，发现外部改动时，在首个目标替换前拒绝整项操作。
5. 单文件只用同目录唯一临时文件、同步与替换，不先删除旧文件，不直接截断目标。
6. 多文件／事件操作允许中断后暂时不一致，但必须留下可识别的恢复记录；不得报告成功，也不得让后续写入绕过它。
7. 恢复只完成同一已获批准的意图，不新增批准、不再次调用模型、不重复记录业务事件。
8. 不把文件系统崩溃、断电、磁盘损坏或外部任意并发编辑概括为已经解决。首版验证进程中断与普通 I/O 故障，不承诺多文件同时可见或断电后的数据库级原子性。

## 组件与依赖

### 存储层：工作目录锁与恢复记录

在 `ziyuan-storage` 提供通用工作目录事务基础设施，不依赖译书类型、Web 或模型。

- 以规范化工作目录定位固定锁文件 `.ziyuan/write.lock`，锁文件不替换、不删除。打开内部路径时保留既有目录／符号链接防护，不接受把控制目录指向外部的别名。
- 排他锁采用操作系统文件锁，等待上限默认五秒；进程退出由系统释放，不靠删锁文件解锁。锁接口接受范围参数，首版只实现“整个工作目录”一种范围；以后细化为路径级时，锁顺序与死锁测试须重做，不能视为免费升级。
- 同进程按规范化工作目录共用互斥量，再取得跨进程文件锁，两层合计共用五秒等待预算。不能假定文件锁一定排斥同进程的其他句柄；平台实现须验证独立句柄、同进程和跨进程语义。Web 的等锁和文件 I/O 均进入阻塞线程，不阻塞异步运行时。
- 固定顺序：工作目录锁→具体 JSON／草稿目录锁或事件簿锁；任何代码不得持内层锁反向申请工作目录锁。
- 私有准备阶段的存活锁是单独的所有权租约，不属于上述业务内层锁：准备者可持租约等待工作目录锁，但清理者持工作目录锁时只能非阻塞试取租约，绝不等待。
- 使用不可复制的事务句柄和内部“已持锁”入口，避免业务方法嵌套调用导致自锁；不使用隐藏的线程局部重入计数。
- 持久化有格式版本、字节上限与内容摘要的恢复记录，损坏或来自更新版本时拒绝写入，不当作空记录。
- 内容暂存与清单分离，首版清单上限 8 MiB、单个暂存文件上限 64 MiB、单操作暂存总量上限 256 MiB；超限在发布意图前报错，禁止偷偷拆成不受保护的写入。通用准奏的内容引用事件簿，不计入暂存上限。既有业务限额继续适用。文件内容先在锁外准备，锁内校验依赖和摘要后发布；不在锁内做模型请求或大规模解析。五秒是等锁预算而非强行终止写入的时限，持锁时间须单独测量。
- 同步指文件内容同步和状态文件原子替换；平台支持时同步目录。首版不把这一机制描述成跨平台断电安全，未能完成要求的文件同步时不能宣告提交成功。
- 恢复资料保存在 `.ziyuan` 内，可能含译稿副本；不得写入密钥或令牌，默认不提交仓库，也不发送到外部。

### 应用层：事务协调器

在 `ziyuan-app` 编排“锁内重读→生成写入计划→校验→准备→落盘→记事件→完成”。

覆盖项目建立／导入、上下文草稿写入及批准、朱批、札记增删改及术语晋升、材料导出、译书下诏／续做、译稿准奏／驳回、定稿／退回。只读检查不创建锁目录或触发恢复写入。

仅靠 CLI 或 Web 包装锁不够，嵌入式应用调用也须走同一边界。所有 `Session` 事件提交与通用准奏入口须遵守外层协调协议，避免代码任务经通用入口修改译书目标或改变同一任务状态时绕过锁。通用准奏的整个选定文件集合均走改动集与恢复记录协议（内容引用事件簿，不另暂存），不按代码／译书另开绕行路径；运行时的直接 `fs::write` 落盘顺序须改为计划式替换。它只改善通用准奏阶段，不覆盖代码执行的任意直接写盘、工作副本隔离、合并冲突等，因此不构成代码任务的完整安全承诺。

协调器先完成路径、容量、权限、输入版本及整项输出的检查，再产生持久化意图。可从源资料重新生成的材料不得绕过现行译稿和待决任务保护。

### 前端：一致的冲突处理

- CLI 返回非零退出码，区分占用超时、版本冲突、需恢复与存储故障。
- Web：版本冲突与需恢复返回 409，等锁超时返回 503 并附 `Retry-After`，存储故障返回 500；未授权请求仍为 401／403，不能泄露恢复内容。客户端可以刷新只读状态，但不能自动重试批准或编辑请求。
- Web 中需审阅的写请求携带对应版本标识；页面过期时保留用户尚未提交的输入，提示刷新和重新确认，不自动重试批准。
- 原有无需预览的命令在锁内读取最新值再执行；编辑已读内容、上下文批准、朱批修改及定稿等基于先前预览的入口，须把所见版本显式带入校验。
- 只读状态可以继续提供，但恢复未完成时显示“不一致／待恢复”，不把部分文件内容当作新的已准奏译稿或有效定稿。

### 读取一致性与版本标识

维护独立的工作目录提交世代号：初始不存在按 0 读取；受管写入在首次修改业务状态前将偶数世代推进到奇数，完整完成后推进到下一个偶数。世代号原子替换、单调递增且不得重置；恢复记录保存本次前后世代，恢复／安全放弃后也推进到对应的新偶数。所有受管材料与事件修改均参与该协议。

应用只读查询不创建文件：先读偶数世代并确认没有已发布未完成意图，读取整份响应所需材料和事件，再核对世代相同且仍无未完成意图。若世代变化或为奇数，最多重新读取两次；仍不稳定返回“写入中／待恢复”，而不是成功返回混合快照。进程中断留下奇数时同样不提供可信审阅载荷。外部编辑不更新世代，仍依各对象摘要和写入前复核处理，不扩大对外部编辑的保证。原始目录直读可能看到不同目标的新旧混合；受管 API 不能把它当一致结果。

版本标识沿用现有 `changes_version` 的格式：`sha256:` 加小写十六进制，各字段带长度前缀拼接后求摘要。准奏的 `expected_version` 就是现有的 `changes_version`，字段名与参数名不变，与现有客户端兼容；所选跳过段落照旧单独提交，并固定在恢复记录里；任务状态与目标现状在锁内经 `BaseState` 核对，不并入版本号。不另造第二种格式；其他操作按同样编码包含工作目录身份、操作种类、目标身份和依赖值。不是权限令牌，不含密钥。工作目录身份采用规范化绝对路径，必须与锁键使用同一规范化规则；移动工作目录会使既有预览失效，有未完成操作时不支持移动，须先完成恢复。每个操作返回独立的 `version`，写请求带 `expected_version`，CLI 对应 `--expected-version`。校验在写锁内重算，不只比较全局世代，避免无关对象变化造成所有页面过期。

| 操作 | 版本摘要依赖 |
| --- | --- |
| 编辑／删除札记、朱批 | 对象 ID、存在性、当前完整内容与其版本；追加新对象由锁内状态分配 ID |
| 草稿修改／术语晋升 | 目标草稿摘要、来源札记内容；多文件修改覆盖所有目标 |
| 上下文批准 | 项目身份、完整草稿文件清单及摘要、当前已批准快照身份 |
| 准奏／逐段取舍／驳回 | 现有 `changes_version`（不变）；所选段落单独提交并记入恢复记录；任务状态与目标原文在锁内另行核对 |
| 定稿／退回 | 块身份、译稿摘要、现行上下文与块朱批摘要、现行 writer 与定稿状态 |
| 下诏／续做／材料导出 | 项目与块身份、相关材料摘要、未结任务和现行版本；从锁内最新状态计算，用户所见预览若作为批准依据则必须带版本 |

保留无预览 CLI 的直接操作语义：省略 `--expected-version` 明确表示“对获得锁时的最新状态执行本命令”，而非对先前浏览过的版本执行。这是兼容现有直接命令的例外，不可用于声称保护了此前的人工审阅。凡本程序展示预览再进入批准／编辑流程时，必须传递该预览版本；预览输出及建议复制的命令须包含 `--expected-version`。文档须提醒分步运行 show／diff 后的人工操作携带版本；程序不能判断用户是否另在外部看过旧内容。Web 编辑和批准必须提供版本；缺失时返回 400 提示刷新。不能把用户输入覆盖到新内容后再声称版本检查通过。

## 写入与恢复协议

### 写入计划

先完整准备一个意图，包含操作 ID、工作目录身份、业务对象、所有目标的相对路径、原有／新内容摘要与存在性、暂存内容引用，以及预期事件簿位置和确切待提交事件。

目标状态明确区分 `Absent` 与 `Present(hash)`，旧、新两端都可为不存在，覆盖创建、替换与删除；1.2.x 的删除只用于材料操作，通用准奏的删除留到 1.3。删除前也核对旧摘要；删除后的恢复按新状态不存在处理，不能把意外丢失的普通文件当作已成功删除。札记删除通常是重写 JSON，不据此虚构必须删除的业务文件。

内容来源分两种，不重复保存：

- **通用准奏**：恢复记录存诏令号、`changes_version`、选定的跳过段落、预期事件簿位置与待写事件，以及每个目标的旧／新 `Absent`／`Present(hash)` 状态（摘要很小，存下可防后续版本的推导逻辑变化）；不复制文件内容，内容从事件簿中该诏令已记下的 `FileChange` 读取。事件簿只追加、残行处理只截掉末尾的不完整行，且已发布意图期间不允许其他写入，因此被引用的内容在恢复期间存在且不变。记录固定当时批准的选择；恢复与重试必须与之一致，不能换一组跳过段落。事件簿中的呈报内容与记录的 `changes_version` 不符时停止恢复。`FileChange` 本身不变：仍只支持文字的新建与改写，删除和二进制留到 1.3 随事件格式升级处理。
- **不经事件簿的材料操作**（如札记晋升术语、上下文草稿写入、材料导出）：内容另行暂存为独立文件，受容量上限约束。

未准备完成的临时文件不改变现行状态。清单与暂存内容都持久化后，才发布可恢复的意图；它们必须足以独立完成恢复，不依赖进程内存。多文件上下文快照仍以完整清单作为发布点，不暴露写了一半的快照为现行版本。

记录状态为 `prepared`（私有暂存，未发布，不阻止写入）、`published`（已发布，普通写入必须拒绝）、`completed` 或 `abandoned`（终态）。终态含操作 ID、摘要与结果，供对账；清理只能删除已验证属于该操作的暂存内容。崩溃留下终态记录不会永久阻止写入：下一写入者在锁内核对并完成世代推进／清理。不能在仍为 published 时靠删除文件“解锁”。

私有暂存以独立操作存活锁标识正在准备的操作。普通写入者持工作目录锁时只能非阻塞试取存活锁，成功且核对目录仅含对应未发布 prepared 内容后才可清理；取得失败则跳过，不能以 PID 不存在、时间久或缺少 published 记录推断可删除。存活锁不得被持工作目录锁的清理流程阻塞等待，避免与等待提交的准备者形成环。

同进程另维护受互斥保护的活跃准备操作集合，先登记再暴露暂存目录，释放租约后再注销；清理须同时确认操作不在本进程活跃集合且跨进程租约可取得，不能仅假定 OS 锁能排斥同进程的其他句柄。验收包含同一 Web 进程内清理与准备竞争，证明不会删除活跃暂存。

### 正常提交

1. 获锁后检查未完成意图，存在则拒绝普通写入。
2. 重读业务状态，核对所有目标、上下文／朱批版本与审阅标识；构造并验证最终事件。状态冲突不自动换基重试。
3. 写入并发布持久化意图，随后推进奇数世代；前者成功而后者中断时，未完成意图本身也阻止可信读取和普通写入。
4. 每次替换前再次核对该目标的旧／新摘要，然后执行原子替换。此二次检查不宣称消除了外部编辑的竞争窗口。
5. 提交同一意图内的确切事件；没有业务事件的纯材料操作也须完成其持久化步骤。
6. 确认文件、完整事件批次与清单均对应意图后标记 completed，推进偶数世代，才返回成功。之后清理仅属于该意图的暂存文件。

### 中断与恢复

不自动回滚，也不把“内容碰巧相同”单独作为准奏成功依据。

提供 `ziyuan text recovery status`（只读）和 `ziyuan text recovery finish <操作ID> --yes`（显式完成）。尽管入口在译书命令组，记录须清楚标出通用准奏操作；不得将代码准奏误标为译书批准。恢复命令获同一工作目录锁，重新核对：

- 若已有 completed／abandoned 终态但世代仍为该操作的奇数，status 只读报告“已完成，待收尾”并给出同一 finish 命令；finish 不需要从可信预览取得版本令牌，只接受操作 ID 与显式确认，核对终态及其目标／事件证据后推进记录的偶数世代并清理，不能再次执行业务写入。Web 给出此指引，避免依赖发起另一项新写入才能解除读取阻塞。
- 每个目标必须恰为意图的旧内容或新内容；出现第三种内容、路径越界、文件缺失与预期不符、暂存损坏则停止，保留资料供人工处理，不强制覆盖。
- 尚为旧内容的目标可完成为已批准的新内容；已是新内容的跳过。
- 以保存的事件簿位置和确切编码核对完整事件批次，包含时间事件。已完整出现则不再追加；仅出现确切前缀时只补齐其余部分，不重复前缀。
- 事件簿出现不匹配的新事件、有效历史被改动、未知完整事件或无法判断的状态时停止；不得靠业务状态看起来相同或仅比较事件条数来猜。
- 残行处理遵守现有存储规则；恢复不得删除有效事件。须有专项测试证明前缀／残行边界，不能复用普通 `Session::commit` 的自动重提议循环完成恢复。
- 检查前后目标均不再匹配时，维持待恢复状态；不提供通用的 `--force`、删除恢复记录或批量回滚入口。

提供严格受限的 `ziyuan text recovery abandon <操作ID> --yes`：仅当全部目标仍为旧状态、该批次未写入任何完整事件或残片、事件历史符合准备时的位置与身份时允许，标记 abandoned、推进偶数世代并保留终态摘要。已部分落盘或写入事件时拒绝放弃；它不是绕过恢复的删除记录功能。

遇到第三种内容时，支持的人工路径是先停止所有写入进程，备份整个工作目录（包括外部改动和恢复资料），再由用户把冲突目标恢复为意图记录中可验证的旧／新状态，之后重新执行 finish。暂存文件损坏仅可用摘要完全匹配的备份恢复；若全部目标均恢复旧状态且无事件，才可 abandon。恢复资料或历史无法核实时，不提供猜测性修复：需从一份完整一致的工作目录备份恢复，并保留当前现场用于排查，不选择性抹掉有效历史。指南须明确这种情况可能需要人工停机恢复。

Web 首版只展示待恢复操作和 CLI 指引，不自行启动恢复。未完成意图会阻止所有参与协议的后续写入；不升级的旧进程是明确不支持的混用场景。

## 兼容与范围控制

- 不重写已有项目、朱批、札记或事件历史；恢复记录独立版本化。新接口或事件若改变可读性，必须按现有版本兼容规则处理，禁止声称旧版本可安全混用。
- 现有写命令保留名称；新增版本参数、JSON 返回字段、Web 状态码和恢复命令在指南中逐项说明。
- 通用准奏的内容引用事件簿，不受暂存上限影响，现有代码准奏的可提交规模不变；恢复记录清单的上限仍适用，超限时拒绝而不是静默截断，须在升级说明中写明。
- 不改事件格式：`FileChange`、准奏相关事件保持原样，恢复记录与世代号是独立的新文件。
- 不包含动态 DAG、Windows 原生隔离、自动抓书、自动出版、文档格式转换或无审批批量写入。
- 向量翻译记忆库在此基础上另做设计，须决定定稿入库、退回失效、模型与维度、索引重建、引用来源和数据外发授权；索引生命周期、内容适配器、范围过滤与检索接口要评估后续代码检索的复用成本，具体要求见[路线图](../../roadmap.md)。本设计不增加嵌入模型调用或向量依赖。
- 与记忆库的接口：索引是可从事件簿与定稿重建的派生数据，不走写事务，不产生恢复记录。索引记下自己覆盖到的事件簿位置与提交世代号，作为新鲜度水位；水位落后即视为过期并增量更新，处于奇数世代或有未完成意图时不入库。1.3 的代码索引以提交号或工作区内容摘要作为同类水位，复用同一过期判断。

## 验收门槛

不能只用同进程线程测试证明进程间安全。以同步屏障控制独立进程的竞争顺序，避免任意 sleep 充当复现条件。

| 场景 | 必须证明 |
| --- | --- |
| 两个 CLI／CLI 与 Web 同改上下文、朱批、札记 | 无丢失更新；过期审阅明确冲突；相同快照批准不制造竞争性重复版本 |
| 同进程两个 Web 请求、写入期间读取三栏材料 | 同进程也互斥；异步运行时不中断；受管读取不把混合版本作为成功响应 |
| 同一块重复下诏、重复准奏、准奏与定稿／退回竞争 | 依锁内最新状态决定；不重复落盘／记事件，不用旧上下文定稿 |
| 术语晋升与上下文批准竞争 | 草稿、快照、晋升结果有明确先后，不产生混合快照 |
| 通用准奏入口与译书写入竞争 | 不能绕过协调器；只读／观政权限不扩大 |
| 外部修改目标、删除目标或更换路径类型 | 在检测到变化后拒绝覆盖，保留外部内容 |
| 第一个／中间／最后一个文件替换前后终止进程 | 无半份目标文件；恢复记录可读；后续写入被阻止；显式完成后对账一致 |
| 事件尚未写、只写时间事件、只写部分事件、完整写入但未完成清理 | 恢复不丢有效历史、不重复业务事件，不假报已完成 |
| 锁持有者异常退出、等锁超时、嵌套业务调用 | 系统释放锁；超时可诊断；锁顺序不死锁 |
| 磁盘写失败、暂存损坏、记录版本过新 | 不重置状态、不猜测恢复、不把失败记为成功 |
| 标记终态后、偶数世代推进前中断；完成后未清理 | 只读 status 可给出收尾指引；finish 无需新预览即可安全收尾，不重复业务写入 |
| 仅发布未落盘、创建中断、材料操作的删除中断、私有 prepared 遗留 | 安全放弃有严格前提；Absent／Present 状态恢复准确；清理不删除活跃准备者的文件 |
| 准奏中断后用另一组跳过段落重试或 finish | 拒绝；结果只能与恢复记录固定的选择一致 |
| 旧数据与原有代码任务 | 无自动迁移破坏；现有代码任务测试仍通过，但不扩大安全承诺 |

在 Windows、Linux、macOS 各自运行针对性进程竞争与恢复测试，并执行工作区格式、clippy、测试和既有 smoke 检查。Linux／macOS 未跑或场景不支持时按平台记录，不以 Windows 结果替代。
