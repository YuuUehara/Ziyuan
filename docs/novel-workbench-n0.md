# N0：人工稿、人物与术语数据契约及验收基线

日期：2026-11-02。状态：**N1a-1／N1a-2a 已推送且原生 CI 通过；N1a-R1 文学标记草稿本地实现，批准链路尚未开放**，范围与验证见第 8、9、11 节。上位规划见[小说工作台计划](novel-workbench-plan.md)。本页确定行为与所有权，不冻结命令拼写、磁盘路径或事件编码；不授权付费调用或发行。

## 1. 现有契约与实现入口

- `text_project/model.rs`、`split.rs`：段落 ID 与提示块分离；原件字节及位置是来源依据，不重切旧项目。
- `text_project/validate.rs`：块级候选须含全部原段 ID、顺序正确、译文非空；草稿不能直接当候选送入这个检查，也不能放宽旧检查。
- `translation/session.rs::finalize_translation`、`status.rs`：当前定稿须能回查已准奏 writer 任务，并核对磁盘、原文、上下文、朱批。**当前不支持无模型的人工定稿来源。**
- `translation/gate.rs`：核对实际选择的最终译稿字节与允许路径；人工批准须复用结构与版本检查、受管写入的语义，不新造直接写盘旁路。
- `translation/context.rs`：GlossaryEntry 拒绝未知字段，scope 是自由文本；现有批准快照持久化上下文，不能直接给旧数组塞新字段。
- `ziyuan-core/src/event.rs`、`ziyuan-storage/src/codec.rs`、`ziyuan-governance/src/{translation,replay}.rs`：人工来源的新增记录必须覆盖编码、回放与最低读取版本；[稳定性约定](stability.md)允许新增事件，不允许改旧事件含义。

## 2. 共用身份、版本与错误规则

下列字段名是设计用语；实现可按现有类型命名，不另造通用工作流框架。

| 概念 | 必须保存的事实／约束 |
| --- | --- |
| 位置 | project、chapter、block、paragraph；必须通过项目模型核对归属，用户输入 ID 不是任意磁盘路径 |
| 来源绑定 | 当前项目来源摘要、块来源摘要；保留原文，不规范化 Unicode 后冒充同一版本 |
| 修订 | 不可复用的文档修订身份，及完整持久字节 SHA-256；删除重建也不得让旧基线再次有效，不用时间戳判相等 |
| 操作者 | 经本地／Web 权限验证的实际操作来源；单人本地模式可记本地操作者，不虚构多人身份，不记录访问令牌 |
| 请求身份 | 保存、提交、批准各自带客户端生成的请求身份及内容摘要；同身份同内容返回原结果，同身份异内容拒绝 |
| 错误 | 区分冲突、来源变化、格式不支持／损坏、权限不足、内容不完整与恢复待处理；不得把读取失败解释为空草稿 |

请求摘要覆盖操作、目标、基线和全部有效输入；不能只对译文字串去重。写锁内先识别已完成的同请求重试，再检查新请求的基线；否则响应丢失后会把已成功请求误报冲突。权限仍须每次检查。

## 3. 人工稿：保存、提交与批准分开

### 3.1 草稿对象

首版每个项目／块只有一份共享人工草稿，段落可独立修改，但保存以整个块草稿修订作并发基线，不实现实时协作或自动合并。

必须保存：格式版本、位置、来源绑定、基线批准来源（无批准稿时显式为空）、上下文版本与朱批摘要、草稿修订、按原文顺序的段 ID／译文、操作者、请求身份。草稿可缺段或空段，但未知／重复／乱序 ID 拒绝；未开始、空草稿和存储错误三者区分。首次从批准稿复制与主动清空均需显式操作，不暗中用批准稿补齐用户清空的段。

保存只发布草稿，不改批准稿、定稿或导出；成功响应必须在可重启恢复后发出。旧修订保存拒绝并返回可比对的当前修订，客户端保留未保存文本，不自动覆盖或丢弃。viewer 不得保存。

### 3.2 生命周期

1. **保存草稿**：可反复进行；没有人工稿不等于没有批准稿。
2. **提交审阅**：冻结不可变提交，绑定草稿修订、完整候选字节、来源、基线批准来源、上下文与朱批；结构检查须通过。提交后继续编辑会产生新草稿，不修改旧提交。
3. **批准或驳回**：仅有写入权限的操作者显式决定，保存者与批准者可为同一人；这不是独立双人审校证明。批准时重新检查所有绑定、块级忙闲状态和受管写入恢复状态；并行模型任务或待决译稿存在则拒绝，不自动取消或覆盖。
4. **批准落盘**：候选作为完整块替换，复用受管写入／恢复协议与结构校验。基线批准来源被另一人工或模型批准替换，即使字节相同也拒绝旧提交；失败不能留下假批准。批准后草稿保留并标明它基于哪次提交，不自动删除。
5. **人工复核／定稿**：批准不等于定稿。人工来源绑定当前原译文、上下文、朱批和来源修订；材料变化显示失效。显式人工定稿不需要捏造模型双审，但必须明确未运行模型审校，并检查无活动任务、结构有效及所有绑定未变。

现行 AI 审校／修订条件不放宽；纯人工与 AI 来源统一供状态、导出及记忆资格读取，但来源必须可辨。有效人工定稿才可进入记忆；未批准草稿不可检索为正式参考。

### 3.3 记录与兼容决策

采用**新增人工提交／批准／定稿事实**，不伪造 EdictIssued、TaskCompleted 或 usage，不把人工修订编码成旧 TranslationKind。共用“当前批准来源”只需区分模型任务与人工批准身份，避免把 task 字段改成另一种含义。

- 人工提交保存不可变内容；批准事实记录提交身份、前一批准来源、候选摘要与全部绑定；定稿事实引用批准身份；驳回／退回保留原因和来源。具体事件数量在 N1a 按最小回放需求确定，不因本页措辞强制一动作一事件。
- 新版须照常读旧日志，保留旧编码与旧 task JSON 语义。新事件提高实际发行版本对应的最低读取版本；旧程序必须提示升级而非跳过。N0 不预占版本号或编码。
- 一旦目录写入新人工来源，不能让旧版仍把旧模型 writer 当当前批准来源；必须有旧版可识别的升级阻断。N1a 在真实旧二进制上验证，不能仅增加一个旧程序会忽略的 sidecar 标志。
- 草稿操作与批准写盘均持工作区写锁；成功请求的去重结果与发布状态必须可恢复。实现前验证现有恢复协议如何覆盖提交对象和新事件，不因“用了原子改名”声称整个流程可恢复。
- 开放人工批准前必须同时更新 governance、codec／readable_since、状态计算、finalize、导出、memory 与适用的 UI／CLI 事实展示。若闭环超过一个可验收小批，只允许独立保存草稿及不赋予批准资格的审阅快照，禁用批准／定稿；不得交付半条批准路径。N1a-2a 的快照与未来准入绑定明确分开，见第 9 节。

## 4. 人物、术语与范围

### 4.1 单一批准词表与人物引用

新上下文使用有版本的术语条目，包含稳定 term 身份、原文形式、类别、允许译法、备注、结构化范围、词证引用与确认状态。**不并建第二个正式词表**。人物对象仅记录稳定 person 身份、原名／读音、别名、称谓规则、口吻例证，并引用 term 身份及出处。

为兼容当前拒绝未知字段的旧词表解析器，人物／术语功能启用时明确引入新版上下文格式与最低写入版本保护；新解析器仍接受旧数组。旧条目 scope 保持说明文字，不自动解析成范围；人工确认后才生成结构化规则。旧快照原字节不变，不回填虚构 term ID 或人物关联；旧条目的编辑升级在新草稿中显式完成。

### 4.2 最小字段与不变量

| 对象 | 字段与约束 |
| --- | --- |
| Person | person_id、原名、可选读音、别名、term 引用、称谓规则、口吻说明／例句、证据；同名不同 ID 合法，别名不自动合并身份 |
| Term | term_id、原文形式、类别、非空 allowed、说明、scope、词证引用、判断状态；人物译名以此为权威，人物卡不复制 allowed |
| 称谓规则 | 被称呼人物、说话人（具体人物／叙述／明确未知）、位置范围、term 引用、说明与证据；未知不是任意说话人的通配符 |
| 证据 | 所属项目、来源段与原文摘要、短引、解释、暂定／确认；外部书目／URL 可引用但不自动抓取。项目事实、角色认知、叙述陈述分开标明，不自动晋升为作品真相 |
| 判断与批准 | tentative／confirmed 表达判断状态；批准上下文版本表达用户允许使用。已批准的暂定资料仍必须标暂定，不能变成硬性校对结论 |

人物身份初始不合并、不删除复用；误建项可停用，旧引用可追查。合并／拆分与自动别名推断不在首版；同名出现必须人工关联后才应用人物特定规则。

### 4.3 位置范围与信息可见性

范围与资料可见性是两回事：scope 回答“这条规则在哪里适用”，available_from 回答“最早何处可以把这条资料用于任务”。

- 位置按项目已确认章节顺序及原段顺序比较，不按文件名、段 ID 字典序或故事时间排序。区间左右端均包含；引用未知位置或起点晚于终点拒绝。
- 范围可取全项目或一个位置区间，并可附说话人／叙述条件；各条件取交集，不取并集。冲突规则同时列出待查，不以最后写入者静默胜出。
- available_from 为明确来源位置；暂定且无来源的笔记不能自动进入请求。未来人物的名称、关系、卡片标题、别名、术语和证据均须一并过滤，不能只隐藏正文字段。
- 首版为**块级模型请求**：可自动选取的资料 available_from 必须不晚于目标块首段，且 scope 与该块存在适用交集。块中段才揭示的资料仍不自动用于整个块，可留给人工查看或显式回修选择；不能声称已在单一提示里实现段间保密。
- 未来资料显式选择只限本次回修，请求预览必须显示泄露风险、完整外发文本、范围与快照；不授予工具权限、不永久放宽筛选。
- 此规则是最小化提示材料，不保证模型不知道剧情或不会自行推断。现有不带范围的全局 style／摘要仍可能包含后文，不能据新增过滤声称旧项目已防剧透；启用严格筛选前须人工检查／升级全部外发上下文，并以实际请求捕获验收。

## 5. 问题报告与版本

报告是可重建派生材料，不是批准依据。必须绑定项目来源、所检查的批准译文身份／摘要、规则快照与扫描范围。每项包含问题身份、类别、当前与参考位置、证据、触发规则、解释及“字面候选／人工确认”的性质。

处理分成 disposition（接受／驳回／待查／不适用）与 resolution（未查／解决／未解决／不适用）；复用现有勘校语义，不把“接受建议”算“问题解决”。合理差异需要理由，且只在绑定版本及位置有效。材料变化令报告或对应处理需复核，不改历史记录；首版可保守整批失效，不承诺最小失效范围。报告缺失、过期、扫描失败与无候选分别显示，不用无候选证明全文一致。

## 6. 自创验收材料与检查层次

[N0 自创样本](fixtures/novel-workbench-n0.json)包含日文三章、自创中文对照、人物／术语与反例。材料由本次 AI 辅助编写，可作为仓库测试夹具使用；不是既有文学作品，也不是双语专家审定的译文，不声称文学水准。位置与 revision 使用样本符号；不是生产文件格式，不把符号当 SHA-256。

- N0 现在检查 JSON 可解析、ID／引用／范围顺序与样本覆盖，及文档本地链接；**没有执行未来产品行为**。
- N1a 起将人工稿场景接公开应用层接口，独立从样本计算真实来源摘要；保存后重启核对实际内容。N2 验证规则适用与外发捕获；N3 验证报告和复核，不新增依赖私有函数或调用顺序的断言。
- 每个场景的预期由本样本预先登记，运行时不得从待测实现反推答案；negative control 明确区分“合理异译”和“同范围错译”。新增行为须有在错误实现下失败的回归。
- 新格式损坏、未来版本、旧二进制拒绝与旧项目不变是必验兼容门槛。实际事件编码、持久化上限及恢复故障注入点在 N1a 开始前登记，不宣称 N0 已证明可恢复或原生通过。

## 7. N0 结项与下一批边界

本设计确定人工来源单独记账、词表单一权威、范围与可见性分离、块级信息过滤及人工问题处理规则。样本不是已通过的功能测试。下一小批建议 **N1a-1：仅人工草稿保存、冲突、重启恢复与去重**；不接模型、不开放提交批准、不改 `zh.json`、定稿、记忆或导出资格。随后 N1a-2 再实现完整人工审批来源闭环；只有兼容与恢复证据齐备才能开放。

## 8. N1a-1 应用层实现与验收边界

本批新增 `Translations::human_draft` 与 `save_human_draft`，供可信本地应用调用；**尚无 CLI 命令、Web API 或人工编辑界面**，不存在新增 viewer 写入入口。未来入口须在调用前鉴权，本地库接口不伪装成多用户权限系统，也暂不记录未经验证的操作者姓名。

- 草稿存 `.ziyuan/text-projects/<项目>/human-drafts/<块>.json`，`JsonFile` 信封格式 v1、文件上限 8 MiB。正文累计至多 256 KiB UTF-8 字节；允许缺段、空段、显式清空，不从现有译稿暗中补段；拒绝未知／重复／乱序 ID。文件与锁以及所经控制目录检查普通文件／目录，拒绝静态符号链接；不承诺抵御并发恶意换链。
- 读取返回当前 basis 和保存时 basis／正文／随机修订身份。basis 含项目与块来源摘要、上下文版本、朱批摘要和磁盘译稿摘要；**磁盘摘要不是批准身份**，人工来源身份及相同字节重新批准的区分仍留待 N1a-2。旧草稿在上下文变化后仍可读取；新保存须显式核对现行 basis。
- 每次新保存发布完整块草稿，要求 expected_revision 与现行随机身份相符；首次须为空。正文与请求摘要、回执同一次 JSON 替换发布。持工作区写锁，拒绝未收尾的受管写入；不推进批准用的 generation，不写事件，不改 `zh.json`。
- 去重范围为项目／块内的 request_id；ID 为 1–128 位 ASCII 字母数字、`-`、`_`。请求摘要覆盖目标、basis、expected_revision 和全部段落。旧同请求重试先于新请求基线检查，返回原修订／内容摘要回执，不覆盖后来正文；同身份改内容返回专门冲突。回执与正文共同受 8 MiB 文件上限约束，不自动淘汰，超限拒绝新保存但保留上次正文、读取与已有回执重试；本批不提供轮换或删除功能，禁止手删内部文件来“清理回执”。
- `DraftConflict` 含现行修订，`DraftRequestConflict` 与 `DraftBasisChanged` 分别表示身份复用和材料变化。损坏、新格式、超限或 I/O 错误沿用可识别存储错误，不重置空稿。现行正文与回执摘要核验可发现未记录的直接手改，不提供防篡改签名保证。
- 恢复含义限定为：正常进程重开或成功响应丢失后，从单份已发布文件恢复正文及回执；不建立多文件批准事务。底层沿用 `JsonFile` 临时文件刷盘、替换与目录尽力刷盘行为；不声称断电安全、强杀故障注入或所有文件系统可用。上下文等现有独立写入仍有各自锁，basis 在保存前及发布前重查，不宣称跨所有旧接口的多文件快照事务。

### 9.2 已实现的审阅快照与格式升级

`submit_human_draft(project, block, DraftSubmit)` 只接受 request_id 和 expected_revision；全文取自该修订的已保存草稿，不接受旁带正文。`HumanSubmission` 冻结 request_id、完整 HumanDraft 与候选字节摘要；`candidate()` 按原有 PromptBlock v1 编码生成完整候选，不复制原文 ruby 等源文注记。复用 `TextProjects::check`，缺段／空白／未知／重复／乱序不能成为提交。

提交身份为项目＋块＋submit＋request_id，与 save 的请求空间分开。同请求及同修订返回原快照；同 ID 换修订返回 DraftRequestConflict。历史重试优先于新修订／basis 检查，不覆写新稿；新的提交须匹配现行草稿修订及当前 basis，发布前重查 basis。没有草稿报错，读取历史快照不会因为材料过期而丢弃它，也不把它标为当前批准版本。列表按请求 ID 排序，不表示时间顺序。

草稿簿信封写为 **v2**，同文件保存现行稿、保存回执与全部提交快照。新版可读 v1（缺省空提交集合），只读／成功旧请求重试不升级文件；首次实际保存或提交才写 v2。v1 读写器须报 Newer 并且保留原文件；未知字段、未来版本、损坏快照／摘要不能静默丢弃或重置。旧日志、译稿和工程未改变；旧程序仍可用旧 AI 功能，并不意味着它理解人工快照。**这仅是草稿文件旧版阻断，不是未来批准事件的全工作区阻断。**

正文仍限 256 KiB，整簿仍限 8 MiB（含快照与回执），不自动清理。超限失败须保留现行稿／历史快照与可重试回执。持工作区锁并拒绝未收尾写入；发布仍只有一次 JsonFile 替换，不推进 generation、不写 court.log／zh.json。沿用第 8 节的文件系统、非恶意并发与非断电保证边界。

**本批快照不绑定“当前批准来源”事件身份，也不记录审批主体，因此不能直接批准。** 后续必须显式准入：重新展示候选与现行材料，核对完整 basis，捕获当时的批准来源身份，再以新的请求冻结审批绑定。不得静默迁移现存 v2 快照为可批准提交；人工修改草稿不会改动旧快照。

### 9.3 审批事件与旧版阻断（待实现）

下列为下一批的行为契约，名称为暂定，不预占事件编号或发行版本。

| 事实 | 最小内容与回放规则 |
| --- | --- |
| HumanSubmissionBound | 明确的准入请求身份／摘要、项目块、快照身份、草稿修订、候选字节与摘要、完整 basis、前一批准来源及经鉴权操作来源；本地快照缺失仍能从权威记录核对批准候选。首次无批准来源显式为空 |

### 9.4 恢复 v2（待实现）

v1 保持读取／恢复能力，不改原格式含义。v2 的 application 为明确 tagged union：model 保留真实 task／changes_version／skipped；human 记录批准操作身份、绑定提交／请求摘要、当前材料及前一批准来源。human 分支只允许对应的批准事件（至多一个前置 Clock），不得夹带模型 ChangesApplied、第二个批准或其他事件；事件、来源、路径、候选字节及前后摘要交叉核对。恢复记录自身的校验与 8 MiB 上限继续适用；超限在任何正文写入前失败。

复用并改造现有事务所有者，不另写人工批准专用的直接落盘器。持工作区锁，预检并固定日志条数／字节数／前缀摘要、完整编码事件批、目标前后状态、候选字节和 generation；准备／发布恢复记录及奇数世代后才写正文，正文就位后追加精确事件批，验证并完成记录、推进偶数世代。失败保留可核验记录，绝不在不确定时自动回滚或盲目重放。

| 中断后的可观测状态 | 允许的恢复决定 |
| --- | --- |
| 正文仍为 before，日志未追加 | 验证输入与来源仍一致后显式继续；或放弃且不发批准事实 |
| 正文全为 after，日志未追加 | 核对日志前缀／候选／来源后仅补精确事件，不再次覆盖正文 |
| 正文为 after，日志已有完全一致的事件批 | 只补收尾；不得重复批准事件或制造另一批准身份 |
| 相同 before/after 字节 | 不能靠文件相等判断批准完成，必须查操作身份与精确事件批 |
| before/after 混合、第三种字节、日志分叉或不匹配事件 | 显示具体不确定证据并阻断；不自动选一边、不抹掉恢复记录 |
| 已完成／放弃但 generation 未收尾 | 对照记录终态与日志／文件再补偶数世代；不能只删标志 |

下一批故障注入需覆盖：发布前、发布后正文前、正文后事件前、事件后收尾前及偶数世代前；每点重启核对真实文件、事件次数、来源身份、重复请求结果和导出／memory 资格。文档中的恢复表不是已经实现或通过的测试。

## 10. 需求补充：能处理注音、着重号的 OmegaT 式工作台

用户明确目标不是纯文本 CAT 加一个注音预览，而是文学标记在**导入 → 对照／编辑 → 保存／冲突／恢复 → 审批 → 导出**中均有明确语义。人物／术语和跨章一致性仍在范围内；本节优先补齐格式契约，不因新需求宣称现有实现已经满足。

### 10.1 当前事实与缺口

- `text_project/document.rs::Inline` 已有 Text、Ruby（基字、读音、源文件字节位置）和 Emphasis。受限 ruby、`《《强调》》` 及 Markdown 的强调已有解析；普通括号不自动视为注音，复杂／破损标记保留字面与警告。不是完整青空／HTML／EPUB 解析器。
- Web `sourceInlineHtml` 能安全显示 ruby，但 Emphasis 统一渲染为 `<em>`，不是语义独立的着重号编辑器。现行模型把粗体／斜体与日文强调折叠为同类，不能还原它们的全部区别，更不含着重点形状、位置或书写方向信息。
- `translation/finished.rs::translated_text` 可从一致的译文 inlines 输出受限 ruby；Emphasis 目前与 Text 一样输出正文，着重语义会丢失。不能把“源文可显示注音”说成“译文编辑／导出已完整保留文学排版”。
- N1a-1／2a 的 DraftParagraph 只有 id／text，未知字段拒绝；快照候选明确不自动复制源文 inlines。当前 API 只覆盖纯文本，不接收结构化译文标记，更不应从含标记的译文降级复制为纯文本后冒充无损编辑。正式接入工作台前必须升级译文契约。

### 10.2 N1a-R 的最小契约（待实现）

1. **译文专用结构**：正文与行内标记有单一权威表示，平文从结构派生或严格核对；源文 byte_start/end 只作原文出处，不能复制为译文偏移。普通字串不重解释为标签；显示不执行任意 HTML。
2. **注音**：基字与读音成对，可选中修改各自内容。保留作者借读音表达另一层意思的可能，不把 ruby 一律当字典发音或术语别名；不能在翻译后自动沿用日文读音。空基字／读音、失配、非法边界在提交时明确拒绝，草稿中的未完成输入必须可恢复且不能冒充可批准候选。
3. **着重独立于粗斜体**：至少区分着重、strong、emphasis；着重的形状／位置等先列明实际支持子集。unsupported 的样式或嵌套可明确拒绝／告警，不能静默改成斜体或普通字。允许的嵌套、同字注音加着重与跨段边界需在开发前固定正反样本，不能假定树模型已覆盖任意交叉范围。
4. **译者主导迁移**：源文标记是参考，不是译文固定坐标；允许人工保留、改写、移动、明确删除。对未处理标记提供提示与逐项确认，不要求源译标签数量机械相等，也不自动把源文范围套到改写后的译文。
5. **全生命周期绑定**：只改读音或着重、正文不变，也必须改变内容摘要、修订、提交与复核绑定，并参与去重和乐观冲突。结构上限同时约束正文、读音、节点数／深度与序列化总量；富标记文件升级后旧读写器拒绝，不忽略新字段。
6. **编辑与辅助**：双语段旁可视预览及可检查标记视图共用同一内容；键盘可选中和编辑基字／读音／着重，支持撤销／重做，下一未译、搜索和术语插入不破坏节点。检索与字数统计区分基字正文和读音，不能把读音又当正文重复匹配。界面批次必须实际验证组合输入、选择边界和复制粘贴。
7. **格式矩阵与导出门槛**：先明确 TXT（具体扩展语法）／Markdown+受限 HTML 各自可表达的标记；标准纯 TXT 无法无损表达样式时显式报告或经用户选择有损导出，不能把丢失说成成功保留。支持格式的往返须保住正文、配对、语义与原章序；未知源标记保留并标出，不能悄悄删除。EPUB／DOCX 的格式适配仍按真实需求另批，不承诺所有站点／格式兼容。

### 10.3 排期与验收

当前 N1a-2a 纯文本快照作为独立基础先验收；在开放人工批准前插入 **N1a-R**：先冻结上述行内模型／格式能力与样本，再小批实现持久化及结构校验。随后恢复／批准事务绑定结构化候选的真实字节，N1b 实现双语标记编辑和导出闭环。不先做一个会丢标记的编辑器，再把注音当装饰补上。

N0 样本追加 `phase=N1a-R` 的格式案例：多字基字、读音与字面含义不同、同字注音与着重、仅标记改动的并发冲突、改译后不自动套用源文位置、未知样式／破损标记、导出能力不足时的显式处理、重启往返。它们是待实现的验收预期，不是当前已通过测试；保留原有三章人物、术语及跨章反例。

## 11. N1a-R1：译文范围标记与草稿持久化

进入条件：N1a-2a 提交 `4908e9b6247b10c12ea2875ae27b09161234800d` 的[六项 CI](https://github.com/YuuUehara/Ziyuan/actions/runs/41380050862)全部成功，包括 Windows／macOS／Linux 原生检查。本节先固定 R1 最小契约，再实现和验收；不把这一小批当作整个文学标记工作台。

### 11.1 数据契约

- 沿用 DraftParagraph 的 id／text，增加默认空且为空时不序列化的 marks。**text 是唯一的基字正文**；每项 TargetMark 含 start、end、kind。范围为当前译文 UTF-8 字节半开区间，不是源文 byte_start/end、Unicode 码点索引或 DOM 偏移。必须非空、在正文内，且两端均为扩展字素边界，不能切开组合字或 emoji 序列；标记不能跨换行或段落。
- kind 是以 type 判别的 JSON 对象：ruby 带 reading（纯文本），emphasis_dots 是圆点着重，strong 是粗体，emphasis 是斜体。例：kind 为 `{"type":"ruby","reading":"ねがい"}` 或 `{"type":"emphasis_dots"}`；四种对象均拒绝未知字段。后续显示位置随版式确定；本批无方向、形状、颜色等样式选项，不隐含支持竖排。原文 Inline 类型不改义、不添加假的源文件偏移。完整实例见 [N0 JSON 的 target_markup_examples](fixtures/novel-workbench-n0.json)。
- 多字 ruby 只有一个范围与一份读音，基字由 text[start..end] 派生，不重复保存。读音是作者／译者提供的另一层文本，不自动改成字典发音、不成为人物或术语别名。草稿 reading 可空或空白，以便恢复未完成编辑；读音不能含换行。标记 JSON 不是 HTML，不执行其中的文本。
- 同一范围可叠加不同种类（如 ruby＋圆点着重）；同种类重复拒绝，即使读音不同也不能为同一基字叠两个 ruby。其余范围必须不相交：当前明确拒绝严格嵌套、部分交叉，而不是把它们压成普通字。相邻范围可用；输入顺序不影响有效性，保存保留输入顺序，不擅自规范化用户正文。
- 全块正文＋全部 ruby 读音合计最多 256 KiB UTF-8 字节；全块最多 4096 项标记；整簿仍限 8 MiB。扁平范围模型不接受子节点或任意 HTML，不需要通过放宽 JSON 深度支持嵌套。
- 所有 marks 参与保存请求摘要、草稿内容摘要与修订冲突。只改读音、着重种类或位置也不能沿用旧修订。改正文但不调整标记，仅在新范围仍有效时可保存；不能推断它仍指同一词，也不能从旧源文偏移自动纠正它。未来 UI 必须提供显式范围调整，本批没有自动迁移。

### 11.2 格式、兼容与本批边界

| 通路 | R1 行为 |
| --- | --- |
| 应用层草稿 JSON | 接受上述四类标记，保存、重读、重试和冲突均保留结构；未知种类／字段或非法范围拒绝，保留旧文件 |
| v1／v2 旧草稿与纯文本提交 | 新版按原义读取，空 marks 不改变旧草稿／回执／候选摘要；读取与旧请求重试不升级文件 |
| 新写入的草稿簿 | 写为 v3，包括普通新保存；v1／v2 读写器必须拒绝，不丢新标记后覆盖；不改旧工程、源文、court.log 或受管写入协议 |
| 含标记草稿的提交／候选转换 | **明确拒绝**，包括读音已填完整的稿；不能调用旧 PromptBlock v1 转换而悄悄丢 marks。已存在的纯文本提交及其重试仍有效 |
| TXT／Markdown／HTML 导入、可视编辑 | 本批不新增格式适配或界面；原有源文 ruby 解析与预览不变，不能自动把旧 Emphasis 认作圆点着重 |

## 12. N1a-R2：无损送审候选与格式诊断

进入条件为 R1 的六项原生 CI 全部成功。本批只扩展不可变送审快照，不接人工批准、受管恢复事务、定稿、记忆、Web／CLI 或正式导出。

### 12.1 编码与校验

- `HumanSubmission::candidate()` 返回独立的 `ReviewCandidate`。无标记时仍是 PromptBlock v1 的原样字段顺序、缩进与结尾换行，历史候选摘要不变；有任意标记时采用候选 schema v2：schema_version、block_id、paragraphs，段中保留 id、text、marks。版本由冻结稿是否含标记确定，不增加另一份权威正文，不复制源文 inlines。
- v2 不是旧模型候选协议的扩展许可：旧 `TextProjects::check` 必须继续拒绝 v2。送审时先校验完整标记（沿用 R1 范围、字素、重叠和容量限制），ruby 读音 trim 后不得为空，但不改写原读音；再用临时纯文本投影复用现有段 ID／顺序／完整性／非空校验。该投影只用于结构检查，不保存、不取代 v2 候选，也不作为候选摘要。
- 实际候选 JSON 的精确字节（含标记顺序与最终换行）参与 candidate_hash；只改读音／着重就改变摘要。新请求仍绑定现行修订与 basis，历史提交重试仍返回原冻结稿，不能因后续改稿或上下文变化重算旧提交。
- 草稿簿新发布升级为 v4，读取 v1／v2／v3 和历史请求重试不升级；支持至 v3 的旧读写器必须拒绝 v4。候选 schema 与草稿簿版本是两种不同协议，不能混用。未知候选版本／字段、损坏候选摘要拒绝；失败保留原文件。

### 12.2 能力矩阵的含义

`ReviewCandidate::check_format` 是只读的**表示能力诊断**，不是导出操作或批准资格。范围限定为下面三个具体表示，不把旧导出的 ruby 扩展 TXT、Markdown、HTML、EPUB／DOCX 报成已支持的新目标格式；这些适配另批实现并做往返验收。

| 表示 | 无标记 | ruby／圆点着重／strong／emphasis |
| --- | --- | --- |
| review_json | v1，候选精确字节可保存和恢复 | v2，全部保留，包含同范围叠加 |
| legacy_prompt_json | 可表示，保留原 v1 字节 | 不可无损表示；逐项列段 ID 与原 marks 索引，不转换或删除 |
| plain_text（无扩展的纯 TXT） | 可表示正文／段落 | 不可无损表示；同上，不把 ruby 字面语法或斜体当替代 |

无效范围、未完成读音和未知版本不能获得“无损”结果。诊断只评价文学标记表示能力，不承诺纯 TXT 保留工程 ID、哈希或往返工程身份，也不暗示生成了任何导出文件。不存在自动有损选项。
