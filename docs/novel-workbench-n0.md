# N0：人工稿、人物与术语数据契约及验收基线

日期：2026-11-06。状态：**恢复双格式与中断样本规划已推送且六项原生 CI 通过；人工译稿 CLI 已打通保存→送审→准奏（落盘）→定稿→导出，恢复收尾与状态分派已加固；Web 人工入口与标记编辑器已开（第 22.31 节），TUI 未开，包版本未升、未发版**，范围与验证见第 8–22 节。旧版独立材料入口并非全部封闭，停旧程序的前提不变。上位规划见[小说工作台计划](novel-workbench-plan.md)。本页确定行为与所有权，不冻结命令拼写或磁盘路径；已实现的事件编码以第 16 节为准。不授权付费调用或发行。

## 1. 现有契约与实现入口

- `text_project/model.rs`、`split.rs`：段落 ID 与提示块分离；原件字节及位置是来源依据，不重切旧项目。
- `text_project/validate.rs`：块级候选须含全部原段 ID、顺序正确、译文非空；草稿不能直接当候选送入这个检查，也不能放宽旧检查。
- `translation/session.rs::finalize_translation`、`status.rs`：当前定稿须能回查已准奏 writer 任务，并核对磁盘、原文、上下文、朱批。**当前不支持无模型的人工定稿来源。**
- `translation/gate.rs`：核对实际选择的最终译稿字节与允许路径；人工批准须复用结构与版本检查、受管写入的语义，不新造直接写盘旁路。
- `translation/context.rs`：GlossaryEntry 拒绝未知字段，scope 是自由文本；现有批准快照持久化上下文，不能直接给旧数组塞新字段。
- `ziyuan-core/src/event.rs`、`ziyuan-storage/src/codec.rs`、`ziyuan-governance/src/{translation,replay}.rs`：人工来源的新增记录必须覆盖编码、回放与最低读取版本；[稳定性约定](stability.md)允许新增事件，不允许改旧事件含义。

## 2. 共用身份、版本与错误规则

下列字段名是设计用语；实现可按现有类型命名，不另造通用工作流框架。

| 概念 | 必须保存的事实／约束 |
| --- | --- |
| 位置 | project、chapter、block、paragraph；必须通过项目模型核对归属，用户输入 ID 不是任意磁盘路径 |
| 来源绑定 | 当前项目来源摘要、块来源摘要；保留原文，不规范化 Unicode 后冒充同一版本 |
| 修订 | 不可复用的文档修订身份，及完整持久字节 SHA-256；删除重建也不得让旧基线再次有效，不用时间戳判相等 |
| 操作者 | 经本地／Web 权限验证的实际操作来源；单人本地模式可记本地操作者，不虚构多人身份，不记录访问令牌 |
| 请求身份 | 保存、提交、批准各自带客户端生成的请求身份及内容摘要；同身份同内容返回原结果，同身份异内容拒绝 |
| 错误 | 区分冲突、来源变化、格式不支持／损坏、权限不足、内容不完整与恢复待处理；不得把读取失败解释为空草稿 |

请求摘要覆盖操作、目标、基线和全部有效输入；不能只对译文字串去重。写锁内先识别已完成的同请求重试，再检查新请求的基线；否则响应丢失后会把已成功请求误报冲突。权限仍须每次检查。

## 3. 人工稿：保存、提交与批准分开

### 3.1 草稿对象

首版每个项目／块只有一份共享人工草稿，段落可独立修改，但保存以整个块草稿修订作并发基线，不实现实时协作或自动合并。

必须保存：格式版本、位置、来源绑定、基线批准来源（无批准稿时显式为空）、上下文版本与朱批摘要、草稿修订、按原文顺序的段 ID／译文、操作者、请求身份。草稿可缺段或空段，但未知／重复／乱序 ID 拒绝；未开始、空草稿和存储错误三者区分。首次从批准稿复制与主动清空均需显式操作，不暗中用批准稿补齐用户清空的段。

保存只发布草稿，不改批准稿、定稿或导出；成功响应必须在可重启恢复后发出。旧修订保存拒绝并返回可比对的当前修订，客户端保留未保存文本，不自动覆盖或丢弃。viewer 不得保存。

### 3.2 生命周期

1. **保存草稿**：可反复进行；没有人工稿不等于没有批准稿。
2. **提交审阅**：冻结不可变提交，绑定草稿修订、完整候选字节、来源、基线批准来源、上下文与朱批；结构检查须通过。提交后继续编辑会产生新草稿，不修改旧提交。
3. **批准或驳回**：仅有写入权限的操作者显式决定，保存者与批准者可为同一人；这不是独立双人审校证明。批准时重新检查所有绑定、块级忙闲状态和受管写入恢复状态；并行模型任务或待决译稿存在则拒绝，不自动取消或覆盖。
4. **批准落盘**：候选作为完整块替换，复用受管写入／恢复协议与结构校验。基线批准来源被另一人工或模型批准替换，即使字节相同也拒绝旧提交；失败不能留下假批准。批准后草稿保留并标明它基于哪次提交，不自动删除。
5. **人工复核／定稿**：批准不等于定稿。人工来源绑定当前原译文、上下文、朱批和来源修订；材料变化显示失效。显式人工定稿不需要捏造模型双审，但必须明确未运行模型审校，并检查无活动任务、结构有效及所有绑定未变。

现行 AI 审校／修订条件不放宽；纯人工与 AI 来源统一供状态、导出及记忆资格读取，但来源必须可辨。有效人工定稿才可进入记忆；未批准草稿不可检索为正式参考。

### 3.3 记录与兼容决策

采用**新增人工提交／批准／定稿事实**，不伪造 EdictIssued、TaskCompleted 或 usage，不把人工修订编码成旧 TranslationKind。共用“当前批准来源”只需区分模型任务与人工批准身份，避免把 task 字段改成另一种含义。

- 人工提交保存不可变内容；批准事实记录提交身份、前一批准来源、候选摘要与全部绑定；定稿事实引用批准身份；驳回／退回保留原因和来源。具体事件数量在 N1a 按最小回放需求确定，不因本页措辞强制一动作一事件。
- 新版须照常读旧日志，保留旧编码与旧 task JSON 语义。新事件提高实际发行版本对应的最低读取版本；旧程序必须提示升级而非跳过。N0 不预占版本号或编码。
- 一旦目录写入新人工来源，不能让旧版仍把旧模型 writer 当当前批准来源；必须有旧版可识别的升级阻断。N1a 在真实旧二进制上验证，不能仅增加一个旧程序会忽略的 sidecar 标志。
- 草稿操作与批准写盘均持工作区写锁；成功请求的去重结果与发布状态必须可恢复。实现前验证现有恢复协议如何覆盖提交对象和新事件，不因“用了原子改名”声称整个流程可恢复。
- 开放人工批准前必须同时更新 governance、codec／readable_since、状态计算、finalize、导出、memory 与适用的 UI／CLI 事实展示。若闭环超过一个可验收小批，只允许独立保存草稿及不赋予批准资格的审阅快照，禁用批准／定稿；不得交付半条批准路径。N1a-2a 的快照与未来准入绑定明确分开，见第 9 节。

## 4. 人物、术语与范围

### 4.1 单一批准词表与人物引用

新上下文使用有版本的术语条目，包含稳定 term 身份、原文形式、类别、允许译法、备注、结构化范围、词证引用与确认状态。**不并建第二个正式词表**。人物对象仅记录稳定 person 身份、原名／读音、别名、称谓规则、口吻例证，并引用 term 身份及出处。

为兼容当前拒绝未知字段的旧词表解析器，人物／术语功能启用时明确引入新版上下文格式与最低写入版本保护；新解析器仍接受旧数组。旧条目 scope 保持说明文字，不自动解析成范围；人工确认后才生成结构化规则。旧快照原字节不变，不回填虚构 term ID 或人物关联；旧条目的编辑升级在新草稿中显式完成。

### 4.2 最小字段与不变量

| 对象 | 字段与约束 |
| --- | --- |
| Person | person_id、原名、可选读音、别名、term 引用、称谓规则、口吻说明／例句、证据；同名不同 ID 合法，别名不自动合并身份 |
| Term | term_id、原文形式、类别、非空 allowed、说明、scope、词证引用、判断状态；人物译名以此为权威，人物卡不复制 allowed |
| 称谓规则 | 被称呼人物、说话人（具体人物／叙述／明确未知）、位置范围、term 引用、说明与证据；未知不是任意说话人的通配符 |
| 证据 | 所属项目、来源段与原文摘要、短引、解释、暂定／确认；外部书目／URL 可引用但不自动抓取。项目事实、角色认知、叙述陈述分开标明，不自动晋升为作品真相 |
| 判断与批准 | tentative／confirmed 表达判断状态；批准上下文版本表达用户允许使用。已批准的暂定资料仍必须标暂定，不能变成硬性校对结论 |

人物身份初始不合并、不删除复用；误建项可停用，旧引用可追查。合并／拆分与自动别名推断不在首版；同名出现必须人工关联后才应用人物特定规则。

### 4.3 位置范围与信息可见性

范围与资料可见性是两回事：scope 回答“这条规则在哪里适用”，available_from 回答“最早何处可以把这条资料用于任务”。

- 位置按项目已确认章节顺序及原段顺序比较，不按文件名、段 ID 字典序或故事时间排序。区间左右端均包含；引用未知位置或起点晚于终点拒绝。
- 范围可取全项目或一个位置区间，并可附说话人／叙述条件；各条件取交集，不取并集。冲突规则同时列出待查，不以最后写入者静默胜出。
- available_from 为明确来源位置；暂定且无来源的笔记不能自动进入请求。未来人物的名称、关系、卡片标题、别名、术语和证据均须一并过滤，不能只隐藏正文字段。
- 首版为**块级模型请求**：可自动选取的资料 available_from 必须不晚于目标块首段，且 scope 与该块存在适用交集。块中段才揭示的资料仍不自动用于整个块，可留给人工查看或显式回修选择；不能声称已在单一提示里实现段间保密。
- 未来资料显式选择只限本次回修，请求预览必须显示泄露风险、完整外发文本、范围与快照；不授予工具权限、不永久放宽筛选。
- 此规则是最小化提示材料，不保证模型不知道剧情或不会自行推断。现有不带范围的全局 style／摘要仍可能包含后文，不能据新增过滤声称旧项目已防剧透；启用严格筛选前须人工检查／升级全部外发上下文，并以实际请求捕获验收。

## 5. 问题报告与版本

报告是可重建派生材料，不是批准依据。必须绑定项目来源、所检查的批准译文身份／摘要、规则快照与扫描范围。每项包含问题身份、类别、当前与参考位置、证据、触发规则、解释及“字面候选／人工确认”的性质。

处理分成 disposition（接受／驳回／待查／不适用）与 resolution（未查／解决／未解决／不适用）；复用现有勘校语义，不把“接受建议”算“问题解决”。合理差异需要理由，且只在绑定版本及位置有效。材料变化令报告或对应处理需复核，不改历史记录；首版可保守整批失效，不承诺最小失效范围。报告缺失、过期、扫描失败与无候选分别显示，不用无候选证明全文一致。

## 6. 自创验收材料与检查层次

[N0 自创样本](fixtures/novel-workbench-n0.json)包含日文三章、自创中文对照、人物／术语与反例。材料由本次 AI 辅助编写，可作为仓库测试夹具使用；不是既有文学作品，也不是双语专家审定的译文，不声称文学水准。位置与 revision 使用样本符号；不是生产文件格式，不把符号当 SHA-256。

- N0 现在检查 JSON 可解析、ID／引用／范围顺序与样本覆盖，及文档本地链接；**没有执行未来产品行为**。
- N1a 起将人工稿场景接公开应用层接口，独立从样本计算真实来源摘要；保存后重启核对实际内容。N2 验证规则适用与外发捕获；N3 验证报告和复核，不新增依赖私有函数或调用顺序的断言。
- 每个场景的预期由本样本预先登记，运行时不得从待测实现反推答案；negative control 明确区分“合理异译”和“同范围错译”。新增行为须有在错误实现下失败的回归。
- 新格式损坏、未来版本、旧二进制拒绝与旧项目不变是必验兼容门槛。实际事件编码、持久化上限及恢复故障注入点在 N1a 开始前登记，不宣称 N0 已证明可恢复或原生通过。

## 7. N0 结项与下一批边界

本设计确定人工来源单独记账、词表单一权威、范围与可见性分离、块级信息过滤及人工问题处理规则。样本不是已通过的功能测试。下一小批建议 **N1a-1：仅人工草稿保存、冲突、重启恢复与去重**；不接模型、不开放提交批准、不改 `zh.json`、定稿、记忆或导出资格。随后 N1a-2 再实现完整人工审批来源闭环；只有兼容与恢复证据齐备才能开放。

## 8. N1a-1 应用层实现与验收边界

本批新增 `Translations::human_draft` 与 `save_human_draft`，供可信本地应用调用；**尚无 CLI 命令、Web API 或人工编辑界面**，不存在新增 viewer 写入入口。未来入口须在调用前鉴权，本地库接口不伪装成多用户权限系统，也暂不记录未经验证的操作者姓名。

- 草稿存 `.ziyuan/text-projects/<项目>/human-drafts/<块>.json`，`JsonFile` 信封格式 v1、文件上限 8 MiB。正文累计至多 256 KiB UTF-8 字节；允许缺段、空段、显式清空，不从现有译稿暗中补段；拒绝未知／重复／乱序 ID。文件与锁以及所经控制目录检查普通文件／目录，拒绝静态符号链接；不承诺抵御并发恶意换链。
- 读取返回当前 basis 和保存时 basis／正文／随机修订身份。basis 含项目与块来源摘要、上下文版本、朱批摘要和磁盘译稿摘要；**磁盘摘要不是批准身份**，人工来源身份及相同字节重新批准的区分仍留待 N1a-2。旧草稿在上下文变化后仍可读取；新保存须显式核对现行 basis。
- 每次新保存发布完整块草稿，要求 expected_revision 与现行随机身份相符；首次须为空。正文与请求摘要、回执同一次 JSON 替换发布。持工作区写锁，拒绝未收尾的受管写入；不推进批准用的 generation，不写事件，不改 `zh.json`。
- 去重范围为项目／块内的 request_id；ID 为 1–128 位 ASCII 字母数字、`-`、`_`。请求摘要覆盖目标、basis、expected_revision 和全部段落。旧同请求重试先于新请求基线检查，返回原修订／内容摘要回执，不覆盖后来正文；同身份改内容返回专门冲突。回执与正文共同受 8 MiB 文件上限约束，不自动淘汰，超限拒绝新保存但保留上次正文、读取与已有回执重试；本批不提供轮换或删除功能，禁止手删内部文件来“清理回执”。
- `DraftConflict` 含现行修订，`DraftRequestConflict` 与 `DraftBasisChanged` 分别表示身份复用和材料变化。损坏、新格式、超限或 I/O 错误沿用可识别存储错误，不重置空稿。现行正文与回执摘要核验可发现未记录的直接手改，不提供防篡改签名保证。
- 恢复含义限定为：正常进程重开或成功响应丢失后，从单份已发布文件恢复正文及回执；不建立多文件批准事务。底层沿用 `JsonFile` 临时文件刷盘、替换与目录尽力刷盘行为；不声称断电安全、强杀故障注入或所有文件系统可用。上下文等现有独立写入仍有各自锁，basis 在保存前及发布前重查，不宣称跨所有旧接口的多文件快照事务。

### 9.2 已实现的审阅快照与格式升级

`submit_human_draft(project, block, DraftSubmit)` 只接受 request_id 和 expected_revision；全文取自该修订的已保存草稿，不接受旁带正文。`HumanSubmission` 冻结 request_id、完整 HumanDraft 与候选字节摘要；`candidate()` 按原有 PromptBlock v1 编码生成完整候选，不复制原文 ruby 等源文注记。复用 `TextProjects::check`，缺段／空白／未知／重复／乱序不能成为提交。

提交身份为项目＋块＋submit＋request_id，与 save 的请求空间分开。同请求及同修订返回原快照；同 ID 换修订返回 DraftRequestConflict。历史重试优先于新修订／basis 检查，不覆写新稿；新的提交须匹配现行草稿修订及当前 basis，发布前重查 basis。没有草稿报错，读取历史快照不会因为材料过期而丢弃它，也不把它标为当前批准版本。列表按请求 ID 排序，不表示时间顺序。

草稿簿信封写为 **v2**，同文件保存现行稿、保存回执与全部提交快照。新版可读 v1（缺省空提交集合），只读／成功旧请求重试不升级文件；首次实际保存或提交才写 v2。v1 读写器须报 Newer 并且保留原文件；未知字段、未来版本、损坏快照／摘要不能静默丢弃或重置。旧日志、译稿和工程未改变；旧程序仍可用旧 AI 功能，并不意味着它理解人工快照。**这仅是草稿文件旧版阻断，不是未来批准事件的全工作区阻断。**

正文仍限 256 KiB，整簿仍限 8 MiB（含快照与回执），不自动清理。超限失败须保留现行稿／历史快照与可重试回执。持工作区锁并拒绝未收尾写入；发布仍只有一次 JsonFile 替换，不推进 generation、不写 court.log／zh.json。沿用第 8 节的文件系统、非恶意并发与非断电保证边界。

**本批快照不绑定“当前批准来源”事件身份，也不记录审批主体，因此不能直接批准。** 后续必须显式准入：重新展示候选与现行材料，核对完整 basis，捕获当时的批准来源身份，再以新的请求冻结审批绑定。不得静默迁移现存 v2 快照为可批准提交；人工修改草稿不会改动旧快照。

### 9.3 审批事件与旧版阻断（待实现）

| 事实 | 最小内容与回放规则 |
| --- | --- |
| HumanSubmissionBound | 明确的准入请求身份／摘要、项目块、快照身份、草稿修订、候选字节与摘要、完整 basis、前一批准来源及经鉴权操作来源；本地快照缺失仍能从权威记录核对批准候选。首次无批准来源显式为空 |

### 9.4 恢复 v2（待实现）

v1 保持读取／恢复能力，不改原格式含义。v2 的 application 为明确 tagged union：model 保留真实 task／changes_version／skipped；human 记录批准操作身份、绑定提交／请求摘要、当前材料及前一批准来源。human 分支只允许对应的批准事件（至多一个前置 Clock），不得夹带模型 ChangesApplied、第二个批准或其他事件；事件、来源、路径、候选字节及前后摘要交叉核对。恢复记录自身的校验与 8 MiB 上限继续适用；超限在任何正文写入前失败。

复用并改造现有事务所有者，不另写人工批准专用的直接落盘器。持工作区锁，预检并固定日志条数／字节数／前缀摘要、完整编码事件批、目标前后状态、候选字节和 generation；准备／发布恢复记录及奇数世代后才写正文，正文就位后追加精确事件批，验证并完成记录、推进偶数世代。失败保留可核验记录，绝不在不确定时自动回滚或盲目重放。

| 中断后的可观测状态 | 允许的恢复决定 |
| --- | --- |
| 正文仍为 before，日志未追加 | 验证输入与来源仍一致后显式继续；或放弃且不发批准事实 |
| 正文全为 after，日志未追加 | 核对日志前缀／候选／来源后仅补精确事件，不再次覆盖正文 |
| 正文为 after，日志已有完全一致的事件批 | 只补收尾；不得重复批准事件或制造另一批准身份 |
| 相同 before/after 字节 | 不能靠文件相等判断批准完成，必须查操作身份与精确事件批 |
| before/after 混合、第三种字节、日志分叉或不匹配事件 | 显示具体不确定证据并阻断；不自动选一边、不抹掉恢复记录 |
| 已完成／放弃但 generation 未收尾 | 对照记录终态与日志／文件再补偶数世代；不能只删标志 |

下一批故障注入需覆盖：发布前、发布后正文前、正文后事件前、事件后收尾前及偶数世代前；每点重启核对真实文件、事件次数、来源身份、重复请求结果和导出／memory 资格。文档中的恢复表不是已经实现或通过的测试。

## 10. 需求补充：能处理注音、着重号的 OmegaT 式工作台

用户明确目标不是纯文本 CAT 加一个注音预览，而是文学标记在**导入 → 对照／编辑 → 保存／冲突／恢复 → 审批 → 导出**中均有明确语义。人物／术语和跨章一致性仍在范围内；本节优先补齐格式契约，不因新需求宣称现有实现已经满足。

### 10.1 当前事实与缺口

- `text_project/document.rs::Inline` 已有 Text、Ruby（基字、读音、源文件字节位置）和 Emphasis。受限 ruby、`《《强调》》` 及 Markdown 的强调已有解析；普通括号不自动视为注音，复杂／破损标记保留字面与警告。不是完整青空／HTML／EPUB 解析器。
- Web `sourceInlineHtml` 能安全显示 ruby，但 Emphasis 统一渲染为 `<em>`，不是语义独立的着重号编辑器。现行模型把粗体／斜体与日文强调折叠为同类，不能还原它们的全部区别，更不含着重点形状、位置或书写方向信息。
- `translation/finished.rs::translated_text` 可从一致的译文 inlines 输出受限 ruby；Emphasis 目前与 Text 一样输出正文，着重语义会丢失。不能把“源文可显示注音”说成“译文编辑／导出已完整保留文学排版”。
- N1a-1／2a 的 DraftParagraph 只有 id／text，未知字段拒绝；快照候选明确不自动复制源文 inlines。当前 API 只覆盖纯文本，不接收结构化译文标记，更不应从含标记的译文降级复制为纯文本后冒充无损编辑。正式接入工作台前必须升级译文契约。

### 10.2 N1a-R 的最小契约（待实现）

1. **译文专用结构**：正文与行内标记有单一权威表示，平文从结构派生或严格核对；源文 byte_start/end 只作原文出处，不能复制为译文偏移。普通字串不重解释为标签；显示不执行任意 HTML。
2. **注音**：基字与读音成对，可选中修改各自内容。保留作者借读音表达另一层意思的可能，不把 ruby 一律当字典发音或术语别名；不能在翻译后自动沿用日文读音。空基字／读音、失配、非法边界在提交时明确拒绝，草稿中的未完成输入必须可恢复且不能冒充可批准候选。
3. **着重独立于粗斜体**：至少区分着重、strong、emphasis；着重的形状／位置等先列明实际支持子集。unsupported 的样式或嵌套可明确拒绝／告警，不能静默改成斜体或普通字。允许的嵌套、同字注音加着重与跨段边界需在开发前固定正反样本，不能假定树模型已覆盖任意交叉范围。
4. **译者主导迁移**：源文标记是参考，不是译文固定坐标；允许人工保留、改写、移动、明确删除。对未处理标记提供提示与逐项确认，不要求源译标签数量机械相等，也不自动把源文范围套到改写后的译文。
5. **全生命周期绑定**：只改读音或着重、正文不变，也必须改变内容摘要、修订、提交与复核绑定，并参与去重和乐观冲突。结构上限同时约束正文、读音、节点数／深度与序列化总量；富标记文件升级后旧读写器拒绝，不忽略新字段。
6. **编辑与辅助**：双语段旁可视预览及可检查标记视图共用同一内容；键盘可选中和编辑基字／读音／着重，支持撤销／重做，下一未译、搜索和术语插入不破坏节点。检索与字数统计区分基字正文和读音，不能把读音又当正文重复匹配。界面批次必须实际验证组合输入、选择边界和复制粘贴。
7. **格式矩阵与导出门槛**：先明确 TXT（具体扩展语法）／Markdown+受限 HTML 各自可表达的标记；标准纯 TXT 无法无损表达样式时显式报告或经用户选择有损导出，不能把丢失说成成功保留。支持格式的往返须保住正文、配对、语义与原章序；未知源标记保留并标出，不能悄悄删除。EPUB／DOCX 的格式适配仍按真实需求另批，不承诺所有站点／格式兼容。

### 10.3 排期与验收

当前 N1a-2a 纯文本快照作为独立基础先验收；在开放人工批准前插入 **N1a-R**：先冻结上述行内模型／格式能力与样本，再小批实现持久化及结构校验。随后恢复／批准事务绑定结构化候选的真实字节，N1b 实现双语标记编辑和导出闭环。不先做一个会丢标记的编辑器，再把注音当装饰补上。

N0 样本追加 `phase=N1a-R` 的格式案例：多字基字、读音与字面含义不同、同字注音与着重、仅标记改动的并发冲突、改译后不自动套用源文位置、未知样式／破损标记、导出能力不足时的显式处理、重启往返。它们是待实现的验收预期，不是当前已通过测试；保留原有三章人物、术语及跨章反例。

## 11. N1a-R1：译文范围标记与草稿持久化

进入条件：N1a-2a 提交 `4908e9b6247b10c12ea2875ae27b09161234800d` 的[六项 CI](https://github.com/YuuUehara/Ziyuan/actions/runs/41380050862)全部成功，包括 Windows／macOS／Linux 原生检查。本节先固定 R1 最小契约，再实现和验收；不把这一小批当作整个文学标记工作台。

### 11.1 数据契约

- 沿用 DraftParagraph 的 id／text，增加默认空且为空时不序列化的 marks。**text 是唯一的基字正文**；每项 TargetMark 含 start、end、kind。范围为当前译文 UTF-8 字节半开区间，不是源文 byte_start/end、Unicode 码点索引或 DOM 偏移。必须非空、在正文内，且两端均为扩展字素边界，不能切开组合字或 emoji 序列；标记不能跨换行或段落。
- kind 是以 type 判别的 JSON 对象：ruby 带 reading（纯文本），emphasis_dots 是圆点着重，strong 是粗体，emphasis 是斜体。例：kind 为 `{"type":"ruby","reading":"ねがい"}` 或 `{"type":"emphasis_dots"}`；四种对象均拒绝未知字段。后续显示位置随版式确定；本批无方向、形状、颜色等样式选项，不隐含支持竖排。原文 Inline 类型不改义、不添加假的源文件偏移。完整实例见 [N0 JSON 的 target_markup_examples](fixtures/novel-workbench-n0.json)。
- 多字 ruby 只有一个范围与一份读音，基字由 text[start..end] 派生，不重复保存。读音是作者／译者提供的另一层文本，不自动改成字典发音、不成为人物或术语别名。草稿 reading 可空或空白，以便恢复未完成编辑；读音不能含换行。标记 JSON 不是 HTML，不执行其中的文本。
- 同一范围可叠加不同种类（如 ruby＋圆点着重）；同种类重复拒绝，即使读音不同也不能为同一基字叠两个 ruby。其余范围必须不相交：当前明确拒绝严格嵌套、部分交叉，而不是把它们压成普通字。相邻范围可用；输入顺序不影响有效性，保存保留输入顺序，不擅自规范化用户正文。
- 全块正文＋全部 ruby 读音合计最多 256 KiB UTF-8 字节；全块最多 4096 项标记；整簿仍限 8 MiB。扁平范围模型不接受子节点或任意 HTML，不需要通过放宽 JSON 深度支持嵌套。
- 所有 marks 参与保存请求摘要、草稿内容摘要与修订冲突。只改读音、着重种类或位置也不能沿用旧修订。改正文但不调整标记，仅在新范围仍有效时可保存；不能推断它仍指同一词，也不能从旧源文偏移自动纠正它。未来 UI 必须提供显式范围调整，本批没有自动迁移。

## 12. N1a-R2：无损送审候选与格式诊断

### 12.1 编码与校验

- `HumanSubmission::candidate()` 返回独立的 `ReviewCandidate`。无标记时仍是 PromptBlock v1 的原样字段顺序、缩进与结尾换行，历史候选摘要不变；有任意标记时采用候选 schema v2：schema_version、block_id、paragraphs，段中保留 id、text、marks。版本由冻结稿是否含标记确定，不增加另一份权威正文，不复制源文 inlines。
- v2 不是旧模型候选协议的扩展许可：旧 `TextProjects::check` 必须继续拒绝 v2。送审时先校验完整标记（沿用 R1 范围、字素、重叠和容量限制），ruby 读音 trim 后不得为空，但不改写原读音；再用临时纯文本投影复用现有段 ID／顺序／完整性／非空校验。该投影只用于结构检查，不保存、不取代 v2 候选，也不作为候选摘要。
- 实际候选 JSON 的精确字节（含标记顺序与最终换行）参与 candidate_hash；只改读音／着重就改变摘要。新请求仍绑定现行修订与 basis，历史提交重试仍返回原冻结稿，不能因后续改稿或上下文变化重算旧提交。
- 草稿簿新发布升级为 v4，读取 v1／v2／v3 和历史请求重试不升级；支持至 v3 的旧读写器必须拒绝 v4。候选 schema 与草稿簿版本是两种不同协议，不能混用。未知候选版本／字段、损坏候选摘要拒绝；失败保留原文件。

### 12.2 能力矩阵的含义

`ReviewCandidate::check_format` 是只读的**表示能力诊断**，不是导出操作或批准资格。范围限定为下面三个具体表示，不把旧导出的 ruby 扩展 TXT、Markdown、HTML、EPUB／DOCX 报成已支持的新目标格式；这些适配另批实现并做往返验收。

| 表示 | 无标记 | ruby／圆点着重／strong／emphasis |
| --- | --- | --- |
| review_json | v1，候选精确字节可保存和恢复 | v2，全部保留，包含同范围叠加 |
| legacy_prompt_json | 可表示，保留原 v1 字节 | 不可无损表示；逐项列段 ID 与原 marks 索引，不转换或删除 |
| plain_text（无扩展的纯 TXT） | 可表示正文／段落 | 不可无损表示；同上，不把 ruby 字面语法或斜体当替代 |

无效范围、未完成读音和未知版本不能获得“无损”结果。诊断只评价文学标记表示能力，不承诺纯 TXT 保留工程 ID、哈希或往返工程身份，也不暗示生成了任何导出文件。不存在自动有损选项。

## 13. N1a-2b-1：显式写入协议升级闸门

### 13.1 本批范围与顺序

恢复 v1 的 application 仍强制真实模型任务；恢复 v2 的人工来源需要新审批事件及完整来源核对，不能先塞 task=0 或把带标记候选写成旧译稿。本批先准备既有 `.ziyuan/write-protocol` 的显式升版与兼容门控，不修改恢复记录、事件、工程格式或批准资格。新 API 暂无生产调用点，不增加 CLI／Web 升版命令，也不在普通锁／草稿保存／送审时自动开启。

- `Workspace::write_protocol()` 只读，缺失标记返回 None、按旧 v1 能力处理，不创建目录或文件。识别规范字节 `1\n`／`2\n`；不规范的已知版本、未知未来版本、非普通文件／重解析路径均明确拒绝，不修复或重置标记。
- 普通 `lock` 仍只在缺失时创建 `1\n`；已有 v1／v2 不改写。`ensure_writable` 也核验协议，不能在不取锁的预检中将未来或损坏版本报为可写；写入者仍必须持锁，预检不取代排他。

### 13.2 闸门不是全部旧入口阻断证明

## 15. N1a-2b-3：准奏来源与恢复契约细化

### 15.1 本批交付与代码所有权

本批仅细化契约及设计样本，**不实现或开放人工准奏、恢复第二版、事件／会典新格式，也不新增页面或命令**。第 9 节已有方向，但尚未确定来源身份、权威候选所在及恢复批次的分工；先解决这些约束，避免只加 human 标签后仍无法核验批准事实。

- `ziyuan-core` 定义事件携带的来源事实；`ziyuan-governance` 核对来源引用、请求身份和状态迁移。二者不能反向依赖 app。现有 `ReferenceBinding` 已采用应用载荷由 app 解释的边界；人工绑定沿用此分层，不另写一份文学标记模型。
- `translation/draft.rs`／`markup.rs` 继续拥有候选精确字节与文学标记校验。app 在准入、恢复和消费已准稿时解析同一冻结载荷；无法理解候选格式即拒绝，不能只凭批准事件名显示有效正文。
- storage 负责恢复信封、来源分支、编码事件批和路径／摘要的自洽；不把编解码成功当成候选有效、用户已鉴权或基线仍为当前。现有 `edicts.rs` 仍是受管事务所有者，后续扩展它，不另造人工直接写盘器。
- CLI 恢复展示现按 `application.task` 打印任务号；只有上述契约落地后才能显示“模型诏令来源／人工准奏来源”，不能为人工分支填任务零号或伪装成模型任务。网页与文档亦同义，技术版本号不成为产品名称。

### 15.2 身份不能混用

| 身份 | 固定语义 |
| --- | --- |
| 送审快照 | 项目＋块＋既有 submit 请求 ID，引用不可变修订与候选；仍不是可准奏凭据 |
| 事件引用 | 同一工作区事件簿中的从零起事件索引＋该事件的规范编码行 SHA-256（不含行尾换行）；摘要为 64 位小写十六进制。不能与“已有事件条数”混算，也不能只按相同正文寻找一行 |
| 当前准奏来源 | 显式为空，或带 model／human 判别的来源及其事件引用；模型保留真实 task／changes_version，人工引用对应准奏操作。上下文／草稿修订或候选摘要不能代替来源身份 |
| 人工准奏操作 | 沿用受管事务的 32 位小写十六进制 operation_id，同时作为批准身份，不再造另一个含义相同的 ID。恢复、事件与请求回执必须引用同一身份 |
| 客户端请求 | 绑定与准奏各有独立操作域，范围均为项目＋块＋请求 ID；沿用现有 1–128 位 ASCII 字母数字、短横线或下划线规则。服务端计算请求摘要，不接受客户端自报摘要作为证明 |

请求摘要必须采用带操作域、表示版本及固定字段顺序的编码。绑定请求覆盖项目／块、鉴权得出的操作来源、原送审快照身份／修订、候选摘要、完整 basis 和预期前一准奏来源；准奏请求改为引用已存在的绑定事件及其冻结事实，不能让绑定请求摘要反过来引用尚未产生的自身事件。未知字段拒绝，不能靠任意 JSON 对象的键顺序判同；具体编码在实现批固定字节样本，本批不冒充已有编解码器。

鉴权先于回执读取：本地只记“本地操作者”，网页只记鉴权所确认的写入来源，不假定现有共享令牌能证明个人实名，令牌本身绝不入簿。同一有效请求返回原操作身份；同 ID 异内容／异操作来源拒绝。新请求即使候选字节相同，也须重新核对当前来源，不能绕过“甲→乙→甲”式基线变化。

### 15.3 一份权威候选，两种事件职责

1. **准入绑定**：现有送审快照须经显式再核对，才能发布 `HumanSubmissionBound`。绑定事件保存绑定请求 ID／摘要、完整候选精确字节、候选摘要、完整 basis、原快照身份／修订、预期前一准奏来源和经鉴权操作来源；候选沿用 `ReviewCandidate::serialized()`，包含结尾换行及原标记顺序。只改读音或着重也必须改变摘要，不按源文偏移重建译文标记。
2. **先入簿，后准奏**：绑定事件须已在准奏事务的前缀中，不能与批准事件临时拼成一个不可恢复的首发批次。绑定本身不改正文、当前准奏来源、定稿或记忆资格；只有绑定而未批准的历史仍只是待决材料。
3. **准奏事实**：`HumanTranslationApproved` 引用绑定事件、operation_id、准奏请求摘要、前一来源、唯一目标及前后字节摘要。它不再复制一套可独立编辑的候选。仅此事件更新当前准奏来源；驳回、送审和保存不能代替它。
4. **重启依据**：本地草稿簿／原快照丢失时，已入簿绑定仍提供完整候选与标记，允许核对或恢复；绑定事件自身缺失、摘要不符或候选未知时阻断，不回退到现行草稿或平文猜测。日志及工作区仍是可信本地材料，摘要不是签名或鉴权替代品。
5. **分离存储与门控**：空目标列表可以表示前后字节本就相同，但不代表准奏已发生；仍需唯一匹配的批准事件。富标记正文最终落盘表示及其状态／定稿／导出／记忆消费者须同批适配后才开放，不把当前 review_json 诊断当正式输出已兼容。

### 15.4 恢复来源与决策表

恢复第一版继续按原含义读取和收尾，编码输出与旧协议一致，读取不自动重写；不能给旧记录悄悄补 kind 或换格式。第二版使用明确 model／human 判别：model 保留真实任务来源；human 保存绑定事件引用、准奏 operation_id、准奏请求摘要、预期前一来源及候选摘要，以绑定事件取得完整材料。缺标签、未知标签、串入另一分支字段均拒绝，不能尝试退回第一版解读。

human 的待追加批次只能是可选的一条前置 Clock 与唯一对应的 `HumanTranslationApproved`；禁止夹带 `HumanSubmissionBound`、模型 `ChangesApplied`、重复批准、定稿或其他事件。Clock 在发布记录前一次取定，跨分钟也不能重新计算。事件簿前缀仍固定条数、实际字节数与字节摘要；来源中的规范单行摘要与原始前缀字节摘要是不同口径，不可互换。

| 可核验证据 | 允许决定 |
| --- | --- |
| 绑定位于固定前缀内且完全有效；目标仍为 before，日志无新批次 | 核对当前材料／前一来源／写权后，显式继续或放弃；放弃不发批准事实 |
| 目标全为 after，日志无新批次 | 同样核对绑定与前缀，仅补记录固定的精确事件批，不重写候选 |
| 目标为 after，指定位置已有完全相同批次及同一 operation_id | 只补收尾，不重新核对会被本操作替换的旧基线，不再发批准事件 |
| before 与 after 相同，日志无批准事件 | 仍未批准；不能靠目标文件相等跳过批准或误报完成 |
| 部分事件批、不同操作的同文事件、日志分叉／第三种目标字节 | 列明不确定证据并阻断；不自动补尾、选边或回滚 |
| 草稿簿缺失，但绑定及前缀完整 | 使用绑定的冻结候选，不改用后来的草稿；不能把缺草稿误当空译文 |

恢复时不把本操作已知的 after 状态与 basis 中旧 translation_hash 直接比较并误报外部改稿：盘上译文须对照记录的 before／after 及冻结候选摘要，其余原文、上下文、朱批仍核对材料绑定。当前准奏来源由固定前缀与指定位置的精确事件批重放取得，不根据文件字节推断。

超限须检查真实候选、绑定的实际事件编码及最终恢复信封，不按“正文长度”估算转义后的规模；沿用恢复信封 8 MiB 上限。容量／编码及可预检的路径／权限错误在正文写入前拒绝；落盘时仍可能发生 I/O 失败，记录已发布则保留可核验现场，不能以删记录掩盖失败。

### 15.5 后续实现顺序与验收门槛

## 16. 来源与送审绑定事件：内部实现小批

第 15 节保留前一设计批的记录，实际进展以本节为准。本批只落地来源事实类型、完整候选的待决绑定、事件编解码与回放；**没有绑定发布命令／网页接口，没有人工批准事件、准奏事务、恢复第二版或正式富标记输出**。

### 16.1 已固定的数据与字节

- `ziyuan-core::DraftBasis` 是原 app 类型的唯一所有者，app 保留同名导出；字段及旧草稿 JSON 不变。`TranslationSource` 必须显式带 `kind`：`none`、`model` 或 `human`，缺失、未知及串分支字段拒绝。模型保留真实任务号与改动版本，人工保留准奏操作身份；两者均带从零起事件索引和规范事件行的 SHA-256。
- `HumanBindingRequest` 按声明顺序固定为 project、block、request_id、actor、submission_id、revision、basis、candidate、candidate_hash、previous。actor 仅为本地／网页入口来源，不是个人实名或鉴权结果的替代品。candidate 是 `ReviewCandidate::serialized()` 的完整 UTF-8 字节（含末尾换行），保留标记顺序，不从正文或源文偏移重建。
- 请求摘要固定为 SHA-256（紧凑 JSON 数组 `["ziyuan/human-submission-bind",1,request]` 的 UTF-8），覆盖声明顺序的全部字段，含候选原字节与摘要；无自引用事件身份。固定样本摘要为 `3864b2134d8fceebb737f2604a9c23f918d226a6dbec9016cfe4a6c7f135fc50`，输入见 governance 测试及 `compat.tsv`。只改读音、材料版本、操作来源或前一来源都会改变请求摘要。
- `HumanSubmissionBound` 编码为 `v1`、`HUMANBOUND`、绑定对象紧凑 JSON 的 UTF-8 hex，三个 Tab 分隔字段，不含行尾换行；外层和各结构拒绝未知字段。既有模型事件编码和恢复第一版未改。

### 16.2 回放与应用层边界

治理核对项目／块／请求／修订格式、各摘要格式、候选与请求摘要自洽，并按项目＋块＋绑定请求 ID 保存一份待决回执。重复事件即使同文亦拒绝；重启后可查原回执，不能重发。不同块的同请求 ID 不互相占用。容量按 JSON 转义后再 hex 的实际事件行检查，最多 8 MiB，不按中文字数或正文长度估算。

**来源类型和摘要自洽不等于来源已经核验**：本批不解析所引事件是否真实存在、是否为相应项目的批准、是否仍为当前来源；也不进行鉴权、项目归属／段落完整性与当前材料核对。这些必须由后续持锁准入与恢复调用者完成。治理可保留不理解的候选载荷，app 必须拒绝不理解的语义。待决绑定绝不更新现行批准来源、译稿文件、御览定稿或记忆资格，也不伪造任务和用量。

## 17. 来源解析与持锁准入核对

本批接通真实模型准奏来源的解析与本地持锁核对，**只返回一个待决绑定事件，或已有同请求回执；不追加事件、不写译稿、不开放命令／网页接口或人工准奏**。生产发布的日志前缀 CAS、重新核对、恢复双格式和人工批准事件仍未实现，不可在丢锁或日志变化后直接发布此前返回的事件。

### 17.1 来源以准奏事件顺序为准

`resolve_translation_source` 逐条回放实际历史，以最后一次本块有效 `ChangesApplied` 为来源，不按任务号最大值、定稿或候选同文猜测。模型来源携带真实任务、该时点完整改动的既有 `changes_version`、从零起的准奏事件位置及规范行摘要；译稿摘要按逐段取舍后的实际结果计算。仅补建议的修订保留前稿摘要，但产生新的批准身份；非本块译书准奏改写目标、无可核验译稿的初译或无前稿的空修订拒绝。不改旧状态页的 writer 选择规则。

### 17.2 持锁核对的条件与重试

`Translations::admit_human_binding` 使用调用者仍持有的工作区写锁，并核对 canonical 根目录一致、偶数代次、无任何恢复记录、工作区写入协议第二版及项目清单第三版；不自动换版。它从该锁对应的真实事件簿重读，不能用别的 Session 缓存或另一工作区的日志冒充。

本地入口先拒绝网页操作来源，核对项目、块和候选表示，再查已入簿回执。同作用域请求与冻结绑定完全相同，返回无新事件，允许材料已变化或原草稿簿已丢失；同请求异内容拒绝。只有新请求才继续从草稿簿核对真实送审快照、修订、完整候选、段落归属与顺序／完整性、现行 basis、现行批准来源及盘上译稿摘要。请求摘要自洽不能放行虚构的提交或事件引用。

这仍是受信任本地 Rust API，不是用户鉴权系统，也不是跨进程持久凭据。真实发布必须继续持锁、使用核对时的日志前缀并在冲突后重新核对；外部手改文件、旧进程及绕过受管接口的底层写入不在排他保证内。换版前停旧进程的要求不变。

### 19.3 会典门槛的反向对照

伪改仅是故障注入，**不是允许的换版操作，也不是对文件篡改的安全承诺**；这些副本已清理。现行会典 tag 与旧版隔离必须保留，不可因包版本相同而退回旧 tag。另发现 `migrate` 的 `huidian.current` 仍只比较包版本式 tag，会把实际可采用的新会典报告为非现行；已单列独立修复建议，本批不改该字段，也不以它为缓存是否实际生效的证据。

### 19.4 阻断边界与交付状态

**不宣称所有旧读写入口均封闭。** 发布版的项目查看与朱批写入被第三版清单拒绝且不改盘；前绑定内部版已经支持第三版清单，它的项目查看仍成功，独立朱批写入也确实成功并改变材料，而事件簿不变。其独立材料通路不重读事件簿，不能由新事件门槛撤销；这与旧进程缓存、手改文件一样，仍要求换版前停止旧程序及在途写入。

本批确认的是**重新打开事件簿时的兼容性拒绝及会典隔离**，不是自动停写确认或操作系统访问控制。尚无自动停旧进程／停写确认闭环，不能据此开放人工准奏。没有修改 Rust、CLI／网页文案或布局、版本头、恢复格式及 N0 的 57 项设计样本，也未发版。本次真实旧二进制验收仅在 Linux 执行，不能以第 18 节的跨平台 CI 代替本次 macOS／Windows 混用旧二进制实测。

## 20. 恢复双格式与中断样本细化

**本节是设计，不是已实现能力。** 当前 `RECOVERY_FORMAT` 仍为 1，尚无 `HumanTranslationApproved` 编码、人工恢复或准奏入口。本批只补文档和验收输入，不改恢复文件、代次、事件、CLI／网页文案或布局。机器字段保留协议原名；面向译者使用“恢复格式第一版／第二版”“模型诏令来源／人工准奏来源”，不用研发批号命名页面，不扩建恢复工作流框架。

### 20.1 第一版实际含义与双格式分派

核对入口为 `ziyuan-storage/src/recovery.rs`、`workspace.rs`、`ziyuan-app/src/edicts.rs::{recovery_record,write_transaction}` 及 `ziyuan-cli/src/text_commands.rs::{run_recovery,finish_recovery,events_present}`；真实旧 CLI 回归在 `ziyuan-cli/tests/recovery_commands.rs`。

| 边界 | 固定契约 |
| --- | --- |
| 分派与拒绝 | 先检查完整信封大小及明确的格式号，再选对应结构；第一版无 `application.kind`，第二版必须显式 `model` 或 `human`。零版、缺字段、未知来源／字段、分支字段混用均拒绝；未来格式要求更新读本。不用尝试反序列化成功的先后顺序猜来源，也不把坏的第二版回退成第一版 |
| 第一版保存 | 保留既有字段、固定紧凑序列化与校验和规则；读取不写盘，不注入来源标签、不自动升版。已有允许的 JSON 空白／字段换序读取不变，不承诺原始排版经显式状态更新仍逐字节不变。状态更新仍写第一版，模型新事务默认继续写第一版 |
| 第二版模型来源 | `kind: model` 加真实 `task`、`changes_version`、`skipped`，禁止人工字段；模型事件仍为可选一个前置 `Clock` 加恰好一个匹配的 `ChangesApplied`。沿用模型收尾判据，不用新增人工规则悄悄改变第一版行为。显式读取的第二版记录在状态更新后仍为第二版 |
| 两种版本域 | 恢复记录的模型 `application.changes_version` 目前是协议字面量 `"v1"`；批准来源 `TranslationSource::Model.changes_version` 是提案的 `sha256:…` 摘要。两者不可互换，不能为文案统一改写旧字节 |
| 共同限制 | 保留绝对工作区、32 位小写十六进制 operation_id、偶数前代次及后代次加二的检查，拒绝溢出和任意路径；最终完整信封按 UTF-8 实际字节计不超过 8 MiB，不能只量正文或转义前字符数。第二版也校验固定序列化的类型化记录摘要；其准确字段次序及事件编码须在实现批以独立定本固定 |

第一版 `finish` 只收尾，不改正文或追加业务事件；其日志匹配返回布尔值，现有模型收尾也不要求该值一定为真。第一版行为保留，但**不能直接复用为人工已准奏的证明**。第二版模型分支同样不产生人工批准，不以支持双格式为由默认换写全部模型事务。

### 20.2 人工来源与三种摘要

第二版人工分支的来源事实包括：`kind: human`，项目／块、准奏请求身份及操作者、准奏请求摘要、绑定事件引用及其请求摘要、冻结候选摘要、前任批准来源，以及逻辑输出的格式身份、路径、before／after 状态。准奏 operation_id 以记录顶层为唯一值，批准事件必须匹配，不在分支再存一份可冲突的 operation_id。不填模型任务或用量。

- 绑定引用采用既有零起算位置及规范事件行摘要；必须位于本笔事务固定前缀内，解码后确为对应 `HumanSubmissionBound`，不能只核对自报摘要。完整候选及 basis 从该事件取得，不重新读取当前草稿拼装；草稿簿丢失不改变已入簿候选权威。
- 准奏请求摘要须绑定上述请求及来源身份，使用独立于保存／送审的域和固定序列化；同作用域请求同内容返回原 operation_id，异内容拒绝。先核对操作权限，再查持久回执；不因本笔批准已替换前任而把原样重试误判为旧基线。摘要的准确字节在实现前固定，不沿用绑定请求摘要冒充准奏请求摘要。
- **候选摘要、最终目标字节摘要和事件前缀摘要不同。** 候选是冻结的 `review_json/2` 等表示；最终批准表示须另有确定的格式身份及无损转换规则，其字节可以不同。应用层核对转换与结构，不假定两个摘要相等，也不以明文相同忽略注音／着重变化。批准目标格式仍未实现，未知格式必须拒绝，不能降成旧纯文本格式“恢复”。
- `targets` 仅记录实际物理创建或改写，禁止删除和 before／after 同字节条目；本批规划的单块人工准奏为零或一个物理目标。即便同字节而 `targets` 为空，人工来源和批准事件仍须固定该块**逻辑输出**路径、格式及 before／after，检查盘上确实存在对应字节；不能因遍历空目标列表就认为成功。相同字节批准仍改变批准身份，照常走代次与唯一事件。
- 人工批次只能是可选一个前置 `Clock` 加恰好一个匹配的未来人工批准事件；绑定必须已在前缀，不混进本批，不接受模型批准或另一 operation_id。批准编码、最低读本及会典隔离还须在实现批单独接通，现有绑定兼容验收不代替批准兼容验收。

### 20.3 前缀计数与日志证据分类

`events.expected_events` 是**追加后总条数**；前缀条数等于它减去 `encoded_events.len()`，须检查下溢。`expected_bytes` 与裸十六进制 `history_sha256` 则固定**追加前原始前缀**，包括每条末尾 LF；不改成第 18 节的规范事件序列比较。规范事件引用摘要不含 LF，恢复信封 checksum 则带 `sha256:` 前缀，三者按各自规则核对。

实现人工恢复时，日志读取不能再只有一个布尔值。以下是设计分类名，不是当前 API／界面文字：

| 证据 | 人工处理规则 |
| --- | --- |
| `clean_absent` | 完整前缀的条数、原始字节长度和摘要均匹配，且前缀后没有任何字节；这才证明记录批次未追加。读取报错、短文件或尾部残行均不是这种状态 |
| `exact_at_slot` | 在记录固定位置逐字节找到全部含 LF 的批次，并解码匹配来源、请求、operation_id 及输出；不能找最新几条、别处的同文事件或只有终止标签。后接合法无关事件仍按固定槽位识别；涉及本块材料／批准身份的冲突另行阻断，不截掉后续事件 |
| 部分、残行、分叉或不可读 | 只有 `Clock`、批准行缺 LF、位置被占、前缀被替换、另一笔同文批准、未知事件或 I/O 错误都保留现场并阻断。不得把 `false` 当不存在、截断尾部、补剩余事件、自动回滚或删除记录 |

例如前缀 17 条、本批 2 条，则 `expected_events` 为 19，批准在索引 18；绑定索引 16 可在前缀中，17 不可。语义等价但原始前缀字节改变，也不满足旧恢复摘要；此规则不反向改变待决绑定发布的规范前缀比较。

### 20.4 写入次序与中断矩阵

现行次序是：完成预检并构造固定记录／批次 → **先预留奇数代次** → 发布恢复记录 → 写目标 → 追加固定事件批次 → 记录 `Completed` → 完成偶数代次 → 移除终态记录。不能把“记录先持久化、再预留代次”说成现有保证。未来人工路径须全程持匹配工作区锁，追加时仍持事件簿锁检查固定前缀；构造／大小／格式验证必须在预留前完成。

下表只规定未来人工分支。`finish` 保留“只收尾”的含义；“显式继续”是待实现的另一个操作能力，不在本批添加或借用现有 CLI 命令。

| 中断现场 | 允许行为与必拒绝行为 |
| --- | --- |
| 偶数代次，尚未预留、无记录 | 普通准入；没有持久 operation_id 时，不从当前草稿猜测一笔“旧事务” |
| 已预留奇数代次，记录尚未发布 | 所有新写入继续阻断；这是既有空窗，不因无记录就自动改回偶数或宣称没写过。保留现场并显式诊断；本批不承诺自动修复无记录空窗 |
| `Published`，目标全 before，日志确认未追加 | `finish` 不放行；显式继续必须重做来源／材料／冻结候选准入后再执行原固定事务；显式放弃须证明目标全 before 且日志确为 `clean_absent`，不追加批准 |
| `Published`，目标全 after，日志确认未追加 | 盘上 after 不是已准奏；`finish` 不放行。显式继续在完整核对后只追加原固定批次，不再改稿；basis 的旧译稿摘要对照记录 before，盘上稿对照 after，不能拿本笔已写入的 after 要求等于旧 before。原文、批准上下文、朱批或前任来源真变了仍阻断，不沿用旧准入 |
| `Published`，目标全 after，批次固定位置完整匹配 | 不再写稿或批准，只做完成状态／代次收尾；同文批准必须确认本笔 operation_id。原请求响应丢失则从持久事件返回同一回执，不另造批准 |
| 目标外部改动、before／after 混合，或日志部分／残行／分叉／不可读 | 停止，保留记录与文件；不盲目继续、回滚、放弃或截断 |
| `Completed` 尚为本笔奇数代次 | 先核实逻辑输出 after 与完整固定批次，再推进到记录的偶数后代次并移除记录；不能只信 `Completed` 字样 |
| `Completed` 已为本笔偶数后代次 | 同样核实证据，仅移除记录，不再次 finish 代次或追加事件 |
| `Abandoned` 为本笔奇数／偶数后代次 | 核实全 before 及 `clean_absent`；奇数先完成代次，偶数仅清理。其他代次及证据矛盾均阻断 |

同字节目标须走相同矩阵，不能单靠“全 before”与“全 after”二选一；决定有无批准的是固定批次。首轮人工生产路径只发布 `Published` 记录；若发现人工 `Prepared` 现场，不能据状态名自动执行或清理，须先有单独验收过的状态规则。无记录奇数代次、残行和混合现场均不在自动收尾范围内。

> 补注（第 22.30 节）：本表写于 2c-3b-7 之前，表中“`finish` 不放行”是当时的历史结论；本批之后 `finish` 在“目标已写、批次未追加”时先于事件簿锁内重做人工准入复核，通过才补记固定批次。复核项含送审绑定须位于固定前缀之内、当前来源等于记录的前一来源、材料基准、冻结候选目标与记录一致、磁盘等于记录 `after`；任何一项不符即拒绝且不改盘。这不改变“不得据状态名自动执行或清理”的原意，人工 `Prepared` 仍须 `--confirm-prepared`。

### 21.1 固定编码与坏来源输入

#### 22.2.1 所有权核对

| 层 | 已有或本批新增 | 边界 |
| --- | --- | --- |
| core | `TranslationSource`、`DraftBasis`、`EventReference` 已定义；新增 `HumanApproval`、`HumanApprovalRequest`、`HumanApprovalTarget` | 只描述事实，不解释文学标记或候选载荷 |

#### 22.2.2 事实字段与摘要

- `HumanApprovalRequest` 依次保存 project、block、request_id、actor、submission_id、binding、previous、target。字段顺序参与摘要。
- `submission_id` 是送审绑定的请求 ID，用来在本块回查冻结候选；`binding` 另记该绑定事件的零起位置与规范行摘要。**本批只核对格式与绑定存在，不核对日志位置**，原因见 22.2.4。
- `previous` 必须与本块送审绑定所冻结的前一来源相同，否则拒绝。
- `target` 只允许一个目标：format 为 1–64 位字母、数字或 `.` `-` `/` `_`；path 只能是 `translations/<project>/<block>/zh.json`；before 可空（文件不存在），after 必填；两个摘要均为 64 位小写十六进制。
- `HumanApproval` 另含 request_hash 与 operation_id（32 位小写十六进制，事务身份即批准身份）。请求摘要的域为 `["ziyuan/human-approval", 1, request]`，按声明顺序编码；固定样本摘要 `28209133f97d3a919693b4c36242e643b72428ec5c4c9c83bf71e24d76d69acd` 由独立脚本计算，不调用待测编码器。
- 同一项目／块／批准请求 ID 只能有一份回执；重复发布拒绝。同一候选换请求 ID 是新请求，不共享身份；相同字节也不得靠“同文”跳过新请求。

#### 22.2.3 编码与读取门槛

- 事件行：`v1\tHUMANAPPROVED\t<JSON 的 hex>`；未知字段、错分支、缺字段、多余字段均拒绝；容量按 hex 后的实际字节计，上限 8 MiB。
- 最低读本为预留的 `1.5.0-dev.2`（序号 25），已登记进 `RELEASES`；包版本仍为 1.4.1，**未发布该读本**。
- 会典标签换为 `v1.4.1-human-approvals-v1`，旧缓存不沿用、下次打开重建，避免旧缓存跳过新事实。
- `compat.tsv` 增加一条固定的定本行；摘要与字节由独立 Node 脚本生成，测试只核对往返与最低读本，不用实现反推期望。

#### 22.2.4 不做什么

- 不写 `zh.json`、不落盘、不改 generation 或恢复记录；`human_approval` 只是应用层查询，不是写入凭据。
- 不更新“当前批准来源”。回执只证明“这次请求被记录”，当前来源仍由后续准入批在持锁核对材料与日志后推进。
- 不开 CLI／Web 入口，不接定稿、导出或记忆；也不伪造模型任务或用量。
- 不核对绑定事件在日志中的真实位置：`apply` 只有事件本身，没有索引与原始行。持锁准入批必须用真实事件簿核对前后文，不能拿本批回执冒充已经核对。
- 不定义“批准后写出的字节”。target 只是事实记录；无损转换、写盘与恢复事务都留给 2c-2／2c-3。

### 22.7 本批 N1a-2c-3b-3：显式继续、放弃与空窗提示（内部契约）

本批补齐只收尾之外的两条明确路径，仍不重放业务、不改正文。

- **显式继续**：`Published` + 目标全为新内容 + 批次未追加（`clean_absent`）时，`finish` 用记录里固定的编码行补记批次；补记前重读事件簿并核对条数，再由 `append_if_unchanged` 核对完整规范前文后追加。冲突、残批或位置不明一律拒绝，不截断残行、不覆盖正文。
- **放弃**：`Published` + 目标全为旧内容 + 批次未追加时，`abandon` 把第二版记录标为已放弃、推进世代并清理；目标已变或批次已出现时拒绝。零目标记录核对逻辑输出。
- **空窗提示**：`status` 遇到奇数代次但没有恢复记录时，改说“只留下奇数代次、没有恢复记录；请人工核对工作区，不要手工改代次”，不再显示“无待处理”。
- 未做：真实故障注入矩阵（发布前／正文后／事件后／终态）、`Prepared` 现场、第二版 model 记录的继续／放弃；这些仍阻断。

验收：目标已写、事件未追加时继续成功（补出与记录一致的批次，正文与记录不重写）；目标仍旧、事件未追加时放弃成功（推进世代、清理记录、事件簿不变）；目标已变或批次已在固定位置时两种命令都拒绝。CLI 恢复测试 17 项通过；本机 Windows 通过，不冒充原生 CI。

### 22.8 本批 N1a-2c-3b-4：终态与故障现场（内部契约）

本批补齐收尾的终态与异常现场，仍只动记录与世代，不重放业务、不改正文。

- `Completed` + 批次在固定位置 + 目标新：直接推进世代并清理，不重复标记完成。
- `Abandoned` + 批次未追加 + 目标全旧：`abandon` 可重入，只推进世代并清理，不再改写状态。

- 第二版 model 的继续／放弃仍不支持；`Prepared` 现场仍拒绝。
- 故障现场由构造真实文件状态模拟（缺失／半批／精确／篡改），不是 kill 进程注入；不把模拟结果称为崩溃恢复证明。

#### 22.30.2 行为

**准奏即落盘。** `ziyuan text human approve <项目ID> <块ID>` 在一次受管写入事务内按第 20.4 节次序完成，任一步失败都不留“语义上已准奏、字节上未落盘”的状态：

1. 锁内预检：送审绑定仍在事件簿的固定前缀内、当前来源等于绑定的前一来源、磁盘 `zh.json` 现状等于送审基准、原文／上下文／朱批未变、事件簿无残行。
2. 构造并校验第二版人工恢复记录（大小、分支、零目标规则都在预留前完成）。
3. 预留奇数代次。
4. 发布第二版人工恢复记录（`Published`）。
5. 写目标：同目录临时文件刷盘后改名；Unix 再同步目录，Windows 跳过目录同步；`before` 与 `after` 相同（同字节准奏）时不写盘。
6. 追加“可选一条 Clock＋唯一一条人工准奏”事件批。
7. 标记记录完成，推进到偶数代次，移除记录。

发布之后任何一步失败都保留现场，错误里给出 `ziyuan text recovery status` 与对应的 `finish`／`abandon` 命令，不自动重试、不回滚、不截断事件簿。落盘格式由冻结候选的批准目标决定：无标记的第二版候选按第一版 `zh.json` 落盘，带标记候选按第二版落盘，不因“顺手统一”改字节。调试构建另设三个真实中断点（发布后／写稿后／追加后，`ZIYUAN_INTERRUPT_RECOVERY`，发布构建不编译），供子进程中止测试；它不是发布包功能。

**`apply` 改为只读核对。** 准奏已经落盘，`ziyuan text human apply` 不再写任何文件，只核对“准奏时已落盘”：工作区无未收尾恢复记录、当前来源是人工准奏、磁盘 `zh.json` 等于该准奏的 `target.after`；通过后打印下一步 `ziyuan text human finalize`。磁盘被外部改动时明确拒绝，不顺手重写。

**请求身份由草稿修订号派生。** 送审请求 ID 为 `submit-r<修订号>`，准奏请求 ID 为 `approve-<送审请求 ID>`；同一块可多轮人工流程，每轮新修订号即新请求。同请求重试幂等：送审返回原快照、准奏返回“此前已准奏”，不重复追加事件，也不靠“同文”跳过新请求。

**恢复收尾加固。** 第二版记录的 `finish`／`abandon`：

- 动盘前先核代次：当前代次只能是记录的前代次加一，或等于记录的后代次且记录已是终态（只清理）；其余拒绝且不改盘。
- 人工批次的送审绑定必须位于记录的固定前缀之内，并与准奏事件引用的位置、请求 ID 逐项相符；只在批次里“自带一条绑定”不算。
- 零目标只用于同字节准奏，要求记录的 `before` 必须等于 `after`；为“没写盘”留空目标一律拒绝。
- 发布前（`Prepared`）记录显式继续时，先在事件簿锁内核对条数与完整规范前缀，通过后才把记录推进为 `Published` 并追加，核对失败时记录保持“已准备”，不出现“拒绝却改盘”。
- `--confirm-prepared` 只用于第二版 `Prepared` 记录；用在一版记录、`Published`、`Completed`、`Abandoned` 上都是用法错误（退出码 2），不静默忽略、不改盘。
- 标记完成与放弃前都在锁内再核一遍目标，防外部编辑器在核对与写入之间改动。
- `finish` 对第二版人工记录在“目标已写、准奏尚未入簿”补记前，于锁内重做一遍人工准入：绑定位置与引用、当前来源等于记录的前一来源、材料基准、冻结候选的批准目标等于记录、磁盘等于记录 `after`；不符即拒绝且不改盘。模型第二版记录不走这段人工复核。
- 第二版信封与 `HUMANBOUND`／`HUMANAPPROVED`／`HUMANFINAL` 事件行一律按实际字节计上限 8 MiB，不量正文或转义前字符数。
- `ziyuan text recovery status` 的下一步按记录状态区分，写真实操作号与完整命令（`Prepared` 两条带 `--confirm-prepared` 的命令、`Published` 的 `finish`／`abandon`、`Completed` 的 `finish`、`Abandoned` 的 `abandon`），不再给一句笼统提示。

**状态与导出按当前来源分派。** 当前准奏来源取事件顺序里的最后一条；人工签押只对当前人工 `operation_id` 生效，模型签押只在来源为模型时生效；更早轮次的人工定稿与人工准奏都不算数。人工定稿让位于“待准奏”：有待决改动时先按待准奏显示，不显示已定稿（相较 22.13、22.20 的行为变化）。

新增人工“版本失效”：人工送审或定稿之后原文、批准上下文或朱批变化即失效，状态为 `human_stale`（标签仍是“版本失效”），理由新增 `zhupi_changed` 描述“朱批已变”，须重新保存草稿后重新送审；不自动回滚、不自动重新准奏。

`ziyuan text export-finished` 接受人工定稿块：纯文本块与模型定稿同形状，清单里记 `source: human` 与操作身份；带标记稿在 `--format md` 下按无损规则写出（ruby／粗体／斜体），着重点与同范围叠加整批拒绝，TXT 遇带标记稿整批拒绝并提示改用 `--format md`。导出仍只读，不改审批、材料或记忆资格。

**文案与帮助。** 终端统一说“已保存／已送审／已准奏（并已落盘）／已定稿”，草稿字段称“修订号”并取代 revision 字样；每条成功回执给出完整的下一步命令；`ziyuan help` 与 bash／fish 补全列出 `text human`；帮助文本里的人工准奏一行写明“准奏最新送审并写入 `zh.json`”。

### 22.31 本批：Web 人工译稿接口与标记编辑器

本批开放 Web 人工入口：六个 HTTP 接口加网页里的逐段双语编辑与标记编辑器，不编辑 JSON 即可走完保存→送审→准奏（落盘）→定稿。TUI 仍未开，包版本未升，未发版。第 22.24–22.30 节里“Web 入口未开”“Web／TUI 入口未开”“网页只能显示”的表述是当时结论，由本节取代，原文保留作历史记录。

#### 22.31.1 范围

- 接口（均在 `/api` 下，沿用既有令牌；观政只能 `GET`）：
  - `GET /text/{项目}/blocks/{块}/human`：只读查看现行材料基准、草稿（可无）、状态与人工准奏／定稿事实；未开国时 `founded` 为 `false`，不报错。
  - `GET /text/{项目}/human/progress`：按章与全项目计数，外加下一块未起草的块。
  - `POST …/human/draft`：请求体即 `DraftSave`。修订冲突、材料基准变化、请求号被占都回 409（修订冲突时带 `current`），标记或段落不合法回 400。
  - `POST …/human/submit`、`…/human/approve`、`…/human/finalize`：与 CLI 共用应用层事务，Web 送审／准奏记录 `actor: web`，CLI 仍为 `local`；入口校验来源，不信任请求体自报渠道。送审请求 ID 同样由修订号派生，准奏即落盘，定稿只记事实；重复调用幂等。三者都要求先开国，否则提示 `ziyuan init`，不伪造开国；事件簿读取失败单独报错并提示检查恢复现场，不误报未开国。
- 静态模块：`/assets/editor-core.mjs`（标记纯逻辑）与 `/assets/human-editor.mjs`（编辑器界面）。与 API 同一把令牌：无令牌 401，观政可读，未知资源 404，`no-cache`。页面在打开一块之后才按需加载编辑器（此时必已登录），加载失败只影响编辑器区域，不拖垮整页与登录框。
- 编辑器：逐段左原文、右 `textarea` 人工译文；选区后加注音（输入读音）、着重号、粗体、斜体；每段下方有安全转义的渲染预览，以及“种类／UTF-8 字节范围／读音／删除”结构表。窄屏改为单栏。

#### 22.31.2 行为

**偏移口径。** 浏览器选区是 UTF-16 码元，落盘是 UTF-8 字节，并须落在字素边界上。`editor-core.mjs` 用 `Intl.Segmenter` 切字素，`markup.rs::grapheme_boundaries_agree_with_web_editor` 用同一组样本（CJK、组合符、emoji、ZWJ 家庭）核对它与服务端 `unicode-segmentation` 结论一致。浏览器没有 `Intl.Segmenter` 时退到按码点切分，此时前端校验比服务端宽，以服务端复核为准。

**本地预检与上限。** 前端按服务端同一规则逐段预检（同一行内完整字素的非空范围；只允许不相交或同范围不同种类；重复、嵌套、交叉拒绝），并按**整稿**合计标记数（≤4096）与正文＋读音字节（≤256 KiB）。不合规时禁止保存并逐条列出；服务端仍复核。

**保存状态。** 未保存／保存中／已保存／冲突／不合规五种状态。保存在途时禁止重复提交，同一份内容重试沿用同一请求号。409 或轮询发现磁盘修订、材料基准变化时，若本地有未保存改动即进入冲突，**不静默覆盖**：要么“加载磁盘（替换本地）”，要么“确认保留本地，取最新基准”后再保存；两者都先重新读取，再经确认。本地没有未保存改动时直接跟随磁盘，例如准奏落盘后基准里的译稿摘要变了，不算冲突。

**会话镜像。** 按项目／块把未保存内容镜像到 `sessionStorage`。刷新后发现镜像必须明确选择“恢复”或“忽略”，未选之前不能编辑或保存，也不会自动写盘。保存成功即清除镜像，与磁盘一致的旧镜像自动忽略，不再把已保存内容误报为待恢复。镜像与当前原文段落对不上时拒绝恢复。存储不可用时给出提示。

**输入法。** 组合输入期间不镜像、不校验、不重绘编辑框，`compositionend` 后一次性处理；组合期间要求切块时推迟到组合结束。轮询与整页重绘不替换活跃编辑器的 DOM 节点，编辑框里浏览器原生的撤销与选区因此得以保留。

**撤销。** 文本打字只用浏览器原生撤销，不拦截 `beforeinput` 或 `Ctrl+Z`。“撤销标记／重做标记”只管标记，最多 100 步；文本一改即清空标记历史，以免旧标记套到新文字上。

**流程按钮。** 有未保存改动、冲突、不合规或尚无修订时，送审／准奏／定稿都不可用；每次都要确认；进行中禁止重复。已定稿的块锁定编辑。页面不猜“当前修订是否已送审”（接口不提供这一事实，进度里的送审数是历史计数），按钮照常给出，由服务端核验后回报。观政只读：编辑框只读，写按钮隐藏。

**进度口径。** 已起草＝至少一段非空；送审是历史计数，不代表当前修订已送审；准奏含人工版本失效；“下一未起草”是第一块尚无非空草稿的块，不等于“第一块没译完的块”。正文与读音字素分开计数。进度读草稿时与编辑器走同一套类型化读取，草稿损坏或路径不是普通目录即回 400，不再误计为“未起草”。

**只读不写盘（补正 22.24）。** 原 `peek_human_draft` 经草稿路径的建目录函数读取，会建空的 `human-drafts/` 目录；草稿文件已在、锁文件不在时，`JsonFile::load` 还会建锁文件。两者都已改：只读路径逐级核对已有祖先（仍拒绝符号链接与非目录）而不创建；`load` 仅在锁文件已存在时取共享锁，否则直接读（写入一律整文件改名发布，读到的只会是完整的旧版或新版）。Web 测试的盘面比对随之改为文件与目录一并比较。

#### 22.31.3 不做什么

## 23. 上下文格式第二版：格式与兼容底座（设计）

状态：格式与兼容底座已实现；[work 分支六项 CI](https://github.com/YuuUehara/Ziyuan/actions/runs/42132945744)全过后，已随 `9f9c44dc` 快进并推送 main。本节只定第二版术语表的盘上形状、解析与兼容边界；人物／术语的编辑界面、按位置筛选与外发规则属于 N2a，本批不做。落实第 4.1–4.3 节，不改第 4 节的语义。

### 23.1 盘上形状

仍是同一份 `glossary.json`，**不另建文件**，按顶层类型分派：

- 顶层是数组：第一版（旧格式），条目仍为 `GlossaryEntry`（`source`／`allowed`／`scope`／`note`），原义不变，自由文本 `scope` 不解析成规则；旧快照字节不变，不回填 ID。
- 顶层是对象：第二版，形如 `{"format": 2, "terms": [...], "persons": [...]}`。`format` 只接受 `2`；更大的数字报“须升级”，其他值或缺失报格式错误。

不另建 `entities.json` 等新文件的理由：旧程序批准上下文草稿只读 `glossary.json`、`style.md` 与 `summaries/`，新文件会被静默丢弃，产出缺人物资料的快照。顶层改为对象后，旧解析器（数组且拒绝未知字段）在草稿批准与快照读取两处都会报格式错误，不会静默忽略，等于不另加版本头的最低读写版本保护。

### 23.2 第二版字段

所有对象拒绝未知字段；文本沿用第一版的非空、长度与控制字符检查和条数上限。ID 为 1–64 位 ASCII 字母数字、`-`、`_`，同类内唯一。

- **Term**：`term_id`、`source`、`category`（`person_name`／`place`／`organization`／`title`／`culture`／`common`）、非空 `allowed`、可选 `note`、`scope`、可选 `available_from`、`evidence`、`status`（`tentative`／`confirmed`）。
- **Person**：`person_id`、`name`、可选 `reading`、`aliases`、`terms`（引用 `term_id`，人物卡不复制 `allowed`）、`address_rules`、`voice`（`description` 说明及可选 `examples` 原文例句数组）、`evidence`、`status`。同名不同 ID 合法；别名不合并身份。
- **称谓规则**：`target`（被称呼的 `person_id`）、`speaker`（`{"kind":"person","person_id":…}`／`{"kind":"narration"}`／`{"kind":"unknown"}`；未知不是通配符）、`scope`、`term`（`term_id`）、可选 `note`、`evidence`。
- **范围** `scope`：`{"kind":"project"}`，或 `{"kind":"range","from":位置,"to":位置}`；位置为 `{"chapter":章ID,"paragraph":段ID?}`，省略段表示整章。两端都包含，按项目章序与原段顺序比较。
- **`available_from`**：一个位置，表示最早可用于任务处；缺省时 N2a 不得自动外发（第 4.3 节）。
- **证据**：`paragraph`（段 ID）、`quote`（须为该段原文子串）、`explanation`、`stance`（`project_fact`／`character_belief`／`narration`）、`status`（`tentative`／`confirmed`）。

字段上限：原文、译法、姓名、读音、别名、例句及短引各 200 字，备注与说明各 500 字；`allowed` 为 1–16 项，`aliases` 与 `voice.examples` 各至多 16 项，其余条目／引用／规则／证据数组各至多 5000 项。必填数组须显式给出，可为空，唯 `allowed` 不可为空。整章范围的 `from` 取章首、`to` 取章尾；段到本章整章、整章到本章某段均合法。

### 23.3 校验

- 结构校验（无项目也能做）：字段、ID 形状与唯一、引用不悬空（`terms`、`target`、`speaker.person_id`、`term`）。
- 项目校验（批准与读取快照时）：位置的章／段属本项目、`from` 不晚于 `to`、`quote` 是所引段原文的子串。任一不符整份拒绝，不跳过个别条目。

### 23.4 本批的生产行为

## 24. N2a 首批：范围与可见性判定（设计）

状态：用户已确认本批范围、人物整卡门槛及下列六点设计；本节为待审阅规格，尚未实现。只增加应用层的只读判定，不提前开放人物／术语生产功能。

### 24.1 范围与格式增量

- 输入是同一项目的第二版词表、项目实际章段与目标块，以及调用方显式提供的段落人物关联；不读取网络、不调用模型、不读写草稿或快照文件。
- `Person` 新增可选 `available_from`，形状与 Term 相同，结构与项目校验同步覆盖。缺省仍可解析、序列化不补字段，但整卡不能自动选入。保留 `format: 2`；第 23 节已存在的第二版样本不强制补字段，第一版数组不新增字段、不迁移。
- 本批只有纯应用层接口，没有 CLI、Web API 或界面；第二版的批准、快照生产读取、提示导出、勘校与札记并入继续保持第 23 节的拒绝行为。判定函数能分析第二版不代表该资料已获批准或可进入请求。
- 旧数组不是结构化规则。新判定接口遇旧数组明确报告“旧词表须人工确认并显式升级后才能作结构化判定”，不解析自由文本 scope，也不影响旧生产路径。

### 24.2 两层结果：段落适用与块级自动候选

1. **段落适用**只回答结构化范围、人物关联和说话人条件是否满足；它不授予资料使用资格。后文才知道的规则也可在本地被检查为“范围适用，但尚不可自动选取”。
2. **块级自动候选**还须通过可见性门槛，且至少在块内一个原段适用。返回实际适用段号，不将局部适用的规则冒充全块通用。
3. 项目／区间范围按实际章序与原段顺序计算，左右端包含；整章起点取章首、终点取章尾。范围与目标块的交集以块中实际原段为准，不用 ID／文件名字典序，也不按故事内时间重排。
4. 自动候选要求 `available_from` 不晚于目标块**首段**。等于首段可以；块中途才揭示，即使规则在后半块适用，也不自动选入整个块。
5. 缺少可用起点不能靠字面命中、`confirmed`、证据最早出现处或人物别名自动补齐。`available_from` 是人工提供并经项目位置校验的声明，不宣称已自动证明资料在该处为真。

### 24.3 整卡门槛与证据

- Term 必须有可用起点，且本条全部证据来源段不晚于块首段；未来证据的短引、解释与状态不能夹带到早期候选。缺少起点时，即使已确认也不自动选入；暂定资料通过门槛后仍保留暂定状态。
- Person 整卡包括姓名／标题、读音、全部别名、口吻说明／例句、term 引用、称谓规则、证据及状态。先检查本人的可用起点、卡内全部证据（含称谓规则证据），再检查所有关联术语的可见性；任何一项缺少起点或来自未来，整卡均不进入自动候选，不仅隐藏那一条正文。
- 卡内术语依赖包括 `persons[].terms` 与称谓规则的 `term`。这里检查术语的**可见性**，不要求该术语的 scope 在当前段适用；可见但不适用的术语不会因此成为适用词条。
- 称谓规则还引用目标人物及可能的具体说话人。整卡所引用的这些人物也必须能通过整卡门槛，避免由关系、引用 ID 或卡片标题泄露未来身份。按依赖闭包保守排除：循环引用本身不算错误；循环内全部资料均可见则保留，任一依赖不可见则排除相应卡片及依赖它的卡片，不以遍历顺序决定结果。
- 例句与别名没有逐字段起点；由人物整卡的人工可用起点约束。若新增后文才揭示的别名／口吻，录入者须将整卡起点后移；程序不能从自由文本识别未声明的剧透。本批不创建录入入口。
- 术语可独立通过其自身门槛；人物卡被整卡排除不会倒过来隐藏本来可见、且不受称谓规则约束的术语（包括人名词条）。整卡策略只决定整卡是否进入自动候选，不自动合并、停用、删除或重写人物身份。

### 24.4 人物关联与称谓适用

- 调用方按目标块内的原段 ID 显式提供“本段关联人物 ID 集合、被称呼人物 ID 集合、说话人”。说话人分为具体人物、叙述、明确未知，另以未提供表示**未标注**。不通过原文词形、人物同名、别名或模型推断补关联。
- 人物特定规则仅对已人工关联的人物应用；称谓还须目标人物属于本段显式被称呼集合，并与规则 `target` 相同。具体说话人按 person ID 精确匹配，叙述只匹配叙述，明确未知只匹配明确未知；未标注不匹配任何说话人条件，返回待人工核对原因。
- 段落范围、term.scope、称谓规则 scope、目标人物关联及说话人条件取交集。任何条件不符则本段不适用；多个适用规则全部保留，允许译法不被静默合并成一条“统一答案”，不按数组最后一项胜出。
- 词条候选不等于认定人物身份：`person_name` 也可仅按自己的范围与可见性成为词条候选，不自动关联某张人物卡；共享同一 term 的多个同名人物仍按不同 person ID 处理。只有人物卡与人物特定规则需要人工关联，不能因此改变 N0“恰好块首可用的独立术语仍可成为候选”的预期。
- 被任一称谓规则引用的 term 作为**条件词条**处理：不能绕过规则，以普通词条身份进入自动候选。其段内适用来自实际匹配规则，自动候选还须至少有一条匹配规则及其人物依赖通过可见性门槛；保留各条规则身份，不将不同条件的允许译法混合。若用户另需无条件的同字词条，应显式建立不同 term ID，本批不自动复制。
- 重复段落关联项、未知段落／人物、段落不属于目标块、同段同一集合重复 ID 均报可定位的中文错误，整次拒绝；集合中的同名但不同 ID 合法。一段只能显式给一个说话人状态，无法确定时保留未标注，不假装支持段内多说话人的精确范围。
- 关联仅为调用方本次输入，不新增关联文件、自动出现索引、持久化事实、批准资格或权限。

### 24.5 返回与不做什么

- 返回本地只读判定：项目／目标块身份、段内适用项、自动候选 term／person／称谓规则身份及各自适用段号、暂定／确认状态；同名条目不去重、不自动替换译文。
- 第 23 节称谓规则没有独立 ID，本批用“所属 person ID＋规则数组下标”定位，只在本次输入内有效，不冒充跨版本稳定身份。术语与人物按输入顺序、段号按实际原段顺序返回，不用哈希表迭代顺序决定结果。
- 排除原因单独作为本地诊断：缺可用起点、起点晚于块首段、未来证据、关联资料不可见、范围不相交、人物／目标未关联、说话人未标注或不符等；区分“无适用项”和“输入无效”。诊断可以列被隐藏的本地 ID，但不是可外发资料。
- 不返回姓名、别名、口吻、证据解释、允许译法等正文，不序列化原始 Person／Term 为“已筛选提示”。本地候选 ID、排除原因及隐藏项数量均**不得直接接入模型提示**。以后组装实际材料时还须单独预览、完整过滤与请求捕获验收。
- 自动候选只是范围与可见性的必要条件，不代表已批准、已经外发、文学判断正确或允许自动定稿。不检查模型是否已经知道剧情，也不为旧全局 style／摘要提供防剧透保证。
- 不开放未来资料显式回修选择；不增加 `include_future`、忽略门槛等绕过开关。本批无批准、外发、预算截断、UI、自动关联、自动升级、模型调用、事件、版本号或快照清单格式变更。
