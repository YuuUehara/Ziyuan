# 下一批计划：代码任务闭环、Windows 号舍与代码仓库索引

本文保留 2026-11-01 起的分批设计与验收过程。下文开篇的“当前”“后续”指制定计划时的状态；各批实际进展见后文记录，现行能力与版本以 [README](../README.md) 为准。

日期：2026-11-01。源码盘点基线为 1.4.0 及文档提交 [0cc53e6](https://github.com/YuuUehara/Ziyuan/commit/0cc53e6701ca7dca1f048a71d05e18df60892b58)；当前已发布 [1.4.1](acceptance/1.4.1.md)，该补丁未实现下列能力。按本轮确认，将 Windows 原生号舍和代码仓库索引列为正式开发主线，不再只留作历史议题。这是开发计划，不是已交付功能，也不先承诺下一版本号或日期。

## 一、先看结论

代码任务已有“下诏授玺 → 承办暂存 → 副本测试 → 都察院复核 → 用户审阅 → 准奏落盘 → 可选提交”的闭环，失败写入也已有恢复协议。下一批不重建工作流，不继续扩大翻译功能，先解决**验功所据能否对应眼前改动、止令后执行如何收尾、已落盘怎样安全补提交**。

同时推进两项主能力的分批交付：**Windows 原生号舍**让受保护的测试／本地外藩具备可验证隔离；**代码仓库索引与检索**让代码任务能找到带路径、位置及内容版本的材料，再以实测决定语义向量方案。现有 Windows CI 通过不等于已有原生沙盒，现有翻译字符哈希也不等于已有代码语义检索。

盘点没有证实需要撤回 1.4.0 的越权落盘问题。下文的风险是后续开发优先级，不等于漏洞等级；源码缺少某项绑定不等于已在生产触发。没有动态复现的项目均明确标为待验证。

### 优先级与启动顺序

| 优先级 | 批次 | 先交付什么／依赖什么 |
| --- | --- | --- |
| P1，先行小批 | 4A · 验功有据 | 先复现并修正测试状态，不等待两条新主线，也不扩大为完整报告平台 |
| P1，安全主线 | W0 → W1 → W2 · Windows 原生号舍 | 4A 后先完成 W0 威胁模型与可行性验收；W1 隔离原型与 4B 进程收尾衔接；W2 才接入正式受保护执行 |
| P1，闭环保障 | 4B／4C | 4B 为 W1／W2 提供取消与清理要求；4C 在 W0 后安排复现，若确认会夹带非准奏内容，先修再扩展自动提交入口，不让小修无限挤占主线 |
| P2，功能主线 | R0 → R1 → R2 · 代码仓库索引 | W0 后启动 R0 本地索引契约与样本基线，再做 R1 安全检索闭环、R2 语义向量与混合检索；不必等待 W2 全部完成 |

默认实施节奏为 **4A → W0 → 4B／W1 与 R0 分别验收 → W2 与 R1 → R2**。这是依赖顺序，不是同时铺开所有实现的授权；每次只启动已选定的小批。Windows 条件未齐时先报告缺项，不以无隔离执行凑通过，也不因此无限阻塞本地代码索引。4C 以复现结果决定插入位置，仍须在放宽提交能力前验收。

## 二、现有闭环与边界

| 环节 | 已有能力与直接依据 | 不能混作什么 |
| --- | --- | --- |
| 下诏与授权 | CLI／Web 可指定工具与范围；TUI 普通下诏为默认权限，模板可携带权限。治理层路由收窄玉玺，运行时只构造获授工具。见 [sealed_tools](../crates/ziyuan-runtime/src/tools.rs#L84-L110)、[Web 下诏](../crates/ziyuan-web/src/edicts.rs#L47-L89)、[TUI 模板](../crates/ziyuan-tui/src/input.rs#L664-L673) | `scope` 不是每条路径各自不同的读写 ACL；有测试权限也不等于有任意命令执行权 |
| 承办与测试 | `write_file` 只暂存；`run_tests` 复制项目、叠加暂存文件，只运行用户配置命令，限制环境、输出与时长。见 [RunTests](../crates/ziyuan-runtime/src/tools.rs#L731-L866) | 模型说“测试通过”不是工具实测；测试通过也不是落盘 |
| 复核与审阅 | 程序核对引用位置、最近一次测试成败，再请御史判断；Web／TUI 共用差异预览。见 [check_evidence](../crates/ziyuan-app/src/censorate.rs#L64-L161)、[preview_changes](../crates/ziyuan-app/src/preview.rs#L43-L108) | 行号存在不证明论断正确；背书不是用户“采纳”，采纳也不是准奏 |
| 准奏落盘 | 检查任务及待决改动，可逐段驳回；写前核对原文、持工作区锁，先发布恢复记录，再写文件与事件。见 [apply_reviewed](../crates/ziyuan-app/src/edicts.rs#L414-L466)、[write_transaction](../crates/ziyuan-app/src/edicts.rs#L765-L890) | 受管串行写入不是多文件同时可见，也不是抵御外部恶意进程的原子隔离 |
| 恢复与提交 | 失败写入留下恢复记录并阻断后续写入；CLI 提供 `text recovery`。`commit_applied` 支持已落盘任务补提交，并按尾注识别已有提交。见 [VCS](../crates/ziyuan-app/src/vcs.rs#L118-L181)、[恢复公开测试](../crates/ziyuan-cli/tests/recovery_commands.rs) | 落盘成功不保证 VCS 提交成功；恢复不是自动回滚或自动重跑模型 |

普通代码任务准奏没有“必须测试通过／御史背书”的硬门槛，见 [治理层准奏规则](../crates/ziyuan-governance/src/edicts.rs#L99-L155)。这是用户可显式决断的现行契约，本计划不偷偷改成强制审批链。

## 三、按风险排序

### P1：测试结论尚未绑定最终改动

**已核实源码事实：** [Evidence.tests](../crates/ziyuan-core/src/review.rs#L138-L157) 是最近一次测试的可选布尔值；[check_evidence](../crates/ziyuan-app/src/censorate.rs#L155-L160) 从最近一次指派后的工具事件倒序找 `run_tests`，不检查其后是否又成功写文件。[ToolInvoked](../crates/ziyuan-core/src/event.rs#L271-L278) 不记录测试输出、命令或被测内容摘要。

因此 1.4.1 的记录能证明“那次测试成功”，不能证明“当前最终暂存稿／本次逐段准奏组合通过”。后续开发版 4A 已补上时序失效判断及真实离线命令对照，见下节；仍没有被测内容、命令或外部依赖的快照绑定，不能宣称完整版本证明。

**影响：** 用户和御史可能把过早的通过记录理解为当前改动已验。应优先使结论准确，再考虑更丰富的报告；不能把模型复述当补证。

### P1：任务撤销与测试进程收尾需贯通验证

**已核实源码事实：** [Scheduler](../crates/ziyuan-runtime/src/scheduler.rs#L227-L254) 在超时／撤销时通知协作取消，执行线程收尾前保留许可；[Agent Loop](../crates/ziyuan-runtime/src/agent_loop.rs#L497-L504) 调用同步工具；`RunTests` 的等待循环只有自己的 600 秒时限，没有接收任务取消信号。现有 `timeout_fails_task_and_signals_backend` 测的是后端取消，不足以代替真实测试子进程验收。

**待验证：** 长测任务撤销后，测试命令／其后代能否及时退出，副本、日志与许可何时释放。此处不能声称已证实逃逸、越权写入或所有平台必然泄漏。已有沙箱及晚到结果丢弃机制须保留。

### P1：补提交按文件选取，尚未核对当前字节仍是准奏结果

**已核实源码事实：** [commit_applied](../crates/ziyuan-app/src/vcs.rs#L158-L181) 验证 `Applied`、算出路径后提交当前文件；未比较当前内容与实际获准的逐段组合。[commit_files](../crates/ziyuan-app/src/vcs.rs#L118-L152) 限定文件路径，Git 保留其他路径的已暂存改动，但“同文件后来又改了什么”是另一回事。

**待验证：** 准奏后手改同文件再补提交、同文件有其他工作区改动、相同任务号的旧尾注、失败后重试等场景。不能把“只提交列出的文件”直接宣称为“只提交获准的内容”。不回滚、不覆盖用户改动。

### P2：三端审阅与续办入口不完全一致

- Web 预览附改动版本，再调用 `apply_reviewed`；CLI／TUI 调用允许省略版本的 `apply_changes`。这是可确认的契约差异，不据此断言 CLI／TUI 可以越权写入；需验证旧预览、替换事件簿、逐段编号是否可能误用。
- CLI／Web API 可为已落盘任务补提交；TUI `m` 每次先准奏，Web 页面主要在待决改动时显示提交按钮。后端能续办不等于各端入口都清楚。见 [CLI Apply](../crates/ziyuan-cli/src/commands.rs#L358-L402)、[TUI m](../crates/ziyuan-tui/src/input.rs#L279-L298)、[Web Apply](../crates/ziyuan-web/src/edicts.rs#L160-L194)。
- 测试、复核、评定、落盘、提交与恢复须分别显示，不让“完成”“背书”冒充全部步骤已成功。恢复现有命令位于 `text recovery`，本批先解释其工作区含义，不随意改掉冻结命令。

## 四、分批实施与验收

### 4A · 验功有据：先让测试状态不误导

**首批最小交付：** 以最近一次指派为边界，识别测试之后又有成功暂存写入的情况；保留历史“当次通过”，但当前改动不再据此显示已验。逐段准奏后的组合未被测过时明确提示未知，不沿用全稿通过结论。不自动触发测试、模型调用、复核或落盘，不新增强制准奏门槛。

**实现落点：** runtime 工具审计、app 证据汇总与三端证据展示。先采用已有事件能可靠推导的时序；若需要重启后可证明的被测版本、测试命令与输出摘要，再单独设计增量证据事件，而非改变旧 `ToolInvoked` 或 `Evidence.tests` 的字段含义。旧日志缺证据就显示未知，不回填虚假成功。

**必验的对照：**

1. 写 A → 测试通过 → 完成：当次通过可见；写 A → 测试通过 → 再写坏的 B：不能说 B 通过。
2. 成功测试后又测试失败：失败优先；没有测试／上一尝试通过但新指派未测：当前未知。
3. 测试后失败的写入不改变稿件，与成功写入区分；时序不足以证明内容等价时宁可保守提示，不造已验证结论。
4. 两处改动一起通过、只准其中一处会失败的非对称样例：逐段组合不得继承全稿通过。默认不自动跑命令，用户仍可决断。
5. 重开会话、回放旧日志、CLI／Web／TUI 的事实一致；只读用户不能因此获得执行权。

4A 先交付并验收，再决定是否做更重的被测副本摘要与报告持久化；不要一开始引入全仓快照系统。

**2026-11-01 实施进度（4A 已结项，尚未发版）：**

- app 根据最近指派后的工具时序分别返回历史结果与适用性；成功写入在测试之后、或逐段组合改变时要求另验。没有改写 `ToolInvoked`、`Evidence.tests`、历史复核或考绩。复核提示和无模型回退均区分历史通过与当前适用性；失败测试仍按失败处理。
- CLI、Web、TUI 共用同一判断。Web 状态批量读取所选任务的指派／工具事件，不在每次轮询加载整个事件簿；新增提示不改变 viewer 权限、审批或执行入口。
- 持久回归覆盖写后测、测后写、失败写入、最近测试失败、上一尝试通过但新指派未测、逐段准奏及重开会话；批量查询与单件结果一致。恢复旧回退判断后，同一回归在“测后写仍背书”处失败；恢复修复后通过。
- 临时验证程序通过真实 `sealed_tools` 执行 `write_file`／`run_tests`：两文件全稿在副本通过后，只准其中一文件，实际落盘组合失败；另一个对照在通过后再写坏第二文件，实际落盘组合同样失败。两者重开后均保留历史通过、拒绝沿用为当前已验。**测试显式使用 `ZIYUAN_SANDBOX=off`，只验证证据时序和组合，不作为号舍隔离证据**；未调用模型。临时程序未保留为产品代码。
- `cargo clippy --workspace --all-targets --locked -- -D warnings` 通过；`scripts/smoke.sh` 通过（工作区 724 项测试通过，smoke 输出 `ZiYuan smoke test PASS`）。Web 三种基本状态、桌面／390 CSS 像素窄屏已实渲检查，无新增横向溢出；CLI 实际输出与 TUI `TestBackend` 三种渲染一致。界面数据为离线审计样例，不冒充模型实测。
- 实现提交 [4e78433](https://github.com/YuuUehara/Ziyuan/commit/4e784334ce4bfcaf952812ee9fb9a8de1072baf6) 的[六项 CI](https://github.com/YuuUehara/Ziyuan/actions/runs/41332688102)全部通过，包含 Windows／macOS／Linux，4A 按最小范围结项，进入 W0。磁盘外部改动、依赖变化、测试副本摘要及报告持久化仍未交付；结项不扩大为完整版本证明，也不表示已经发布新版本。

### 4B · 止令收兵：取消贯通到测试命令

先建立可控的本地长测命令及有后代进程的对照，验证撤销／超时后的真实状态，再修改等待与清理路径。让任务取消能够触达测试执行，明确终止、等待、日志读取与副本删除的顺序；只终止本任务拥有的进程，不按名字全局杀进程。

**验收：** 正常完成不受影响；撤销与超时都在有界时间内收尾；晚到测试结果不成为成功证据、不进入下一次尝试；许可在执行线程收尾前不提前释放；命令及其后代的退出、临时副本与日志清理均有实证。Linux／macOS 使用各自号舍实跑；Windows 的需要隔离场景继续失败关闭，不为凑通过而默认关沙箱。显式关闭号舍的进程生命周期测试与沙箱安全验收分开报告。

### 4C · 准奏入册：补提交与审阅一致

先复现已落盘后同文件变化的边界，再确定补提交前的内容核对。**默认拒绝把不能证明属于本件准奏的当前文件自动记入本件提交**，保留用户改动并给出人工处理路径；这是一项待实现、须经公开接口测试的收紧，不宣称当前已有。处理全准／逐段准奏、新文件、CRLF、提交失败重试及已有尾注；重试不重新落盘、不重复提交。

同步补齐 TUI／Web 的“已落盘、未提交”续办与明确错误，不强求三端布局一样；只要求相同材料与权限得到相同事实。对预览版本差异先用可复现输入判断，确有误用风险才收紧相应确认流程，不为统一形式新增破坏性必填参数。

**验收：** Git 与 jj 分别核对提交树；不夹带其他文件或同文件无关内容、不改用户暂存区以外的资料；旧预览拒绝或要求重新审阅；部分写入失败仍按既有恢复协议阻断，不把补提交伪装成写入恢复。桌面／窄屏、长错误、viewer 与键盘路径检查，保留可审阅截图及交互录像。

## 五、Windows 原生号舍：先立边界，再接执行

### W0 · 立界：威胁模型与设计验收

现状以 [ADR-0001](adr/0001-windows-sandbox.md) 和 [haoshe](../crates/ziyuan-runtime/src/haoshe.rs) 为准：W0 时尚无平台 crate，当前 W1a 新增独立实验探针，但 `auto`／`require` 对不可隔离的操作继续拒绝。W0 核对原生 Windows CI、目标系统版本、可用系统接口及 unsafe／FFI 审阅与维护责任；普通功能 CI 不代替隔离探针。

**交付：** 独立平台 crate 的接口设计、能力矩阵与可复现探针方案；列清测试副本允许写入范围、只读运行依赖、宿主源码与凭据保护、默认断网及子进程继承策略。比较 AppContainer／受限令牌／Job Objects 能各自保证什么，不预先将某个 API 等同完整隔离。按 ADR 再评估结果记录方案 B 的启动决定；条件未满足则列明阻塞项，保持方案 A 的执行政策。

**验收：** 每项能力有允许和拒绝对照，事先确定目标 Windows 版本与证据要求；说明创建失败、版本不支持、策略无法安装时如何失败关闭。无法提供文件和网络隔离的原型，只能报告较低能力，不准接成完整号舍。

**2026-11-01 W0 设计核对已完成：** 决定与完整边界集中在 [ADR-0001](adr/0001-windows-sandbox.md)，不再另建重复设计文档。选定 LPAC＋最小资源权限＋Job 的独立实验原型；首个原生目标是已核实的 Server 2025 `26100`／x86_64 MSVC，桌面 Windows 11 另行补验。W1a 只验启动、身份、Job 归属与句柄白名单，再依次验文件、网络、生命周期；不接 runtime／MCP，不改变生产失败关闭。官方 API 约束与现有功能 CI 已核对；W0 时平台 crate 与隔离探针尚未实现，W1a 当前进度见下。长期维护与独立安全签核在 W2 前仍须落实。

### W1 · 入舍：独立平台原型与安全探针

通过 W0 后实现 `ziyuan-sandbox-windows`，将必要 unsafe／FFI 限定在平台边界；不放宽工作区整体的 unsafe 禁令。对外能力等级沿用 ADR 的 `Unavailable`／`RestrictedProcess`／`FileSystemAndNetworkIsolated` 设计，是否已有实现必须单列，不能把规划类型当现成接口。

## 六、代码仓库索引与向量检索：先知出处，再论相似

### R0 · 编目：来源、权限与评测基线

现有 [ziyuan-memory](../crates/ziyuan-memory/src/lib.rs) 面向翻译定稿；`char-hash-v1` 不理解代码语义，不将其改名冒充语义模型。先评估嵌入接口、摘要和重建机制的实际复用成本，只复用真正共用的能力，代码记录不借用译书的段号或定稿资格。

**交付：** 明确支持语言／文件类型与首批仓库范围；记录仓库身份、提交及未提交内容摘要、路径、位置、分块规则和索引／模型签名。CLI 先行，计划提供显式建库、状态、查询与重建，命令形状在实现前审阅，不在本文件提前冻结。索引是可丢弃的派生缓存，不修改源码、暂存区或批准状态。

**验收：** 登记符号精确查找、自然语言同义描述、跨文件调用位置、相似但不适用、删除／改名、未提交变化及无匹配样本；用人工标注出处作答案，不能用待测模型自评。先测现有关键词搜索的命中率、错误命中及过期位置，再在选型前锁定 Recall@k、定位准确率、延迟、磁盘、建库时间及费用门槛。没有预先登记的基线和门槛，不进入 R2，不先许诺向量收益。

#### R0-v1：首批契约与离线样本

以下是 R1 的实现约束，不是当前已存在的产品索引。首批仅支持用户显式选定的**本地单一 Git 工作区**内 UTF-8 `.rs`、`.md`、`.toml`，单文件上限 256 KiB、准入文件合计 10 MiB；超限明确报告，不悄悄索引前半部分。不解析符号 AST 或调用图；“调用位置”首批只是可核对的文本候选，不推断真实调用关系。首批 CLI 操作语义为建库、状态、查询、重建，具体命令拼写留给 R1，不改现有命令。

| 记录／状态 | 必须保留与核对的事实 |
| --- | --- |
| 工作区身份 | canonical 根路径的本地身份摘要；不输出绝对路径，不用远程 URL 作为唯一身份，不把摘要当鉴权。不同工作树／副本分别建库 |
| 来源快照 | HEAD 对象 ID（空仓库明确为无 HEAD）、准入相对路径及原始文件字节 SHA-256 的排序清单摘要；包含未提交修改和获准的未跟踪文件。HEAD 相同不代表文件相同 |
| 位置与分块 | `/` 分隔相对路径、全文件原始字节摘要、0 起且右端不含的 UTF-8 字节范围、1 起且两端包含的行范围、块内容摘要；不规范化换行或 Unicode。初版计划 `lines-v1`：每块最多 40 行且最多 8 KiB、无重叠；超过块上限的单行明确跳过并报告 |

| 查询结果 | 路径、位置、文件与块摘要、来源快照身份及截断状态；候选不是授权、审批、测试或准奏结果 |

**读取与授权：** 建库范围与查询当前范围取交集，硬拒绝优先于任何显式 include：`.git`／`.jj`／`.ziyuan`、`.env*`、`.ssh`、常见私钥文件（`.pem`／`.key`）、生成物与依赖目录。尊重仓库 `.gitignore`／`.git/info/exclude`，规则作为本地控制输入，不作为检索材料；不读取机器全局忽略配置来改变可复现集合。未跟踪但获准的文本可准入，Git 跟踪状态绝不豁免排除或授权。首批不进入子模块、嵌套仓库或任何符号链接；发现越界路径即拒绝。硬链接与读前后换链须在 R1 做平台可行性与哨兵验证，条件未满足则报告路径／平台不可用，不据本契约声称抵御并发恶意文件系统。排除规则不是万能秘密识别器。

**失效与发布：** 索引是独立的可删除缓存，不能借用 `.ziyuan/memory` 的译书记录，也不修改源码、Git 暂存区或批准状态。R1 首版先以重新枚举准入路径、核对字节摘要与签名保证正确性；修改、删除、改名、切分支、忽略规则或范围变化均须明确报“需重建”，不把旧结果当当前，也不伪装“无匹配”。构建前后水位或文件摘要不一致不得发布；查询核对到输出间再变更时拒绝该次结果。临时构建失败／取消不覆盖上一份索引，损坏／新格式拒绝读取。并发锁、同卷发布及换链边界在 R1 通过真实测试后才称已实现。来源仅是磁盘工作树；`write_file` 尚未准奏的内存提案不是磁盘内容，首批不自动叠加。

**复用评估：** `ziyuan-memory` 的 `EmbeddingProvider`／`ModelSignature` 和 SHA-256 方法可供 R2 再评估；`MemoryRecord` 的段落身份、源译配对、定稿事件和 `Watermark` 的事件世代不能表达 Git 工作树。`MemoryIndex` 固定放在 `.ziyuan/memory`。写这段计划时它还不保存向量；1.15.0 的译文记忆已经把向量写进那份索引。即便如此，它记的是译书段落，表达不了 Git 工作树，所以这里说的是代码索引计划：不直接复用那份信封和发布器，也不新增“代码伪段落”适配层。R0 不改生产依赖，只有评测 example 用已锁定的 `ring` 开发依赖记录摘要。

### R1 · 寻章：本地安全建库与检索闭环

先做限定文件类型的可解释分块及关键词／符号精确检索；复杂语法解析逐语言扩展，不一开始引入调用图。默认本地、显式启动；先过滤仓库授权、忽略规则、敏感文件、生成物、依赖目录与越界链接，再读取和建库。单纯被 Git 跟踪不表示内容可外发；不承诺自动识别所有秘密，另设用户可核对的排除规则。

**验收：** 公开接口验证建库／查询不改源码，结果含可核对的路径、位置和内容版本；修改、删除、改名、切换分支、含未提交改动、配置改变及建库中途变化不得返回冒充当前的旧命中。越权文件既不进索引也不出查询结果；损坏或不兼容索引提示重建，发布失败不破坏上一份可用索引。覆盖跨进程重开、CRLF／Unicode 位置、取消与增量更新相对全量重建的等价结果；用临时哨兵文件检查读取／输出边界。

通过 R1 只称“代码索引与精确检索已交付”，不称代码向量化已完成。首批人工查询，不自动注入模型；后续接入代码任务时必须按当前玉玺范围再过滤、重查文件版本，返回候选不扩大读写权限。

### R2 · 会意：语义向量与混合召回

以 R0 固定样本比较关键词、现有字符哈希、本地语义嵌入及可选远程方案；嵌入配置与聊天模型分离，不假定 DeepSeek 聊天端点提供嵌入。优先评估本地方案；实际模型选择及下载资源另行确认。远程嵌入须先列明供应方、模型、外发文件范围、用量上限与停止条件，并取得授权；本计划不授权付费或外发仓库内容。

**交付与验收：** 实现通过门槛的提供方、向量索引及精确／向量候选的组合规则；模型、维度、分块规则或格式变化须失效重建，不能混用旧向量。固定语义改写样本须达到预先登记的收益门槛，精确符号查找不得因加入向量而退化；报告失败样本、错误命中、位置准确率与资源费用，不把相似分数当正确率。若方案未达标，保留 R1、记录 R2 未交付，不以字符哈希替名结项。进入任务材料前再次核对权限、内容版本和预算；仍不自动执行、准奏或提交。
