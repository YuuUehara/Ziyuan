# 1.2.2 验收记录

本页记录 1.2.2 发布前的检查结果。只写实际做过的检查；没做的检查列在最后，不算通过。各平台发行包由发布流程在推送标签后另行下载验收，结果以 GitHub Release 页面为准。

本页对应 [临时文件清理设计](../superpowers/specs/2026-10-31-temp-recovery-design.md) 与 [实施计划](../superpowers/plans/2026-10-31-temp-cleanup.md)。需求只有一条：**原子替换不再遗留需要手工删除的 `.ziyuan-tmp-*`**，同时不得误删仍在使用的写入，也不得改变已有命令的行为、输出字段与退出码。租约协议本身的可行性（原生 Windows 上建锁、试锁、改名与删除的实际行为）见[租约可行性报告](1.2.2-temp-lease-feasibility.md)，本页不重复。

## 本轮做了什么

1. **写入者一侧加租约**：原子替换先在目标目录建 `.ziyuan-lease-<id>`（`<id>` 为 32 位小写十六进制，内容一行 `ziyuan-lease v1 temp=<裸文件名> id=<id>`），再建临时文件，写内容、刷盘、加锁，核验路径仍指向自己，改名之后才关句柄并删租约。租约从临时文件创建覆盖到改名完成之后，清理者因此能凭「能否取到锁」「文件里写的 `temp=` 是谁」判断归属，而不必猜年龄或 PID。
2. **一个核验器**：候选识别、租约核验、受保护判断与决策都在 `ziyuan-runtime` 一处实现，修掉「临时名生成」与「临时名识别」两处字符串各写一遍的隐患。核验器不读恢复记录，受保护集合由调用方构造并传入。
3. **两条入口**：准奏（`apply_changes`）在落盘之前清目标所在目录；`ziyuan text recovery temps [--json] [--yes]` 清整个工作目录，默认只预览。
4. **报告**：路径一律工作区相对路径，逐项给处置与原因，「按路径跳过」与「超过深度上限」分列，绝对路径不外泄；文本与 JSON 走同一套判定与同一个脱敏出口。
5. **退出码**：按冻结约定，跑完为 0（含预览列出可清理项），扫描／删除的 I/O 失败与读不了的目录为 1，用法错误为 2。

### 发版提交上复跑

登记版本号（`Cargo.toml` 升到 1.2.2、`RELEASES` 追加 `"1.2.2"` 并把长度改为 19）之后，在同一台 Windows 机器上按上表重跑了一遍：`cargo fmt --check` 通过，`cargo test -p ziyuan-storage` 86 项通过（`RELEASES` 末项须与 `CARGO_PKG_VERSION` 一致的那条断言含在内），`cargo test --workspace --locked --no-fail-fast` 退出码 0。上表的逐 crate 数字取自这一次复跑。

复跑中观察到一次与本版改动无关的偶发失败：在登记版本号**之前**的提交上，整仓并行跑时 `ziyuan-web` 的 `courier_posts_edicts_and_urgent_ones_jump_the_queue` 失败过一次，单独重跑 0.08 秒通过，之后整仓复跑未再出现。该用例走的是 `ureq` + `spawn_blocking` 的本地 HTTP 回路，与本版改动的临时文件清理、租约、工作区世代都不相交；本轮未查明根因，如实记为未解释的偶发，不声称已修。

## 未测或有限制

- **只在 Windows 上测试。** Unix 专用的符号链接用例（`symlinked_candidate_is_never_followed`）已写但本机未运行，因此「链接绝不被跟随」一行记作**已写未运行**，不计入通过；Linux、macOS 只由发布流程的构建与启动检查覆盖，没有人工走查。
- **不支持文件锁的文件系统上无法写入。** 这类文件系统上 `File::try_lock` 会失败，`Lease::hold` 因此失败，于是**该工作目录里每一次受管写入都会失败**——租约在写入路径上，不只影响清理路径。部分网络文件系统属于这种情况，本机没有这样的样本，未实测；约定见[稳定性约定 · 1.2.2 新增](../stability.md)第 9 条。
- **TUI 只报清理诊断的条数。** 准奏后状态栏只在有诊断时追加「（N 项临时文件未能清理）」，不报路径与原因（全屏画面没有可滚动的诊断区，往 stderr 写会被下一次重绘抹掉）。要看清明细，用 `ziyuan text recovery temps`。
- **未在本轮验证：app 层「记录不可读即不清理」的端到端行为。** 要在发布记录之后、`protected_targets()` 之前注入故障才能复现，本轮没有做故障注入。该选择由纯函数 `sweep_protection` 上的单测 `sweep_protection_fails_closed_when_the_record_is_unreadable` 结构性覆盖，不是端到端证据。
- **未验证：设计里「项目文件恰好与临时名同形」在 app 层的碰撞。** 运行时层面由 `apply_changes_keeps_a_protected_temp` 与 `protected_relative_path_wins_before_any_io` 覆盖，本轮没有在真实准奏流程里造出这种同名目标。
- **并发准奏用例的间歇失败已修。** 全量运行中曾见过 `concurrent_approvals_on_two_tasks_never_interleave` 失败（前后共两次），原因是它断言「两个线程都成功」，而受管写入在锁外 `ensure_writable()` 撞上另一进程已发布的记录或它留下的奇数世代号时会**立刻拒绝**——那是设计行为，测试假设过强。现已抽出 `approve_with_retry`：只有工作区此刻仍不可写才算可重试，等对方收尾后换新会话重来；并新增确定性用例 `approval_retries_until_the_other_process_finishes`，用 `foreign_record` 把「已发布未收尾」的现场摆死，确定地走一遍重试路径（把可重试判据改成恒 `false` 时该用例失败）。
- **研究探针不属于本次交付，但它确实在版本库里。** `crates/ziyuan-runtime/tests/temp_lease_probe.rs` 与 `crates/ziyuan-runtime/tests/support/temp_lease_probe.rs` 是设计阶段的探针（`git ls-files` 可查，随可行性实验一并提交），保留是为了让[可行性报告](1.2.2-temp-lease-feasibility.md)的结论可复现；验收记录早前写成「未提交、CI 不编译」是错的，发版前已更正。它们会再起子进程跑 `probe_child_entry`，其中 `probe_invalid_case_does_not_mutate_scratch` 故意传入未知 case，日志里因此会出现一条预料之内的子进程失败（`child configuration: unknown case`），父用例仍通过；本版 34 项全部通过。它们不属于本版交付的功能，所以上面用例总数把它们扣掉。
- **硬链接数异常未覆盖。** 既没有定义为保留原因，也没有检查，本版不声称能识别这类残留。
- **非符号链接的目录重解析点仍在范围内。** 云占位符一类的重解析点能通过 `is_dir()`，类型判断依赖 `symlink_metadata`，本机没有造出这类样本。
- 协议本身其余的限制（租约残片、一份坏租约挡住整目录、旧版无租约永不自动清理、同名重建未处理、同进程活跃集合不在协议内、Windows 上持锁不阻止他人改名、链接与硬链接边界）已逐条写在[稳定性约定 · 1.2.2 新增](../stability.md)与设计文档的「已知限制」里，本页不另列。
