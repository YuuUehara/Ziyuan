# 1.2.2 临时租约可行性验证报告

状态：第一轮结论为协议**尚未闭合**；第二轮租约载体验证见文末，候选协议在原生 Windows／NTFS 上闭合了已识别的空窗，并已获用户批准写入设计文档；第三轮结清了锁顺序、恢复记录引用并补上加锁前回收窗口。生产实现与发版仍待另行批准。本报告只是实验证据，不是产品验收，也不代表 1.2.2 已修复。

## 结论

现有机制可以可靠判断“某一进程正持有某文件的锁”，但**不足以**支撑安全删除临时文件：

1. 跨进程锁与强杀释放可用（见观察一）。
2. 现有替换流程全程没有加锁，且存在两处无保护空窗：创建后到（未来）加锁前、关闭句柄后到改名前（见观察三、四）。
3. 原生 Windows 上，能否在他人持锁期间改名或删除，取决于写入者打开文件时授予的共享模式：按 std 默认的 `FILE_SHARE_READ|WRITE|DELETE` 打开时，8 次操作全部成功；不给 `FILE_SHARE_DELETE` 时，8 次全部被拒（错误码 32）。现有 `create_temp` 用 std 默认值，即可被他人改名／删除。因此“清理者取得锁”既不证明文件陈旧，也不能防止与存活写入者互相破坏；清理必须依赖显式归属证据（见观察二）。
4. 旧版临时文件没有归属记录，只能记为未知并保留（见观察五）。
5. 无论锁观察到什么，同一进程内的清理仍需活跃集合或等效互斥，因为同进程的锁观察不能替代对“本进程正在写哪些文件”的记录。

按实施计划 Task 4 第 4 步的停止条件：证据不足以写下一个完整协议，本轮**不补充**具体协议、不修改 `replace.rs`、不新增清理命令。下一轮须另行获批。

## 观察

### 一、跨进程锁、强杀与正常释放

- 子进程持排他锁期间，父进程另开句柄非阻塞试锁得到 `WouldBlock`（记为 Busy）。
- 强杀并回收子进程后，父进程在截止时间内取得锁。
- 子进程收到 CONTINUE 正常退出后，父进程同样能取得锁。
- 相关测试：`cross_process_lock_blocks_live_holder_and_releases_after_kill`、`cross_process_lock_releases_after_continue`。

### 二、同进程句柄与 Windows 共享语义

- 同进程内另开 `OpenOptions` 句柄：Busy。`try_clone` 句柄：Busy。关闭全部持有句柄后可重新取得。这些分类在 Windows 上由断言核对，不只是打印。
- 子进程持锁、写入并 `sync_all` 后，父进程分两种共享模式，针对“临时文件已存在／目标不存在／目标已存在旧内容”，共 16 次操作（改名 8 次 + 删除 8 次；每种共享模式各 8 次）：
  - `FILE_SHARE_READ|WRITE|DELETE`（std 默认）：8 次全部成功，报 `kind=None`、`raw_os_error=None`。改名后目标为完整新内容、临时文件消失；删除后目标保持旧内容或不存在。
  - `FILE_SHARE_READ|WRITE`（去掉 `FILE_SHARE_DELETE`）：8 次全部被拒，`raw_os_error=32`（共享冲突），目标与临时文件内容均不变。
- 持锁句柄上继续写入与 `sync_all` 在 Windows 上成功，未观察到锁冲突；子进程仍把该情形以类型化观察回报，不默认成立。
- 相关测试：`same_process_independent_handles_are_observed`、`rename_with_live_handle_records_native_semantics`、`delete_with_live_handle_records_native_semantics`。

含义：锁是协作式的，不是删除防护；能否被外部改名／删除由写入者自己的共享模式决定。现有 `create_temp` 用 std 默认值，因此其他进程可以在它持锁期间把它改名或删除。清理者看到 Busy 可以谨慎跳过；看到 Acquired 不能推出“没人正在写这个文件”。

### 三、关闭句柄后、改名前

现有 `fill` 是创建→写入→同步→关闭句柄，全程不加锁；加锁是本次验证的候选协议步骤，不是现状。实验按“创建→加锁→写入→同步→关闭句柄”的顺序，在改名前停住：父进程此时**取得**了该临时文件的锁，证明只要在 `fill` 内部加锁，关句柄到改名之间就必然失守。父进程释放后子进程改名成功，目标为完整新内容。

相关测试：`close_before_rename_exposes_unprotected_interval`。

### 四、创建后、加锁前

子进程创建临时文件后、加锁前停住，父进程取得锁，证明该区间存在：保护必须从文件可见之前开始，即“先建租约、再加锁、最后建临时文件”。实验只观察，未删除文件。

相关测试：`create_before_lock_exposes_unprotected_interval`。

### 五、旧版无归属文件

子进程以旧版方式打开临时文件、不持有任何归属记录并停住（测试断言它确实仍在运行）。父进程虽然取得了锁，规则仍判定为 `OwnershipUnknown`，文件与内容保持不变。该测试校验的是“无租约记录不得据锁判陈旧”这条规则编码，不是某种机制实现。

相关测试：`legacy_unleased_file_is_never_proven_stale_by_lock_alone`。

## 稳定锁身份

`File::try_lock` 认的是打开时的文件对象，不是路径字符串。实测（Windows／NTFS）：同一文件持锁后改名，经新路径试锁仍为 Busy；对其建立硬链接，经链接试锁同样为 Busy；而删除后按同名重建，新文件可以立即取得锁。也就是说改名与硬链接仍指向同一对象，只有删除后重建才可能落到另一对象上。

因此租约不能只靠“按路径能取锁”表达，需要能证明“这条租约记录仍指同一个临时文件”，例如记录文件标识或内容摘要。删除后重建与“改名后再建同名文件”的竞争顺序仍未验证，下一轮须补。

相关测试：`lock_identity_survives_rename_and_hardlink_but_not_recreate`。

## 租约载体验证

状态：候选协议在原生 Windows 上闭合了“关闭临时文件句柄到改名之间”的空窗。用户已于 2026-10-31 批准把协议写进设计文档（见[清理设计](../superpowers/specs/2026-10-31-temp-recovery-design.md)）；生产实现与发版仍须另行批准，本报告不表示 1.2.2 已可实施。

### 载体格式

- 位置：与临时文件同目录，文件名 `.ziyuan-lease-<id>`，`<id>` 为 32 位小写十六进制随机值（由 `RandomState` 生成，与既有 ID 同法）。
- 创建方式：`create_new`。同名已存在即失败，第二个写入者据此报冲突并退出，不截断、不复用他人的租约。
- 内容：恰好一行，以 `\n` 结尾：`ziyuan-lease v1 temp=<临时文件名> id=<32 位小写十六进制>`；`temp=` 只含文件名，不含目录。

### 生命周期顺序

建租约（`create_new` + 写内容 + `sync_all`）→ 租约加锁 → **核验租约路径仍指向自己这个文件** → 建临时文件 → 写入 → `sync_all` → 改名 → 关闭租约句柄 → 删除租约。

清理侧只允许非阻塞试锁：探到 Busy 即保留，绝不等待租约锁。临时文件名里没有租约 `id`，所以清理者必须反向找：列出同目录的租约，逐个试锁，取得锁后读 `temp=` 与候选比对；认领者有且仅有一个才删除，多于一个保留（`TempAmbiguous`）。

### 各阶段的强杀可回收性

| 强杀点 | 目录残留 | 清理决策 | 依据 |
| --- | --- | --- | --- |
| 已建租约并加锁，尚未建临时文件 | 仅租约 | 删除租约 | 租约 v1、`id` 与文件名一致、引用的临时文件不存在 |
| 已建租约与临时文件，写入后（含持锁） | 临时文件 + 租约 | 先删临时文件，再删租约 | 取得租约锁、版本 v1、`temp=` 与实际一致、临时文件是普通文件 |
| 正常完成 | 仅改名后的目标文件 | 不清理 | 写入者按顺序自行关闭租约句柄并删除租约 |

强杀后租约锁由操作系统释放，父进程在截止时间内取得锁。相关测试：`killed_before_temp_creation_leaves_only_lease`、`killed_writer_lease_is_reclaimable`。

### 保留分支与可区分原因

清理决策用测试专用枚举表达（`LeaseDecision::Remove { reason }` 或 `Keep { reason }`），每个用例断言具体值，不是恒真闭包。

| 场景 | 决策 |
| --- | --- |
| 租约被存活写入者持有 | `Keep { LeaseBusy }` |
| 符合命名但没有租约认领的临时文件 | `Keep { TempWithoutLease }` |
| 租约版本未知 | `Keep { LeaseUnknownVersion }` |
| 租约内容无法解析：格式错误、超大、非 UTF-8、字段重复、`temp=` 不是单一文件名 | `Keep { LeaseUnparsable }` |
| 租约 `id` 与文件名不一致 | `Keep { LeaseIdMismatch }` |
| 租约 `temp=` 与目标临时文件不一致 | `LeaseContentMismatch`（单租约原语内部判定，目录扫描视为“不认领”） |
| 租约合法但引用的临时文件已不存在（按临时文件恢复时） | `Keep { TempAlreadyAbsent }` |
| 临时文件不是普通文件 | `Keep { TempNotRegular }` |
| 租约路径不是普通文件 | `Keep { LeaseNotRegular }` |
| 同一候选被两个合法租约认领 | `Keep { TempAmbiguous }` |
| 租约清理路径发现临时文件仍在 | `Keep { TempStillPresent }` |
| 临时文件路径被恢复记录引用（受保护集合命中） | `Keep { RecoveryReferenced }` |
| 租约清理路径发现租约已不存在 | `Keep { LeaseAlreadyAbsent }` |

上表每一行都有用例断言具体值，包括 `TempNotRegular`、`TempStillPresent`、`LeaseAlreadyAbsent`（见 `uncovered_keep_branches_are_reachable`，该用例同时验证孤儿租约确实可被删除，说明保留分支不是构造上不可达）。这些用例都断言了：临时文件未被删除且内容未变（`LeaseAlreadyAbsent` 一例没有临时文件可比，只核对决策与目录现状）。

两个解析约束值得单独说明：

- `temp=` 必须是单一普通文件名组件。只拒绝分隔符不够：在 Windows 上 `join("C:temp")` 或 `join("a:b")` 会用该名字替换整个基准路径，所以按路径组件判断，含驱动器前缀或冒号的名字一律判为无法解析。
- 租约内容读取有 4096 字节上限，非 UTF-8 或读取失败都归入“无法解析并保留”，不会让整次清理以 I/O 错误中止。

两条入口分开：租约清理只删“引用临时文件已不存在”的孤儿租约，临时文件恢复只在临时文件存在且归属证据齐全时删除。同一状态不会被两条路径同时判为既删又留，但这一分工需要用户在设计阶段确认。相关测试：`cleaner_keeps_temp_while_lease_is_held`、`temp_without_lease_and_foreign_leases_are_retained`、`killed_writer_lease_is_reclaimable`、`uncovered_keep_branches_are_reachable`。

### 冲突与锁等待

- `create_new` 对已存在的租约返回 `AlreadyExists`。测试直接核对该错误码，并核对第二个写入者报冲突后退出、原租约内容逐字节不变。测试：`second_creator_conflicts_instead_of_overwriting`。
- 写入者等待已被占用的租约锁时使用 300 毫秒量级上限，实测 300 ms 超时返回 `TimedOut`；双方仍能收尾，子进程正常退出，无遗留进程。测试：`lease_lock_wait_has_deadline`。

### 两个清理者并行

租约句柄在整个删除过程里保持加锁：取得租约锁 → 核验 → 删临时文件 → 删租约 → 释放句柄。若在删除前先释放锁，“核验后删除”就不再原子，两个清理者可各自核验通过并各删一次，违反“不得重复删除或误报成功”。

这个缺陷已被确定性复现，不再只是推断。测试用一个只在测试中使用的交错点（位于首次删除之前）：先让第一个清理者停在核验之后，等第二个清理者启动并有约 1 秒机会进入核验，再放行第一个。交错点按测试目录绑定，只在本次测试自己的临时目录上触发——测试二进制默认并行，若不限定目录，另一用例的清理会误触发它。

- 正确顺序：第二个清理者只能观察到租约被占用，实测 `Remove { WriterDeadLeaseVerified }` + `Keep { LeaseBusy }`，只有一次删除，目录清空。
- 缺陷顺序（先释放锁再删除）：同一用例 **10 次全部失败**，证明它确实能抓住该缺陷。
- 正确顺序下连续 5 次全量并行运行全部通过（当时 27 项；第三轮补齐后目标整体为 34 项）。

早期的线程同时启动写法看似能测并发，实际上在缺陷顺序下也照样通过（15 次全过），因为第二个清理者常常在释放锁之前就到，得到 Busy；所以那种写法只是冒烟测试，已替换为上述受控交错。

测试：`two_cleaners_never_double_delete`。

### 覆盖空窗的证据

`lease_covers_close_before_rename_window` 让子进程在关闭临时文件句柄、尚未改名时停住：父进程对临时文件本身取得锁（第一轮的无保护空窗仍在），同时对租约得到 Busy。先故意让辅助在关闭临时句柄时一并释放租约，得到 RED：该用例 0 passed / 1 failed，失败断言为“lease must be held by the writer: Acquired”；再改为持续持有租约到改名完成，得到 GREEN。

### 第二轮审查后修正

第二轮独立审查又发现五处问题，均已修正并复验：

1. 交错点原先是进程级全局，测试二进制并行时其它用例的清理会误触发，导致误报失败。已改为按测试目录绑定；收窄后仍能用缺陷顺序 10 次全失败、正确顺序 5 次全通过证明其回归价值。
2. `temp=` 原只拒绝分隔符，`C:temp` 这类带驱动器前缀的名字在 Windows 上 join 时会替换基准路径。已改为要求单一普通文件名组件，并加用例。
3. 租约读取原先无上限，非 UTF-8 内容会以 I/O 错误中止清理而不是保留。已加 4096 字节上限、非 UTF-8 与读取失败一律归入 `LeaseUnparsable`，并拒绝重复字段。
4. 报告原先把三个未被覆盖的保留分支列为已有用例。已补 `uncovered_keep_branches_are_reachable` 覆盖它们。
5. 报告状态行与结论互相矛盾。已把状态行限定为“第一轮未闭合，第二轮见文末”。

### 结论

在原生 Windows／NTFS 上，候选租约载体闭合了第一轮识别的“关闭句柄到改名之间”空窗，并给出强杀后各阶段可回收、竞争冲突、保留分支与锁等待时限的证据。就本轮问题而言该候选协议**可闭合**，用户已批准其写入设计文档；本报告不宣布 1.2.2 已可实施，也不宣布任何缺陷已修复。

## 锁顺序与恢复记录引用（2026-10-31 第三轮结清）

上一节“未验证”里的两项不需要新的租约实验，结论如下。

### 清理器与工作目录锁的锁顺序

不需要新实验，因为等待结构已由代码与既有用例确定：

- `Workspace::lock`（`crates/ziyuan-storage/src/workspace.rs`）有两处等待：进程内 `Reservation` 的 Condvar 与 `.ziyuan/write.lock` 的 `try_lock` 重试。两者共用同一截止时间，最坏结果是 `WorkspaceError::Timeout`，不存在无限等待。
- 同进程第二个句柄取锁会超时而非重入，已有用例 `independent_handles_exclude_and_drop_releases` 断言；跨进程阻塞与强杀释放已由本报告第一节实验证明。
- 受管事务 `write_transaction`（`crates/ziyuan-app/src/edicts.rs`）在持有工作目录锁的状态下调用 `apply_changes`，所以“写入前的自动清理”发生在已持锁的进程内。
- 租约一侧只有非阻塞试探（清理者）与自建文件取锁（写入者，300 毫秒上限）。

结论是一条规则：清理器在任何入口都不获取工作目录锁。自动入口若取锁会自锁到超时；手工入口会挡住写入者、可能让写入超时，且没有收益。锁顺序因此是单边的（写入者：工作目录锁 → 自建租约 → 临时文件；清理者：只试探租约），没有任何主体在持有一把锁时等待另一把，成不了等待环。

仍未取证据的部分：若日后把清理器嵌进写入事务，需要一条回归用例证明“事务内调用清理不会取锁”。这条依赖生产接口定形，现在写不出来。

### 恢复记录引用核验

同样不需要新实验，但要把核验降级为“调用方传入受保护集合”：

- `RecoveryRecord.targets[].path` 是可移植相对路径，校验见 `is_portable_relative`（`crates/ziyuan-storage/src/recovery.rs`）：拒绝空、`\`、`:`、NUL、空段、`.`、`..`。
- 临时文件名只在 `replace_target` 内部生成，从不写入记录，所以记录不会引用“临时文件本身”。
- 真实碰撞是项目文件恰好与临时名同形：此时记录会引用它，而它按严格命名正是清理候选。
- 存储层自己的原子写入在 `.ziyuan/` 内用 `{name}.tmp-<pid>-<nanos>-<n>`，与 `.ziyuan-tmp-*` 不同；清理器不进入 `.ziyuan/`。

用例 `recovery_referenced_temp_is_retained` 已加入 `crates/ziyuan-runtime/tests/temp_lease_probe.rs`：同一份同形临时文件与合法租约，不传受保护集合时返回 `Remove { WriterDeadLeaseVerified }` 并删除文件（证明断言非恒真）；传入后返回 `Keep { RecoveryReferenced }`，文件与租约都保留。

### 加锁前回收窗口（第三轮新发现）

第二轮没有覆盖这一条：孤儿租约路径会在“写入者已写好租约内容、尚未加锁”时看到一个合法、未加锁、引用的临时文件还不存在的租约，因此完全可以把它当残留回收，而写入者其实还活着。

原生 Windows 实测：名字被删除后，写入者手上的句柄再加锁**仍然成功**（观测值 `locked=true gone=true`）。所以“加锁成功”不能证明租约还在，写入者必须在加锁后核验路径仍指向自己的文件（`symlink_metadata` 成立且为普通文件），不成立就放弃、且**在创建临时文件之前**放弃。

用例 `writer_aborts_when_its_lease_was_reclaimed_before_the_lock` 用同一套子进程协议对比两种写法：

- 不核验（缺陷模型）：写入者继续建临时文件，返回 `LEASE_PROCEED locked=true gone=true`，目录里留下一个没有任何租约指向的临时文件；再用临时文件恢复入口查它，只能得到 `Keep { TempWithoutLease }`，也就是一个永远无法自动证明陈旧的残留。
- 核验：写入者返回 `LEASE_ABORTED locked=true gone=true`，目录保持为空。

因此协议补上一步：`Held` 之后、创建临时文件之前核验路径。加锁成功后清理器再也取不到锁，路径不会再被回收，核验一次即充分。这一步已写入设计文档的写入者状态机与失败降级表。

### 归属只能反向找（第三轮审查修正）

原先把清理写成“看同目录有没有 `.ziyuan-lease-<id>`”，但候选名 `.ziyuan-tmp-<pid>-<nanos>-<counter>` 里没有 `id`，那样写等于假设调用方会凭空给出 `id`，无法实现。已改为目录扫描：

1. 列出租约 `.ziyuan-lease-<id>`，`id` 只从文件名读取；
2. 逐个非阻塞试锁，取得锁后才读内容，`temp=` 指向本候选的才算认领者；
3. 认领者恰好一个、且目录里没有读不懂或版本未知的租约才删除；没有认领者则 `TempWithoutLease`（目录里有坏租约时改报那类原因）；多于一个则 `TempAmbiguous`；
4. 目录里任何一个租约被占用，本候选保留（`LeaseBusy`）——读不到内容就不能排除它是主人。

用例 `sweep_finds_the_lease_that_names_the_temp` 在同一目录放两份租约（一份指向别的文件），断言只删对被认领的那份、且只消费认领者的租约。RED 证据：把“`temp=` 必须与本候选一致”改成恒真后，两份租约都成了认领者，决策变成 `TempAmbiguous`，用例 0 passed / 1 failed。

用例 `sweep_keeps_temp_claimed_by_two_leases` 断言两个合法租约同时认领时保留。RED 证据：把 `TempAmbiguous` 改成“取第一个认领者删除”，用例 0 passed / 1 failed。

用例 `sweep_refuses_a_directory_with_an_unreadable_lease` 断言“一份合法认领 + 一份读不懂的租约”也不删：读不懂的租约可能同样指向该候选，一份认领不足以证明归属。删掉那份坏租约后同一目录立刻可清理，说明保留不是因为规则本身失效。RED 证据：把实现改成“有唯一认领者就删”，用例 0 passed / 1 failed。

用例 `sweep_checks_candidate_type_before_looking_for_a_lease` 断言候选类型先于租约判断：一个名为临时文件的**目录**，在完全没有租约的目录里也必须报 `TempNotRegular`，不能因为“没有租约”就先报 `TempWithoutLease`。RED 证据：去掉第 4 步的类型前置判断，用例 0 passed / 1 failed。

### 非普通文件与受保护路径（第三轮审查修正）

- 类型判断改用不跟随链接的 `symlink_metadata`，租约与候选两侧都查：租约路径是目录时 `Keep { LeaseNotRegular }`。用例 `lease_that_is_not_a_file_is_never_followed` 断言临时文件不被删除、孤儿租约路径也返回同一原因。
- 受保护集合必须按工作区相对路径比较。用例 `recovery_referenced_temp_is_retained` 增加嵌套目录分支：`sub/<name>` 命中集合时保留，改用裸文件名比较时同一份文件被删除，说明用错形式就会漏保护。目录扫描入口因此带上目录的工作区相对前缀（根目录为空串，下一级为 `sub/`），前缀只用于比较，不拼接到任何实际路径。同一用例还断言受保护判断发生在打开租约之前——目录里没有租约时仍返回 `RecoveryReferenced`，先读租约的实现只会得到 `TempWithoutLease`。RED 证据：把前缀拼接收回裸文件名，目录扫描用例 0 passed / 1 failed。
