# 1.2.1 验收记录

本页记录 1.2.1 发布前的检查结果。只写实际做过的检查；没做的检查列在最后，不算通过。各平台发行包由发布流程在推送标签后另行下载验收，结果以 GitHub Release 页面为准。

## 本轮做了什么

把准奏的落盘从「先写文件、再记事件、两者之间没有保护」改成受管写入：

1. 取工作目录锁（同进程登记 + 跨进程文件锁，共用等锁预算）。
2. 锁内复核世代号与恢复记录，有未收尾的写入时拒绝。
3. 记下每个目标改动前后的摘要、事件批次与事件簿位置，发布恢复记录。
4. 世代号推进为奇数，逐个文件原子替换（同目录临时文件 + 刷盘 + 改名）。
5. 记事件，成功则把记录转为已完成、世代号回偶数、删掉记录。

中途崩溃留下的状态是「记录已发布、世代号为奇数」，下一次写入会被拒绝，须先用 `text recovery` 核对收尾。这消除了此前「文件已经写了、事件却没记上」且无从察觉的情况。

| 时钟批次与记录一致 | 文件事件簿上本批是否记时辰，由发布记录时一次钉死，实际追加沿用同一决定；盘上事件簿与内存条数一致 |

测试先行：准奏原子替换的首轮 RED 是**行为**失败——在直接写入的仪器化基线上 8 个「旧字节保持完整」断言失败，随后改为原子替换转绿；恢复记录校验器同样先以空校验器跑出 15 项失败再实现。不是把编译失败当作证据。

## 未测或有限制

- **只在 Windows 上测试。** Unix 专用的符号链接用例已写但本机未运行；Linux、macOS 由发布流程构建与启动检查，没有人工走查。
- **不保证一个批次的多文件对外同时可见。** 只保证单个文件要么是旧内容、要么是新内容。
- **不防绕过紫垣的外部写入者。** 检测到文件被外部改动时拒绝再写，但外部进程可以在任何时刻直接改文件。
- **原子替换会生成新的文件身份。** 不保留所有者、ACL、扩展属性与硬链接关系；Unix 权限位会保留，只读文件会被拒绝而不是清掉只读标记。
- **进程被杀可能留下临时文件**（`.ziyuan-tmp-*`），本版不自动清理，需手工删除。
- **收尾只做摘要核对，不重新执行业务写入。** 目标内容对不上记录时拒绝，需要人自行判断并修正。已发布但一个文件都没写时，`finish` 也不会替你决定，须重新准奏或明确放弃。
- **译书材料写入尚未并入同一把工作目录锁**，仍用原有的目录锁与原子替换，计划在 1.2.2 处理。因此 1.2.1 不声称译书材料与准奏之间已经完全互斥。
- **Web 端未做版本冲突的交互处理**，也未见真实浏览器走查本轮改动（本轮没有前端改动）。
- 恢复记录中的事件位置按「写入前事件簿状态」记录：`history_sha256` 与 `expected_bytes` 都是本批追加**之前**的口径，`expected_events` 则是追加**之后**应有的条数。不同批次是否带一条时辰，由发布记录时一次决定、实际追加沿用，因此两者始终对得上。
